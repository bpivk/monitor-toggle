# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a Windows Forms (.NET 10) desktop application, not a web/React project. There is no `components.json`/Tailwind/shadcn — the shadcn initialization gate does not apply (tech stack is WinForms, not React/Next.js/Vite). This contract adapts the standard UI-SPEC template to WinForms concepts: the "Color" section specifies exact `System.Drawing.Color`/`SystemColors` values per theme instead of Tailwind hex tokens; "Spacing"/"Typography" describe what stays unchanged (existing Designer-generated layout/font) since this phase's scope is exclusively light/dark **recoloring and flat styling**, not a layout or type redesign. Two of six checker dimensions (Registry Safety, and most of Spacing) are genuinely not applicable to this phase — marked N/A below rather than fabricated.

## Spacing Scale

Not applicable in the standard 4px-multiple sense — **this phase makes zero layout/spacing changes**, with one exception:

| Token | Value | Usage |
|-------|-------|-------|
| Existing layout | unchanged | All control `Location`/`Size` values in `MainForm.Designer.cs`/`SettingsForm.Designer.cs`/`MonitorConfirmDialog.Designer.cs` stay exactly as they are today. This phase recolors and restyles controls in place — it does not resize, reposition, or reflow anything. |
| `GroupBox`→`Panel` replacement border/caption spacing | 1px flat border (see Color section); caption `Label` positioned exactly where the `GroupBox`'s built-in caption text currently renders (top-left inset, ~9px from the panel's left/top edge — match the existing `GroupBox` caption position pixel-for-pixel so re-parented child controls need zero position adjustment) | `grpMonitor`, `grpAudioDevices`, `grpAppPath` (THEME-05) |

Exceptions: The `GroupBox`→`Panel` refactor is a structural change (new control type) but must preserve the existing outer bounding box (`Location`/`Size`) exactly, and every child control currently parented to each `GroupBox` keeps its existing `Location` (relative to the new `Panel`, unchanged) — this is a control-type swap, not a re-layout. Do not introduce new spacing values anywhere in this phase.

## Color

This is the core contract of the phase. Two theme states — **Light** and **Dark** — must both be fully specified per control category. Base-layer coloring (most `Label`/`TextBox`/`ComboBox`/`CheckBox`/`Button` fill+text) comes from `Application.SetColorMode(SystemColorMode.System)` automatically and needs no explicit color literal in application code. The values below are **only** for the confirmed gaps requiring hand-written overrides (per 12-RESEARCH.md Pattern 5): `DataGridView` (`dgvMonitors`), `GroupBox`→`Panel` replacement, and `txtHotkey`'s three hand-rolled state colors. Do not add explicit color overrides to any control not listed below — that would duplicate/fight `SetColorMode`'s own handling (Pitfall 1/8).

| Role | Light value | Dark value | Usage |
|------|-------------|------------|-------|
| Dominant / surface (60%) | `SystemColors.Control` / `SystemColors.Window` (managed by `SetColorMode`, no literal needed) | Managed by `SetColorMode` — do not hardcode; this is the base form/control background `SetColorMode` already owns | Form background, standard control surfaces |
| Secondary — `DataGridView` grid surface (30% of the Settings screen; the single largest recolor surface in this phase) | `grid.BackgroundColor = SystemColors.Window`; `DefaultCellStyle.BackColor = SystemColors.Window`; `DefaultCellStyle.ForeColor = SystemColors.ControlText`; `GridColor = SystemColors.ControlLight`; `ColumnHeadersDefaultCellStyle.BackColor = SystemColors.Control`; `ColumnHeadersDefaultCellStyle.ForeColor = SystemColors.ControlText` | `grid.BackgroundColor = Color.FromArgb(32,32,32)`; `DefaultCellStyle.BackColor = Color.FromArgb(45,45,48)`; `DefaultCellStyle.ForeColor = Color.FromArgb(240,240,240)`; `GridColor = Color.FromArgb(70,70,70)`; `ColumnHeadersDefaultCellStyle.BackColor = Color.FromArgb(32,32,32)`; `ColumnHeadersDefaultCellStyle.ForeColor = Color.FromArgb(240,240,240)` | `dgvMonitors` (THEME-04) — matches 12-RESEARCH.md's verified code example exactly. `EnableHeadersVisualStyles = false` MUST be set before header colors take effect (well-known gotcha). |
| Selection / accent (10%) — reserved exclusively for the elements listed under "Accent reserved for" below | `DefaultCellStyle.SelectionBackColor = SystemColors.Highlight`; `SelectionForeColor = SystemColors.HighlightText` | `DefaultCellStyle.SelectionBackColor = Color.FromArgb(0,90,158)`; `SelectionForeColor = Color.White` | `dgvMonitors` row/cell selection highlight only — the one place a genuine accent color exists in this phase's scope |
| `GroupBox`→`Panel` border (replaces bevel, THEME-05) | `Panel.BorderStyle = FixedSingle`; border renders as `SystemColors.ControlDark` (WinForms default `FixedSingle` border color, theme-follows automatically) | Same (`FixedSingle`); if visual testing on the rig shows `FixedSingle`'s default border doesn't suffiently contrast against a dark background, override with an explicit `Color.FromArgb(70,70,70)` border via `Panel.Paint` — flagged as a rig-verification fallback, not the default plan | `grpMonitor`, `grpAudioDevices`, `grpAppPath` → replaced `Panel`s. Caption `Label` uses the same base-layer `SetColorMode` text color as every other `Label` — no separate override needed. |
| `txtHotkey` — Idle/Configured state | `BackColor = SystemColors.Window`; `ForeColor = SystemColors.WindowText` | `BackColor = Color.FromArgb(45,45,48)`; `ForeColor = Color.FromArgb(240,240,240)` (match `DataGridView`'s dark cell palette for visual consistency across the Settings screen) | `SettingsForm.RenderHotkeyIdleDisplay()`, Configured branch — replaces hardcoded `SystemColors.Window`/`WindowText` (12-RESEARCH.md Pitfall 8 finding) |
| `txtHotkey` — Idle/Unconfigured state | `BackColor = SystemColors.Window`; `ForeColor = SystemColors.GrayText` | `BackColor = Color.FromArgb(45,45,48)`; `ForeColor = Color.FromArgb(160,160,160)` (dark-mode-appropriate muted/gray text — matches the "disabled/placeholder" contrast ratio `SystemColors.GrayText` provides in light mode) | Same method, Unconfigured branch |
| `txtHotkey` — Recording state (the one genuine accent moment outside the grid) | `BackColor = SystemColors.Info`; `ForeColor = SystemColors.WindowText` | `BackColor = Color.FromArgb(0,90,158)` (same accent blue as grid selection, for a consistent "active/in-progress" signal across the app); `ForeColor = Color.White` | `SettingsForm.TxtHotkey_MouseDown` — replaces hardcoded `SystemColors.Info`/`WindowText` |
| Destructive | Not applicable — this phase introduces no new destructive actions and does not touch existing ones (no destructive-action UI exists in MainForm/SettingsForm's scope for this phase; `btnDiscardChanges`/`btnCancel` are non-destructive "discard unsaved form state" actions, not data-destroying, and keep their existing native styling/copy) | Not applicable | N/A |

Accent reserved for: **only** (1) `dgvMonitors` row/cell selection highlight, and (2) `txtHotkey`'s Recording state background. Do not introduce the accent blue (`FromArgb(0,90,158)`) anywhere else on either form — every other control's coloring is delegated to `SetColorMode`'s own base-layer resolution, not a hand-picked accent.

**Dark-mode literal palette summary** (for quick reference, all sourced from 12-RESEARCH.md Pattern 5's verified code example):
- Surface: `#202020` (32,32,32)
- Cell/control surface: `#2D2D30` (45,45,48)
- Primary text: `#F0F0F0` (240,240,240)
- Muted/secondary text: `#A0A0A0` (160,160,160)
- Grid lines / borders: `#464646` (70,70,70)
- Accent (selection / recording): `#005A9E` (0,90,158)
- Accent text-on-accent: `#FFFFFF` (White)

**Windows-11-only chrome (THEME-06, not a "color" per se but adjacent):** `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND (2)`, `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_MAINWINDOW (2, standard Mica — NOT Mica Alt/Acrylic per D-02)`. Applied to both `MainForm` and `SettingsForm` handles. Best-effort — a non-zero `DwmSetWindowAttribute` HRESULT on Windows 10/unsupported builds is silently ignored, never surfaced as an error state to the user (no error copy needed for this failure mode — see Copywriting).

## Copywriting Contract

This phase adds **no new user-facing strings**. It is a pure recoloring/restyling pass — every existing label, button caption, warning message, tooltip, and MessageBox string (per D-01, left native/untouched) keeps its exact current text. The template's standard categories are addressed below only to confirm none apply:

| Element | Copy |
|---------|------|
| Primary CTA | Not applicable — no new call-to-action is introduced. Existing CTAs (`btnToggle` "Toggle", `btnSettings` "Settings", `btnSaveSettings` "Save", etc.) keep their current text; only `FlatStyle` changes (THEME-05), not copy. |
| Empty state heading | Not applicable — this phase has no empty-state UI in scope. |
| Empty state body | Not applicable |
| Error state | Not applicable — THEME-06's Windows-10/unsupported-API fallback is a **silent** best-effort no-op per D-07, not a user-visible error. No error copy is introduced for a failed/skipped DWM call; the app must not show a message, toast, or dialog about it. |
| Destructive confirmation | Not applicable — no new destructive actions in this phase's scope (see Color section). |

**One explicit copywriting non-change to protect during implementation:** `MonitorConfirmDialog`'s `chkDontAskAgain` ("Don't ask again"), `btnContinue` ("Continue"), `btnCancel` ("Cancel"), and `lblMessage`'s dynamic warning text must render unchanged in both themes if this dialog is included in scope (see Registry Safety / Discretion note below) — only `FlatStyle`/base-layer color changes apply, never text edits.

## Scope Notes for Planner/Executor (resolves open discretion items from 12-CONTEXT.md / 12-RESEARCH.md)

- **`MonitorConfirmDialog` is IN SCOPE** for this UI contract (resolves 12-RESEARCH.md Open Question 2). It is small (4 controls, all in the "themes automatically via `SetColorMode`" bucket per Pattern 5's table — `Label`, `CheckBox`, 2 `Button`s), has zero `GroupBox`/`DataGridView`/hardcoded-`SystemColors` complications, and leaving it unthemed would produce a jarring light-mode popup inside an otherwise dark-themed toggle flow it shows on every first toggle. Its two buttons get the same `FlatStyle.System` treatment as every other button in this phase (THEME-05 consistency). No new copy, no new colors beyond base-layer `SetColorMode` — this is the cheapest possible scope addition.
- **`FlatStyle.System`** (not `.Flat`) is the confirmed value for all 9 buttons across the three forms (`btnToggle`, `btnSettings`, `btnBrowse`, `btnSaveSettings`, `btnDiscardChanges`, `btnContinue`, `btnCancel`, plus MonitorConfirmDialog's `btnContinue`/`btnCancel` — note `MonitorConfirmDialog` and `SettingsForm` each independently declare their own `btnContinue`/`btnCancel` fields), per 12-RESEARCH.md Pitfall 6 (`dotnet/winforms#13897` routing).
- **`ErrorProvider` glyphs** (6 instances) are explicitly left untouched — their built-in red warning icon reads legibly on both light and dark backgrounds with zero code change (per Pattern 5's table).
- **`MessageBox` (4 call sites) and `OpenFileDialog`** are explicitly left untouched — native/unthemed by design (D-01), not a gap.
- **`ToolStrip`/`ContextMenuStrip`** (tray menu) live-flip stale-color bug is an accepted, documented limitation (D-03) — no visual contract violation, no code fix expected; note in code comments only.
