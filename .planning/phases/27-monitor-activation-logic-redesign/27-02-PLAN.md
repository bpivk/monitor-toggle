<objective>
Delete the mechanisms that Plan 01 made unreachable, so this phase is provably a subtraction and
not an addition. Per `.planning/debug/monitor-position-regre.md` §22.2 this removes 6 of the 15
catalogued mechanisms outright (plus the reflection-patch technique that served them), narrows 1
to single-purpose, and leaves 8 untouched.

It also resolves one genuine gap in the redesign proposal that direct source inspection surfaced
during planning: §22.2 keeps mechanism 1 (`_lastKnownActiveModeByDevicePath` / `CacheLiveModes`)
on the stated ground that the retained correction loop "needs a live position cache to restore any
accidentally-dropped survivor" — but that cache's ONLY reader in the entire file is inside
`TryBuildScopedActivationPlan`, which this plan deletes. Post-redesign the correction loop's
nested call goes through Extend, which reads nothing from that cache. The cache therefore becomes
write-only unless something is done about it, and that bears directly on Symptom 1 of the debug
session (monitor position resetting on re-enable). Task 1 puts that in front of the operator with
Plan 01's rig evidence in hand instead of resolving it by assumption.

Purpose: make the simplification real and verifiable, and close the one disposition in the
proposal whose stated rationale does not survive contact with the source.

Output: a materially smaller `WindowsMonitorController.cs` and test file, plus a recorded decision
on the live-mode cache.
</objective>

  <decision>
    What happens to `_lastKnownActiveModeByDevicePath` and `CacheLiveModes` once

  </decision>
  <context>
    Verified by direct source read during planning, against the pre-Plan-01 file: the field is
    WRITTEN in exactly one place (`CacheLiveModes`, line 945), which is CALLED from exactly two
    places (`ActivateMonitorsCore` line 678, and `DeactivateMonitors` line 1846). It is READ in
    exactly one place: line 1148, inside `TryBuildScopedActivationPlan`. `DeactivateMonitors` does
    NOT read it — its survivor repositioning uses positions taken live from the current
    `GetActivePaths()` survivors, not from the cache.

    So debug §22.2's row for mechanism 1 ("KEPT, unchanged", because the correction loop "needs a
    live position cache to restore ANY accidentally-dropped survivor") does not hold as written:
    after this plan, the correction loop restores dropped survivors by calling
    `ActivateMonitorsCore` again, which now calls Extend, which consults nothing in that cache.
    Whatever position a re-activated monitor lands at comes from Windows' own persisted CCD
    database, not from this cache.

    That is exactly the mechanism behind Symptom 1 of this debug session ("monitor position wrong
    immediately after disable/re-enable"). Plan 01 Task 3 Check B asked the operator to answer,
    on real hardware, whether position is preserved under Extend-only. Read that answer from
    `27-01-SUMMARY.md` before choosing.
  </context>
  <options>
    <option id="option-a">
      <name>Delete the cache: remove the field, the CacheLiveModes method, and both of its call sites</name>
      <pros>No write-only state left behind; the file has no dead data structure a future reader could mistake for live. Consistent with this plan's job of making the subtraction real. Correct choice if Plan 01 Check B reported position IS preserved, because then nothing needs the cache.</pros>
      <cons>Contradicts the literal §22.2 table (which says KEPT). If position resets later turn out to be a real regression, the capture code has to be written again from git history.</cons>
    </option>
    <option id="option-b">
      <name>Keep the field and CacheLiveModes exactly as they are, write-only, with a comment recording that Phase 27 removed its only consumer and why it was retained anyway</name>
      <pros>Matches the §22.2 table literally; keeps the capture points warm at near-zero cost, so a future position-restore feature only has to add a reader. Honest if the comment states plainly that nothing currently reads it.</pros>
      <cons>Leaves genuinely dead state in a file this phase exists to simplify; a future reader may assume the data is consumed and reason incorrectly about the activation path.</cons>
    </option>
    <option id="option-c">
      <name>Keep the cache and add a post-Extend repositioning pass that consumes it</name>
      <pros>The only option that actually preserves monitor position under Extend-only. Would reuse the repositioning-aware ApplyPathInfos shape DeactivateMonitors already uses and has rig-proven, rather than inventing a new mechanism.</pros>
      <cons>Adds a NEW mechanism during a subtraction phase, and puts ApplyPathInfos back on the activation path (for repositioning, not activation) days after removing it. It needs its own rig verification pass and its own failure semantics. If Plan 01 Check B reported position DOES reset, this is the right fix — but it should be scoped as its own follow-up phase against fresh rig evidence, not absorbed into this cleanup plan.</cons>
    </option>
  </options>
