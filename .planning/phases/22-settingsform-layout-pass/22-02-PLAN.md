<hard_constraints>
1. **Only `src/RigToggle.App/SettingsForm.Designer.cs` may change.** `SettingsForm.cs` and `ThemeApplier.cs` stay byte-identical to commit `0c1234f`. 22-PATTERNS.md verified directly that the D-01/D-02 reparenting needs zero code-behind changes: `grep -n "\.Parent" src/RigToggle.App/SettingsForm.cs` returns nothing, and every `ThemeApplier` call targets a named instance field.
2. **`MinimizeBox` stays `false`.** This is a functional-correctness requirement, not a style default. `SettingsForm` is shown via `ShowDialog()` with `ShowInTaskbar = false`; minimizing that combination can strand the dialog with no taskbar entry to restore it from, or close it outright (22-RESEARCH.md Pitfall 3, 22-UI-SPEC.md Sizing & resize rules). Do not "match the Sizable convention" by enabling it.
3. **Do not add `MinimumSize` or `MaximumSize` to the Form.** Those are the only two properties `AutoSize` still respects, so adding one silently overrides D-05's content-driven intent (22-RESEARCH.md Pitfall 2). Control-level `MinimumSize` on individual children is required and expected — the prohibition is Form-level only.
4. **No `TabControl`, no wizard, no second page.** This stays a single-page form (FEATURES.md anti-pattern, restated in 22-CONTEXT.md D-01).
5. **No sub-grouping inside the shared section.** App path, hotkey, debug-logging checkbox and the three tray/autostart checkboxes are one flat stack — no extra `GroupBox`-style wrapper around any subset (D-02). The two small nested containers this plan does add (`tlpAppPath` inside the existing `pnlAppPath`, and `tlpHotkey` for the caption+field row) are single-row/field layout helpers, not visual groupings, and get no `BorderStyle`.
6. **Phase 22 does NOT build Phase 23's radio group.** No new `AppSettings` field, no new control with visible text, no new logic. D-04 is layout room only.
7. **Never use `SizeType.Absolute`.** `Percent` and `AutoSize` only.
8. **No hand-rolled layout code** — no `Resize`/`Layout` handler, no size arithmetic. `Form.AutoSize` + `AutoSizeMode.GrowAndShrink` is the mechanism (22-RESEARCH.md "Don't Hand-Roll").
</hard_constraints>

**FlowLayoutPanel behaviour that shapes this plan (22-RESEARCH.md Pattern 2, from the official anchor/dock walkthrough):** `FlowLayoutPanel` does not honour `Dock` on its children. It computes an implied column width from its **widest child** and stretches `Anchor`-set children to that width. Consequences to accept, not fight:
- Use `Anchor`, never `Dock`, on `flpShared`'s direct children.
- The shared section's content will be as wide as its widest child (`chkEnableDebugLogging`'s one-line text, roughly 430px at 100% scale) — not the full form width, since the two mode columns above will make the form wider than that. Content will read as left-aligned inside a wider bordered box. This is expected. If the resulting dead space to the right reads as broken on the rig, Plan 03's rig check 14 records it and the authorised fallback is swapping `flpShared` for a single-column `TableLayoutPanel` (22-RESEARCH.md Assumptions Log A2 explicitly calls that an equally valid implementation with no loss of capability) as a gap-closure fix — **do not preemptively make that swap in this plan.**

**Label sizing rule (unchanged from Plan 01):** `Label` defaults to `AutoSize = false`. Wrapping/fixed-height labels keep `AutoSize = false`, drop `Location`/`Size`, and gain `MinimumSize = new System.Drawing.Size(0, <today's height>)` so an `AutoSize` row cannot collapse them to one text line. `lblHotkeyWarning`'s height today is 36; `lblAutostartWarning`'s and `lblAppWarning`'s are 20.

**Checkbox change:** `chkEnableDebugLogging`, `chkCloseMinimizesToTray`, `chkMinimizeToTray`, and `chkStartWithWindows` are today `AutoSize = false` with an explicit 396-wide `Size` (which is why the debug-logging caption wraps to two lines in the current build). In a top-down flow stack they become `AutoSize = true`, which is what guarantees their text can never truncate at any display scale. Their `Text` values are unchanged, verbatim.

**Button truncation:** `btnBrowse`/`btnClearAppPath` (70x25) and `btnSaveSettings`/`btnDiscardChanges` (110x32) are today fixed-size. Each becomes `AutoSize = true` + `AutoSizeMode = GrowAndShrink` + `MinimumSize` equal to today's size — so it can grow if 125%/150% text needs more room but never shrinks below today's footprint. This is what structurally removes the truncation risk Plan 03's rig check 4 looks for. Their `Text`, `DialogResult`, `FlatStyle.Flat`, and `Click` wiring are untouched (the `FlatStyle.Flat` value is load-bearing — see the existing `btnBrowse` comment on dotnet/winforms#13897).

**Drag-drop wiring (T-12-07, load-bearing).** Today `pnlAppPath` and `txtAppPath` each carry `AllowDrop = true` plus `AppPath_DragEnter`/`AppPath_DragDrop`. Once `tlpAppPath` is docked to fill `pnlAppPath`'s client area, the panel's own surface is no longer hit-testable for drops — the new table intercepts them. `tlpAppPath` must therefore carry the same `AllowDrop = true` and the same two handler subscriptions, or the drop target silently shrinks to just the text box. Nothing is removed from `pnlAppPath` or `txtAppPath`.
