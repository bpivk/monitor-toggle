<root_cause_analysis>
This section is the reasoning the fix rests on. Read it before editing — it explains why the fix is shaped the way it is, and, just as importantly, which parts of it are certain and which are hedged.

## What the rig actually reported

- **Check 1 FAIL:** "Both modes only have explanations and monitor and audio are both missing." Caption and explain text render; **everything from the grid row down is gone** in *both* columns.
- **Check 3 FAIL:** "resize preview flickers when dragged but then disappears, nothing resizes."

## Bug A — high confidence, mechanism identified

`SettingsForm` sets `this.AutoSize = true` with `AutoSizeMode.GrowAndShrink` (Designer lines 905-906). When a `Form` has `AutoSize` on, every layout pass runs the auto-size pass and writes the form's bounds back to its computed preferred size. A user edge-drag generates `WM_SIZING`/`WM_SIZE`, which triggers a layout pass, which immediately overwrites the dragged bounds. "Preview flickers, then nothing resizes" is the exact signature of that loop.

The Designer file currently carries a comment (lines 899-904) asserting the opposite — that `AutoSize` "does not fight a user-driven edge drag." `22-RESEARCH.md` Pattern 3's caveat says the same thing. That assertion came from reading the `Form.AutoSizeMode` docs, not from running it, and the rig has now falsified it. `22-03-PLAN.md`'s own acceptance criteria pre-authorised the remedy: *"disabling `Form.AutoSize` after first show, keeping the container `AutoSize` intact."* This plan applies that remedy, with one refinement — `AutoSize` is never turned on at all, rather than turned on and then off, because the "first show" handoff is what produces the content-driven size and it is cleaner to compute that size explicitly than to read it back out of a property that is about to be disabled.

## Bug B — mechanism uncertain, fix deliberately made mechanism-independent

The hypothesis carried forward from `22-03-SUMMARY.md` was: a `SizeType.Percent, 100F` row nested inside an `AutoSize=true` `TableLayoutPanel` collapses to zero height.

**That hypothesis is contradicted by the official documentation.** Microsoft's `autosize-behavior-in-the-tablelayoutpanel-control` guide (already cited in `22-RESEARCH.md`'s sources) states that when the `TableLayoutPanel` itself is `AutoSize`, `Percent` rows "acquire an automatic sizing aspect," and that the control "expands the column or row to create adequate free space, so that no column or row with `SizeType.Percent` styling clips its contents." A collapsing-to-zero percent row is precisely what that sentence rules out. `22-VERIFICATION.md` independently flagged the same hypothesis as insufficient for a different reason: `cboAudioNormal`/`cboAudioRig` sit in row 4, an **`AutoSize`** row, not the percent row — so percent-row collapse alone cannot explain their absence either.

**A better-fitting explanation exists.** The observed symptom is not "one row vanished" but "the column's content is clipped below roughly the first two rows." The two mode wrappers, `pnlMonitor` (Designer lines 158-164) and `pnlMonitorNormal` (lines 343-349), are the **only** container `Panel`s in this file that never set `AutoSize` — `pnlSharedSection` sets it (line 768), `pnlAppPath` sets it (line 508), every `TableLayoutPanel` sets it. Each mode wrapper's sole child is `Dock=Fill`, and a `Dock=Fill` child contributes nothing to a `DefaultLayout` container's own extent ("fill whatever is left" is not a measurement). A plain `Panel` that never measures its content reports its default `Panel` size — **200 × 100** — up to the `TableLayoutPanel` cell it lives in. Give the mode row ~100px, subtract the wrapper's 12px padding on each side, and roughly 76px reach `tlpNormalColumn` — enough for the caption row (~23px with margin) and the explain row (50px floor + 8px margin), and nothing at all for the grid, warning, audio, or audio-warning rows below. That is the reported symptom, in both columns, including the `AutoSize`-row audio picker that the percent hypothesis could not account for.

**This explanation is well-supported but still not proven** — it cannot be, without a Windows layout engine to run. So the fix does two things at once:

1. **Repair the suspected node** (add `AutoSize` to both mode wrappers, matching what every other container in the file already does). Cheap, and correct regardless.
2. **Add a floor that makes the failure impossible whatever the mechanism turns out to be** — an explicit `MinimumSize` height on `tlpModeColumns`. `Control.GetPreferredSize` clamps its result to `MinimumSize` on the way up, and `Control.SetBoundsCore` clamps to it on the way down, so the mode-columns row is guaranteed a real height in **both** directions of the layout pass. This holds if the break is at the wrapper `Panel`, if it is at the percent row, and if it is somewhere neither of us identified.

Note that `MinimumSize` is DPI-safe here: `Control.ScaleControl` scales `MinimumSize` and `MaximumSize` along with `Size`, so a floor expressed at 100% scale is scaled up automatically under `AutoScaleMode.Font` at 125% and 150%. This also keeps `22-RESEARCH.md` Pitfall 2 satisfied — that pitfall warns against *undocumented* `MinimumSize`/`MaximumSize` and explicitly permits a documented one added "for a specific, deliberate reason."

The `Percent, 100F` rows stay. They are what makes rig Check 3(d) pass once the window can actually grow, and the documentation says they are not the problem. If Plan 05's rig pass shows the grids still absent *with* the floor in place, that is genuinely new information and the follow-up is to eliminate the intermediate wrapper `Panel`s entirely (hosting `tlpNormalColumn`/`tlpRigColumn` directly in the `tlpModeColumns` cells with `BorderStyle.FixedSingle` and `Padding=12` carried onto the tables, which are themselves `Panel` subclasses and render an identical THEME-05 flat border). That fallback is recorded here so the next planner does not have to rediscover it; **do not implement it in this plan.**
