# Phase 22 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a native Windows Forms (.NET 10, `net10.0-windows`) desktop application, not a web app. The shadcn/component-registry model from this template is not applicable — see Design System and Registry Safety sections below for the WinForms-equivalent contract. This document follows the same platform-adapted shape established by `12-UI-SPEC.md`/`13-UI-SPEC.md`/`19-UI-SPEC.md`/`20-UI-SPEC.md`/`21-UI-SPEC.md`.
>
> **Phase framing:** This phase is a pure *layout-container* migration of `SettingsForm.Designer.cs` (D-03) — every control's `Text`, data-binding, and theming pipeline is unchanged; only `Location`/`Size`/container-type become `TableLayoutPanel`/`FlowLayoutPanel`-driven `Dock`/`Anchor`/`Percent`/`AutoSize` composition, and grouping changes from category-based (all grids, then all audio, then app path...) to mode-based (D-01: Normal column, Rig column, shared global section). Zero new colors, zero new typography, zero new copy beyond what's already in the form (SETTINGS-01/SETTINGS-02 only). This is this codebase's **first** use of `TableLayoutPanel`/`FlowLayoutPanel` anywhere — no prior-art fallback exists in `MainForm`/`MonitorPanelForm`.

## Spacing Scale

Declared values (must be multiples of 4), applied to `SettingsForm`'s new `TableLayoutPanel`/`FlowLayoutPanel` structure. This phase deliberately **replaces** hand-picked pixel offsets with these tokens (D-03's stated purpose) rather than preserving the old Designer.cs's literal pixel positions — unlike Phase 12's panel-wrapper migration, which kept "pixel parity" because it changed only the container's border style, not its layout mechanism.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between a caption `Label` and the control it labels on the same row inside the shared section (e.g. `lblHotkeyCaption` → `txtHotkey`); gap between a mode column's caption and its explain text |
| sm | 8px | Vertical gap between stacked items inside `flpShared` (app-path row → hotkey row → hotkey warning → debug-logging checkbox → tray/autostart checkboxes → autostart warning → Phase 23 reserved row) — this is `FlowLayoutPanel`'s per-child `Margin`, not a manual offset |
| md | 16px | `tlpRoot`'s outer `Padding` from the form's client edges; gap between Row 0 (mode columns) and Row 1 (shared section) in `tlpRoot`; gap between Row 1 (shared section) and Row 2 (Save/Discard button row) |
| lg | 24px | Not used this phase — reserved, matching `19-UI-SPEC.md`'s convention of declaring the full token set even when a given phase doesn't need every rung |
| xl | 32px | Not used this phase |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions:
- **12px** — content `Padding` inside each `Panel` wrapper (`pnlMonitorNormal`, `pnlMonitor`, `pnlSharedSection`) between the panel's `FixedSingle` border and its first child. Matches this codebase's existing GroupBox-native-caption-inset convention (THEME-05, `~9px` rounded to a clean 12px token) and `22-RESEARCH.md`'s own Code Example (`pnlMonitor.Padding = new Padding(12, 60, 12, 12)`). Kept as its own named exception rather than forced onto `sm`(8)/`md`(16) for the same reason `19-UI-SPEC.md` named its 12px tile-gap exception explicitly rather than silently drifting off the 4px grid.
- **12px** — `tlpModeColumns`'s inter-column gap (`Margin` between `pnlMonitorNormal` and `pnlMonitor`), reproducing today's existing 12px gap between the two panels (`420 - (12 + 396) = 12`) so the side-by-side balance the user already approved of stays visually intact even though the underlying container type changes.
- **6px** — `dgvMonitors`/`dgvMonitorsNormal`'s internal top-inset from their mode column's caption/explain block when `Dock=Fill` is adopted (see Layout Structure Contract, Open Question 1 resolution below) — not a new token, an artifact of the existing caption+explain block's measured height; do not hand-tune this value, let `AutoSize`/`Dock=Top` on the caption/explain stack derive it.

## Layout Structure Contract

This is the section that actually changes this phase. Supplements the Spacing Scale above with the exact container hierarchy and composition rules — prescriptive, not exploratory, per this document's downstream-consumer contract.

### Container hierarchy (D-01, D-02, D-03)

Every item added to `flpShared`/`tlpModeColumns`/`tlpRoot` uses `Anchor = Left | Right` (never `Dock` on a `FlowLayoutPanel` child — `FlowLayoutPanel` does not support meaningful `Dock` on children per `22-RESEARCH.md` Pattern 2, confirmed against official docs) so each item stretches to the flow panel's implied-column width instead of keeping a fixed pixel width.

### Grouping rules (D-01, D-02 — locked, not discretionary)

- **Mode-based, not category-based.** The Normal column holds Normal's monitor grid AND Normal's audio picker; the Rig column holds Rig's monitor grid AND Rig's audio picker. `pnlAudioDevices` (today's single panel holding both `cboAudioNormal` and `cboAudioRig` together) is deleted as a container — its two children move into their respective mode columns, each keeping its own caption/warning label.
- **One flat shared section, not sub-grouped.** App path, hotkey capture, debug-logging checkbox, and the three tray/autostart checkboxes all live directly in `flpShared` — no additional nested `Panel`/`GroupBox`-style wrapper around any subset of them.
- **Do not re-tab.** This stays a single-page form (`FEATURES.md`'s explicit anti-pattern) — no `TabControl`, no wizard flow, regardless of how tempting a "Normal tab / Rig tab" split might look.

### Sizing & resize rules (D-05, D-06 — locked, not discretionary)

- `Form.AutoSize = true`, `AutoSizeMode = GrowAndShrink`. Remove `this.ClientSize = new Size(828, 768)` entirely — the form sizes to `tlpRoot`'s computed content size. No fixed/target width or height to hit or verify against (D-05).
- `FormBorderStyle = Sizable` (changed from `FixedDialog`). `MaximizeBox = false` (unchanged). **`MinimizeBox` stays `false`** (unchanged) — this is a functional-correctness finding, not a style call: `SettingsForm` is shown via `ShowDialog()` with `ShowInTaskbar = false` (both unchanged), and enabling `MinimizeBox` on that exact combination is a documented WinForms failure mode (minimizing can strand the window with no taskbar entry to restore it from, or close the dialog outright) — see `22-RESEARCH.md` Pitfall 3.
- Do not add `MinimumSize`/`MaximumSize` to `SettingsForm` unless there's a specific, deliberate, documented reason — `AutoSize`'s docs state these two properties (not `Size`) are what still constrain it, and an undocumented addition would silently override D-05's "content-driven, no fixed target" intent.

### Open Question 1 resolution (dgvMonitors/dgvMonitorsNormal Dock behavior)

**Locked for this phase: switch both grids to `Dock = DockStyle.Fill`** inside their panel (replacing today's fixed `Location`/`Size` inside an already-Panel-wrapped grid), consistent with D-03's stated purpose of removing hardcoded pixel math everywhere, not just at the outer-container level. This is a genuinely new behavior this phase introduces (today's grids use fixed pixel bounds even while sitting inside a `Panel`) — flag explicitly as the single most heavily rig-verified layout element (see DPI/Rig-Verification checklist reference below), since it's the most novel new-behavior surface in this phase. The grids' own `AutoSizeColumnsMode.Fill` column configuration (`colMonitorName`/`colMonitorNameNormal`) is unchanged — do not touch column-level `AutoSizeMode`/`FillWeight`.

### Tab order (Pitfall 5)

Add controls to each new container in the same left-to-right, top-to-bottom order they visually appear (Normal column top-to-bottom, then Rig column top-to-bottom, then shared section top-to-bottom, then Save/Discard) — mirroring today's flat `InitializeComponent()` add-order intent, since nested-container `.Controls.Add()` order now determines the composed Tab sequence instead of one flat sequence. If the implicit order proves wrong on a manual Tab-through check, set `TabIndex` explicitly on the top-level containers rather than leaving it to chance.

### DPI / rig verification (Pitfall 9, non-negotiable per D-03's accepted tradeoff)

This build environment cannot exercise Windows display scaling at all. Every claim in this Layout Structure Contract about `Dock=Fill`/`Percent`/`AutoSize` behavior at 125%/150% Windows scale is unverified until confirmed on real hardware. Full 12-step checklist is defined in `22-RESEARCH.md`'s "DPI / Rig-Verification Checklist" section (100% baseline, 125%/150% grid-column checks, overlap/crowding re-check, button-text-truncation check, form-level AutoSize sanity, manual-resize interaction at each scale, MinimizeBox-absence confirmation, tab-order walkthrough, live theme-flip-while-open confirmation) — the plan must schedule this as an explicit rig checkpoint before this phase is considered done, per this project's established fail-loud/verify-on-real-hardware discipline (Phase 12/13/21 precedent). Do not mark SETTINGS-01/SETTINGS-02 satisfied on an inferred "should work" basis for any DPI-scale claim.

## Component Behavior Contract

Beyond copy/color/spacing/layout, these interaction details are load-bearing for the executor, derived directly from `22-CONTEXT.md`'s locked decisions and `22-RESEARCH.md`'s patterns/pitfalls:

- **Data-binding, validation, and Save/Load logic are entirely untouched.** `SettingsForm.cs`'s constructor wiring, `SettingsForm_Load`, `BtnSaveSettings_Click`, audio-picker population, hotkey-capture state machine — none of it changes. Only `Location`/`Size`/`Dock`/`Anchor`/container-type change (D-03's own framing).
- **`.Parent`-relative code audit (Pitfall 4):** before finalizing the D-01 `pnlAudioDevices` split, grep `SettingsForm.cs` for `.Parent`, `.Controls[`, and any reference to `pnlAudioDevices` by name — confirmed by this research pass that no such reference exists in the code-behind today (only in `Designer.cs`), but re-verify as a cheap final check since `cboAudioNormal`/`cboAudioRig` will have different parents after the split.
- **`AllowDrop`/drag-drop wiring on `pnlAppPath` and `txtAppPath` must survive the reparent unchanged** — both the panel-level and textbox-level `DragEnter`/`DragDrop` handlers (`AppPath_DragEnter`/`AppPath_DragDrop`) are preserved verbatim, just moved into the new `flpShared` container.
- **Theming pipeline reach is container-agnostic (confirmed, not assumed)** — `ThemeApplier`/`SettingsForm.cs`'s theming call sites target specific instance fields by name, never a `Controls`-tree walk. No new theming code is needed for this migration; verify by flipping Windows Light↔Dark while the dialog is open (rig checklist item 11) as a practical confirmation that this research finding holds in the actual built app, not just in source analysis.
- **`AcceptButton`/`CancelButton` wiring is unchanged** — `btnSaveSettings`'s `DialogResult.OK` and `btnDiscardChanges`'s `DialogResult.Cancel` stay as-is; this is exactly the `ShowDialog()` modal semantics that make the `MinimizeBox=false` finding (Pitfall 3) load-bearing.
