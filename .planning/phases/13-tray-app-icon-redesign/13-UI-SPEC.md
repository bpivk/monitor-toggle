# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a Windows Forms (.NET 10) desktop application, not a web/React project — same as Phase 12. There is no `components.json`/Tailwind/shadcn; the shadcn initialization gate does not apply. **This phase's "UI" is not a screen or form — it is icon artwork**: two 16px-native tray icons (`normal.ico`, `rig.ico`, monochrome silhouette + outline, `NotifyIcon`-hosted) and one color `.exe`/taskbar icon (`app.ico`, `<ApplicationIcon>`-hosted), all procedurally drawn via GDI+/`System.Drawing` per 13-CONTEXT.md's locked decisions (D-01 through D-07). This contract therefore replaces the template's layout-oriented Spacing/Typography sections with a **pixel-geometry contract** — exact silhouette coordinates, stroke widths, and colors an executor can implement without any further design judgment call, the same way a web UI-SPEC pins down hex values and px sizes instead of leaving them to "looks about right."

## Design System

**Visual focal point:** Not applicable in the usual "primary UI element" sense — there is no screen. The three artifacts are peers, each serving a distinct role: `normal.ico`/`rig.ico` are the moment-to-moment mode indicator (glanced at dozens of times per session in the system tray), `app.ico` is the at-rest taskbar/Explorer identity. Silhouette-shape contrast between `normal.ico` and `rig.ico` (ICON-01) is the single most important visual property this phase delivers — everything else (color, outline, sizing) exists to keep that contrast legible at 16px.

## Icon Canvas & Geometry Grid

Replaces the template's px-based Spacing Scale — this phase's "spacing scale" is a **resolution-independent geometry grid**, since the same shape must be redrawn crisply at four (tray) or six (exe) discrete pixel sizes, not laid out once.

**Governing rules (apply to every icon in this contract):**

1. **Design in fractions, not fixed pixels.** Every coordinate below is expressed as a fraction of canvas width/height (`0.0`–`1.0`, canvas is always square: `W == H`). At implementation time, multiply by the actual target size (16/20/24/32/48/256) to get device pixels for that frame.
2. **Redraw at each target size — do not scale a single bitmap.** Render fresh via `Graphics` sized to each target resolution (`SmoothingMode.AntiAlias`, `PixelOffsetMode.HighQuality`) so every frame is pixel-sharp (this is what ICON-03 requires — bitmap-scaling a single 256px master down to 16px produces mushy edges at the size that matters most, the tray).
3. **Minimum feature thickness ≥ 2px at the 16px canvas**, measured before anti-aliasing. Any bar, neck, ring, or spoke whose computed dimension rounds below 2px at W=16 must have its governing fraction increased — do not ship a feature that disappears at native tray size. (Corner radii are exempt from this rule; a sub-1px radius is acceptable and will render as a near-square corner at 16px, which is fine.)
4. **Background is fully transparent** (alpha 0) on all three icons, in every region not covered by a filled shape — including negative-space cutouts (the wheel's ring hole, the gaps between spokes).

## Color

This is the core contract of the phase.

| Role | Value | Usage |
|------|-------|-------|
| Tray silhouette fill (both `normal.ico` and `rig.ico`) | `#FFFFFF` (255,255,255), fully opaque | The entire filled silhouette shape — monitor on `normal.ico`, wheel on `rig.ico`. No per-mode color per D-04; shape is the sole differentiator. |
| Tray silhouette outline (both tray icons) | `#000000` (0,0,0), fully opaque | Traced around **every** boundary edge of the filled silhouette — outer contour *and* internal negative-space edges (e.g. the wheel's inner ring hole, the gaps between spokes). This is the ICON-02 "self-contained contrast" mechanism (D-05): white fill reads against a dark taskbar, black outline reads against a light taskbar — one asset, both themes, no theme-detection code. |

| Exe/taskbar icon body (bezel/stand/base) | `#2D2D30` (45,45,48) — dark gray | `app.ico`'s monitor bezel, neck, and base bar (D-07's "dark-gray body"). Deliberately reuses Phase 12's established dark control-surface color (12-UI-SPEC.md's `#2D2D30` dark cell/control surface) for cross-phase visual cohesion — this app's dark-mode "neutral surface" tone now also anchors its icon identity. |
| Exe/taskbar icon accent (screen "glass") | `#005A9E` (0,90,158) | A single inset rectangle inside the bezel representing the display area — the icon's one color accent (D-07's "subtle accent"), reusing Phase 12's established accent blue (`12-UI-SPEC.md`'s selection/recording-state accent) rather than inventing a new brand color. This mirrors the context's VS Code reference (colorful taskbar icon, plain tray glyphs) while keeping the app's palette internally consistent. |
| Exe/taskbar icon background | transparent (alpha 0) | Everywhere not covered by the bezel/stand/base/screen shapes |
| Destructive | Not applicable — icons have no destructive-action affordance | N/A |

Accent (`#005A9E`) reserved for: **only** the screen-glass inset rectangle on `app.ico`. Never used on `normal.ico` or `rig.ico` — both tray icons stay strictly monochrome (white fill + black outline only) per D-04; introducing color there would defeat ICON-01's "shape alone, not color" guarantee.

No outline stroke on `app.ico` — flat color fill only, no forced black border. This matches native Windows app-icon convention (File Explorer, Settings icons have no outline) and is visually appropriate at the larger sizes/richer Explorer/Alt-Tab backgrounds this icon renders against, unlike the tray's variable, low-pixel-budget context that outline exists to solve.

## Icon Geometry Contract

### `normal.ico` — Desktop monitor silhouette (tray, monochrome)

All coordinates as fractions of canvas `W`×`H` (square canvas):

| Shape | Position | Size | Corner radius |
|-------|----------|------|----------------|
| Screen (rounded rect) | top-left `(0.125W, 0.125H)` | `0.75W` × `0.5H` | `0.06W` |
| Neck (rect) | top-left `(0.4375W, 0.625H)` | `0.125W` × `0.125H` | none (sharp rect) |
| Base (rounded bar) | top-left `(0.28W, 0.75H)` | `0.44W` × `0.125H` | `0.03W` |

At the 16px canvas this renders as: a 12×8px screen at (2,2), a 2×2px neck at (7,10), and a 7×2px base bar at (4.5,12) — every feature clears the ≥2px minimum. Fill white, outline black per the Color table, outline traced around the full contiguous silhouette (screen ∪ neck ∪ base as one shape, since they touch/overlap).

### `rig.ico` — Steering wheel silhouette (tray, monochrome)

Circular design, center `(0.5W, 0.5H)`. All radii as fractions of `W`:

| Element | Radius | Notes |
|---------|--------|-------|
| Outer rim | `0.40W` | Outer edge of the filled ring |
| Inner cutout | `0.26W` | Transparent hole inside the rim — ring thickness = `0.40W − 0.26W = 0.14W` (≈2.2px at W=16) |
| Hub | `0.12W` | Small filled disc at dead center, connected to the rim via the three spokes below (not an isolated island) |
| Spoke width | `0.14W` | Matches ring thickness exactly — keeps stroke weight visually consistent across the whole icon |

**Spoke layout:** exactly 3 spokes, evenly spaced 120° apart, radiating from the hub edge (`0.12W`) to the inner rim edge (`0.26W`). Angles measured clockwise from 12 o'clock: **180° (straight down / 6 o'clock), 60° (2 o'clock), 300° (10 o'clock)** — a classic tri-spoke "Y" racing-wheel layout (one spoke down, two upper spokes), distinct from a generic circle/clock-face and evocative of a Moza-style sim wheel per the context's specific-ideas note.

The full silhouette is one contiguous shape: rim ∪ hub ∪ 3 spokes. Outline traces every boundary — outer rim contour, inner ring-hole edge, and both edges of each of the 3 gaps between spokes (6 additional short outline segments total). Fill white, outline black per the Color table.

**Shape-contrast check (ICON-01):** a circular wheel-with-spokes silhouette vs. a rectangular monitor-on-a-stand silhouette are unambiguous at any size down to 16px, including in grayscale/colorblind simulation — satisfies "tell mode apart by shape alone."

### `app.ico` — Exe/taskbar icon (color, larger sizes)

Reuses `normal.ico`'s exact monitor geometry (screen/neck/base fractions above, D-06/ICON-04) at the color treatment defined in the Color table:

| Shape | Fill |
|-------|------|
| Screen bezel (outer rounded rect, same geometry as `normal.ico`'s screen) | `#2D2D30` |
| Screen glass (inset rect inside the bezel, inset `0.06W` from the bezel's inner edge on all sides) | `#005A9E` |
| Neck | `#2D2D30` |
| Base bar | `#2D2D30` |

No black outline (see Color section rationale). Background transparent.

## Multi-Resolution `.ico` File Contract (ICON-03)

| File | Embedding mechanism | Sizes (minimum, all required) | Recommended additional sizes |
|------|---------------------|-------------------------------|-------------------------------|
| `normal.ico` | `EmbeddedResource` with `LogicalName="normal.ico"` in `RigToggle.App.csproj` (unchanged pattern), loaded at runtime via `Assembly.GetManifestResourceStream` in `MainForm.LoadTrayIconsIfNeeded()` | 16, 20, 24, 32px | none — these 4 sizes exactly cover Windows' tray DPI-scaling requests (100/125/150/200%); no benefit to bloating the tray `.ico` further |
| `rig.ico` | Same pattern, `LogicalName="rig.ico"` | 16, 20, 24, 32px | none, same reasoning |
| `app.ico` | New `<ApplicationIcon>Resources\app.ico</ApplicationIcon>` MSBuild property in `RigToggle.App.csproj`'s existing `<PropertyGroup>` (does not currently exist — confirmed absent in current csproj) | 16, 20, 24, 32px | **48px and 256px** — Explorer's large-icon/details views, Alt-Tab, and the taskbar's jumbo thumbnail view request these; a bare-minimum 4-size `.exe` icon looks visibly blurry when a user right-clicks → Properties or hovers Alt-Tab. Include both. |

**Frame encoding:** all `.ico` frames as 32bpp ARGB with alpha transparency. Sizes ≥32px MAY use PNG-compressed frames (Vista-style `.ico`, smaller file, universally supported on Windows 10/11); sizes ≤24px should use standard uncompressed BMP-in-ICO frames for broadest compatibility. If the chosen implementation approach (script vs. build step — left to RESEARCH.md/planning per 13-CONTEXT.md's Claude's Discretion) uses a simple hand-rolled `.ico` writer rather than a library, uncompressed 32bpp BMP frames for all sizes is also acceptable — the size difference is negligible for a handful of small icons.

This contract is agnostic to *how* the icons are generated (one-time script producing checked-in files vs. a build-time step) — the geometry, color values, and size/embedding requirements above apply identically either way; that mechanism choice is RESEARCH.md/planning's to make, not this contract's.

## Scope Notes for Planner/Executor

- **File naming:** `normal.ico` and `rig.ico` keep their exact current filenames/`LogicalName`s (only their pixel content changes) — no code changes needed in `MainForm.cs`'s loading path. `app.ico` is a new file under `Resources/`; the exact filename `app.ico` is a suggestion (13-CONTEXT.md leaves naming to discretion) — use it unless a stronger convention emerges during planning.
- **Human verification recommended:** per this project's established pattern (Phase 12's rig-checkpoint plans, e.g. 12-04/12-06), add a plan step to visually inspect both tray icons at actual 16×16 size against both a light-taskbar and dark-taskbar Windows 11 rig session before calling ICON-01/ICON-02 done — the geometry fractions above are a confident starting point, not a guarantee against real-pixel rasterization surprises. If a shape reads ambiguously at 16px, adjust the *proportions* in this contract (larger ring thickness, wider spoke, etc.), not the *motif* (D-01's monitor-vs-wheel choice is locked).
- **`ApplicationIcon` MSBuild property does not currently exist** in `RigToggle.App.csproj` — confirmed by direct read; this phase adds it for the first time (the current pair is tray-only, per 13-CONTEXT.md's integration-points note).
- **Do not introduce a 4th/5th icon asset** for theme-swapping — REQUIREMENTS.md's Out of Scope table and D-04/D-05 already settled this; the single self-contained-contrast tray design above is the complete, final answer for both taskbar themes.
