<objective>
Build the two self-contained prerequisites the manual monitor panel depends on, so Plan 02 can be a single-concern panel plan:

1. **Toggle/panel serialization (resolves 17-RESEARCH.md Open Question 1).** The panel is architecturally required to bypass `ToggleService`/`ToggleOrchestrator` for its mutations (PANEL-02, Pattern 2), but `WindowsMonitorController` is a stateful singleton shared with the toggle path. Add a `BeginExclusiveMonitorAccess()` lease to `ToggleOrchestrator` that shares the *existing* `_busy` flag with `RunGuarded`, giving bidirectional mutual exclusion without the panel adopting any toggle semantics.
2. **The Identify overlay window (PANEL-05).** A borderless, topmost, self-closing `Form` positioned from a CCD-sourced `MonitorPathSnapshot`.

Purpose: both are leaf dependencies with zero file overlap with the panel itself; landing them first lets Plan 02 focus purely on the panel.
Output: `BeginExclusiveMonitorAccess()` + 5 new unit tests, and `src/RigToggle.App/MonitorIdentifyOverlay.cs`.
</objective>

<planner_decision>
**Resolves 17-RESEARCH.md Open Question 1 / Assumption A3 (concurrency between panel actions and the Rig/Normal toggle path).**

Decision: **add a lightweight shared lease rather than accept the race.**

Rationale:
- The race is more reachable than the research estimated. `MonitorConfirmDialog.ShowDialog()` (PANEL-04's gate) runs a nested WinForms message loop, which *does* dispatch `WM_HOTKEY` to `MainForm.WndProc`. A hotkey press while the panel's confirmation dialog is open would start a full three-step toggle underneath a half-finished manual action, both mutating the same `WindowsMonitorController._originalPathsCache`.
- The mitigation is ~25 lines reusing machinery that already exists (`_busy`, `Interlocked.CompareExchange`, `ToggleInProgressException`, and the existing user-facing busy copy). No new abstraction, no new exception type, no new user-facing string.
- It does **not** compromise PANEL-02's independence: independence means the panel must not run toggle *semantics* (audio step, app step, `IModeStore` write, `AppSettings` monitor-set write). Sharing a mutual-exclusion flag is a serialization concern, not mode semantics. The panel still calls `IMonitorController` directly and still never touches `ToggleService`.
- The reverse direction is free: `MainForm.BtnToggle_Click` already catches `ToggleInProgressException` and shows the message with `MessageBoxIcon.Information`; `MainForm.PerformBackgroundToggle` already catches it and shows a balloon. **No `MainForm` change is required for a toggle to be correctly rejected while the panel holds the lease.**

Rejected alternative: an `IsBusy` read-only pass-through the panel checks before mutating (the research's cheaper suggestion). Rejected because a bare check is TOCTOU-racy across the confirmation dialog's message pump and gives no protection in the panel-holds/toggle-arrives direction.
</planner_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI thread (panel/hotkey/tray triggers) → shared stateful `WindowsMonitorController` singleton | Two independent entry points mutate the same live CCD topology and the same `_originalPathsCache` field with no serialization prior to this plan |
| Managed app → Windows CCD subsystem (`SetDisplayConfig`) | An incorrect topology mutation can leave the user with no usable display |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-17-02 | Denial of Service | Permanently wedged busy flag if a lease is never released (leaking the lease would block every future toggle for the process lifetime) | mitigate | Lease is `IDisposable`, always consumed via `using` at the call site (Plan 02), and releases exactly once via `Interlocked.Exchange(ref _released, 1)`.
