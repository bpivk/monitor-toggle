# Phase 17 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Context note:** No `CONTEXT.md` exists for this phase (`/gsd:discuss-phase` was not run — project is in autonomous "yolo" mode). Every decision below was made by this researcher from `17-RESEARCH.md`'s findings and this project's existing WinForms UI conventions (verified by reading `MainForm.Designer.cs`, `SettingsForm.Designer.cs`, `MonitorConfirmDialog.cs`/`.Designer.cs`, `ThemeApplier.cs`, `WindowsThemeProvider.cs` directly). ## Spacing Scale

Declared values (must be multiples of 4), applied to the **new** surfaces this phase introduces (`MonitorPanelForm`, `MonitorIdentifyOverlay`, the new `MainForm`/tray entry points):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Padding within the status-icon column |
| sm | 8px | `MainForm`'s new `btnMonitors` gap below `btnSettings` — pixel-matches the existing `btnToggle`→`btnSettings` gap (60+40=100 to 108 = 8px), not a new token |
| md | 16px | `MonitorPanelForm`'s outer margin (grid/button inset from form edges) — matches `MainForm`'s existing 16px control margin |
| lg | 24px | Gap between the monitor grid's bottom edge and the Identify button row |
| xl | 32px | Reserved; not used by this phase's compact panel |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions: Existing forms (`MainForm`, `SettingsForm`, `MonitorConfirmDialog`) predate a strict 4px-multiple discipline and are **not** being retrofitted by this phase (e.g. `SettingsForm`'s internal label offsets of 22px/25px) — per the existing project convention already documented inline (`SettingsForm.Designer.cs`: "UI-SPEC Spacing contract — pixel-parity, not a new token"), reused/adjacent-to-existing-control positions keep pixel parity with their neighbors rather than being forced onto a new grid. This phase's brand-new controls (the panel form, the identify overlay, `btnMonitors`) have no such legacy constraint and follow the 4px scale above cleanly.

## Typography

This codebase has a single, deliberate typography discipline: **one system font, one size, one weight, everywhere** — differentiation between "body" and "heading" text is achieved via layout position and bordered-panel grouping (THEME-05's flat-panel-caption convention), never via font size or boldness. Verified: zero `Bold`/`FontStyle` usage anywhere in `RigToggle.App`. This phase continues that discipline with exactly one deliberate exception (the Identify overlay's display number).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 9pt (Segoe UI, system default) | Regular (400) | native control auto-height (not CSS-driven; n/a) |
| Label | 9pt (Segoe UI, system default) | Regular (400) | native control auto-height (n/a) — panel captions differentiated by position inside a bordered `Panel`, never by font, matching every existing panel caption in `SettingsForm` |
| Heading | 9pt (Segoe UI, system default) | Regular (400) | native control auto-height (n/a) — this codebase has no distinct heading style; do not introduce bold/larger section headers in the new panel |
| Display | 120pt (Segoe UI) | Bold (700) | n/a — full-bleed centered via `Label.Dock = Fill` + `TextAlign = MiddleCenter` |

Display is the one deliberate exception: the Identify overlay's per-monitor number (PANEL-05), per `17-RESEARCH.md` Pattern 6's cited example value, shown full-screen on a black overlay. It visually scales down to fit smaller/lower-resolution monitors via the Label's Dock=Fill + MiddleCenter layout — there is no strict legibility SLA beyond "readable at a glance," matching PANEL-05's "briefly overlays a number" requirement.

## Color

This app themes via `Application.SetColorMode` plus the existing `ThemeApplier`/`WindowsThemeProvider` explicit-override pattern (dark values below are the exact literals already used in `ThemeApplier.ThemeMonitorGrid`/`ThemeButton`/`ThemeComboBox`, reused verbatim — not new colors). All new panel controls must be run through the same `ThemeApplier` helpers (or new sibling helpers following the identical `try { } catch { /* cosmetic-only */ }` shape) rather than inventing new colors.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Light: `SystemColors.Control`/`Window` (~#F0F0F0); Dark: `#202020` (`Color.FromArgb(32,32,32)`) | `MonitorPanelForm` background / window chrome |
| Secondary (30%) | Light: `SystemColors.Window` (#FFFFFF, grid cells) / `SystemColors.Control` (buttons); Dark: `#2D2D30` (`Color.FromArgb(45,45,48)`) | Grid cell background, button background, bordered-panel fill |
| Accent (10%) | Light: `SystemColors.Highlight` (system accent blue); Dark: `#005A9E` (`Color.FromArgb(0,90,158)`) | Reserved **only** for: `DataGridView` row selection highlight (reusing `ThemeApplier.ThemeMonitorGrid`'s existing `SelectionBackColor` verbatim). No other element in this panel uses the accent color — not buttons, not the Identify action, not row action buttons. |
| Destructive | not applicable this phase | No dedicated destructive-red styling is introduced. "Disable" is a reversible, guarded action (PANEL-04 confirmation + DISPLAY-12 zero-survivors guard already cover the risk), consistent with this codebase's existing convention of never using a red/destructive button treatment for the equivalent Rig/Normal-toggle monitor-disable action. |

Additional small-area semantic colors (icon glyphs only, each covering well under 5% of any surface — not part of the 60/30/10 chrome split, do not treat as "accent"):

| Role | Value | Usage |
|------|-------|-------|
| Status — active/on | `#2ECC71` (`Color.FromArgb(46,204,113)`) | Per-row status-dot icon (PANEL-01) when a monitor is currently active/on — exact literal from 17-RESEARCH.md Pattern 3 |
| Status — inactive/off | `#C83C3C` (`Color.FromArgb(200,60,60)`) | Per-row status-dot icon when a monitor is currently OS-disabled/off — exact literal from 17-RESEARCH.md Pattern 3 |
| Identify overlay | Background `#000000`, text `#FFFFFF` | PANEL-05's full-screen per-monitor overlay only — a deliberate, isolated exception to the chrome palette, not reused anywhere else |

Accent reserved for: **DataGridView row selection highlight only.** Do not use the accent blue for the Enable/Disable row-action buttons, the Identify button, or any hover state — those follow `ThemeApplier.ThemeButton`'s existing gray-scale hover/press palette exactly as `MainForm`/`SettingsForm` already do.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (MainForm button) | `Monitors…` — new button, placed directly below `btnSettings` at (16,148), size (288,32), `FlatStyle.Flat`, themed via `ThemeApplier.ThemeButton` exactly like `btnToggle`/`btnSettings`. Ellipsis matches `btnSettings`'s "Settings…" convention (this app always suffixes a button that opens another window with "…") |
| Tray menu entry | `Monitors` (no ellipsis) — new `ToolStripMenuItem`, inserted immediately after `traySettingsMenuItem` and before `traySeparator`. Final tray order: Switch to Rig/Normal Mode → Settings → **Monitors** → separator → Exit. No ellipsis matches the existing tray items' convention (`traySettingsMenuItem.Text = "Settings"`, no ellipsis, even though it opens a dialog) |
| Panel window title | `Rig Toggle — Monitors` — matches `SettingsForm`'s exact `"Rig Toggle — Settings"` title pattern |
| Row action button (per monitor) | Dynamic label: `Disable` when the row is currently active/on, `Enable` when currently inactive/off. Verb-first, sentence case, matches this app's existing action-button tone (`"Switch to Rig Mode"`, `"Save Settings"`) rather than the passive grid-checkbox labels ("Off"/"On") used elsewhere — these are immediate-effect buttons, not deferred config, so the copy must read as an action |
| Identify action | `Identify` — single button, bottom of the panel, triggers the per-monitor number overlay (PANEL-05) |
| Confirmation dialog title | `Confirm Monitor Changes?` — reused verbatim from the existing `MonitorConfirmDialog` |
| Confirmation dialog body | `This will disable "{MonitorFriendlyName}". Continue?` — single-monitor, disable-only adaptation of `MonitorConfirmDialog`'s existing clause-joining logic (`FormatNames`); PANEL-04 only gates Disable, never Enable, matching the dialog's existing enable/disable-direction precedent |
| Confirmation checkbox | `Don't ask again` — reused verbatim, writes back through `AppSettings.SkipMonitorConfirmation` exactly as the existing dialog does |
| Confirmation buttons | `Continue` / `Cancel` — reused verbatim |
| Error state (DISPLAY-12 rejection) | Title: `Rig Toggle` (this app's universal `MessageBox` title — never a bespoke title, verified across every `MessageBox.Show` call site in `MainForm.cs`). Body: `ex.Message` **reused verbatim, unmodified** — currently `"Cannot disable all configured monitors — at least one active display must remain."`, thrown by `WindowsMonitorController.DeactivateMonitors`. Do not reword this for panel context even though "configured monitors" reads slightly toggle-flavored in a manual-panel setting — DISPLAY-12's entire point is one shared codepath with one shared message; diverging the copy per call site would undermine that. `MessageBoxIcon.Warning`, `MessageBoxButtons.OK` |
| Empty state (defensive, expected unreachable) | Heading/body collapsed into one label shown in place of the grid if `GetAllMonitors()` ever returns zero rows: `"No monitors detected. Reconnect a display and reopen this panel."` Windows guarantees at least one active display exists whenever the desktop is running, so this is a defensive fallback, not an expected user-facing state |
| Destructive confirmation | Not applicable — see Color section's Destructive row. Risk is covered by the reused confirmation dialog (PANEL-04) and the zero-survivors guard (DISPLAY-12), not by destructive-styling or an extra "are you sure" beyond the existing pattern |

## Component Behavior Contract

Beyond copy/color/spacing, these interaction details are load-bearing for the executor and were derived directly from `17-RESEARCH.md`'s patterns — included here so the plan doesn't have to re-derive them:

- **`MonitorPanelForm`**: non-modal (`Show()`, never `ShowDialog()`), `Owner = null`, `ShowInTaskbar = true` (must be findable even when `MainForm` is minimized to tray), `FormBorderStyle = FixedDialog`, `MinimizeBox = true`, `MaximizeBox = false`, `StartPosition = CenterScreen`. Themed identically to every other form in this app: `DwmTitleBar.ApplyRoundedCornersAndMica` at construction, subscribes to `IThemeProvider.ThemeChanged` with the standard marshal-then-try/catch handler, unsubscribes both on `FormClosed` and as a `Dispose(bool)` backstop (the exact WR-01 pattern already used by `SettingsForm`/`MonitorConfirmDialog`).
- **Grid**: `DataGridView`, one row per `MonitorInfo` from `GetAllMonitors()`, `Tag = monitor.DevicePath` for stable row identity (matching `SettingsForm.dgvMonitors`). Columns: status icon (32px, `DataGridViewImageColumn`) → monitor name (Fill, `DataGridViewTextBoxColumn`, reusing `SettingsForm.PopulateMonitorGrid`'s existing Primary/OS-disabled suffix logic) → action button (80px, `DataGridViewButtonColumn`, label flips per Copywriting Contract above). Button-column clicks commit immediately — deliberately avoids Pitfall 5 (checkbox dirty-state commit lag) by not using checkboxes here.
- **Live refresh (PANEL-03)**: subscribes to `Microsoft.Win32.SystemEvents.DisplaySettingsChanged` while the form is open, unsubscribes on `FormClosed` + `Dispose(bool)` backstop, marshals via `InvokeRequired`/`BeginInvoke` exactly like `WindowsThemeProvider`'s consumers. The panel's own action-triggered refresh and the event-triggered refresh will both fire for a panel-initiated change (harmless double re-render, documented in 17-RESEARCH.md Pitfall 1 — do not add debounce logic to "fix" this).
- **Confirmation gate (PANEL-04)**: shown only on Disable clicks, only when `!AppSettings.SkipMonitorConfirmation`. Enable clicks are never gated.
- **Safety guard (DISPLAY-12)**: the panel calls `IMonitorController.DeactivateMonitors(new HashSet<string> { devicePath })` directly — the exact same method both toggle directions already call. No new pre-check is written in the panel; the zero-survivors guard lives solely in `WindowsMonitorController`.
- **Identify (PANEL-05)**: scoped to active monitors only (an OS-disabled monitor has no coordinates to place an overlay at); positioned from `CaptureState()`'s `MonitorPathSnapshot.PositionX/Y`/`ResolutionWidth/Height` (CCD-sourced), never `Screen.AllScreens`. Numbering derives from the panel grid's current row order. Auto-closes after 2500ms via `System.Windows.Forms.Timer`.
- **Out of scope reminders** (from `REQUIREMENTS.md`, load-bearing for this contract): no drag/resize/orientation editing in the panel; panel actions never write to `AppSettings.MonitorsToDisable`/`NormalMonitorsToDisable` or `IModeStore` — purely ad-hoc, session-local.
