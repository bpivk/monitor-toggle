# Phase 9 — UI Design Contract

> Visual and interaction contract for Phase 9 (Global Hotkey Trigger). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** Rig Toggle is a native WinForms desktop utility, not a web app. This project has no design-system tooling (no shadcn, no Tailwind, no component registry) — the template's web-oriented sections (spacing scale, color tokens, registry safety) are adapted below to their literal WinForms equivalents: absolute-position pixel layout, `SystemColors`/default control font, and "not applicable" for anything registry-specific. The governing principle for this phase is the same one Phase 8 used: **match the existing `SettingsForm` look exactly** (same dedicated-inline-warning pattern as `chkStartWithWindows`/`lblAutostartWarning`/`errAutostart`) — introduce zero new visual language. The one genuinely new interaction this phase adds is the hotkey-capture textbox itself (D-01), which is fully specified below since no prior phase has a "recording" control to copy.

## Spacing Scale

This app has no CSS-style spacing scale — layout is absolute `Location`/`Size` pixel values on designer-generated forms. The table documents the **actual conventions already in use** (verified by reading `SettingsForm.Designer.cs`), which every new control this phase adds must match:

| Token | Value | Usage / Evidence |
|-------|-------|-------------------|
| Form-edge margin | 12px | Every `SettingsForm` group box and loose control starts at `x=12` |
| Content width (`SettingsForm`) | 396px | `ClientSize.Width (420) − 2×12px margin`; full-width controls (`lblAutostartWarning`, `chkEnableDebugLogging`) use `Width=396` |
| Vertical gap, loose-control-to-loose-control | 8px | `chkEnableDebugLogging` bottom (524) → `chkStartWithWindows` top (532) in the current file |
| Caption + inline field row (label left, control right) | Established by `grpAudioDevices`: caption `Label` at `x=12`, field control starting at `x=64` or `x=76`, both vertically centered in a ~20-23px row | Use for the new `lblHotkeyCaption`/`txtHotkey` pair below |
| Dedicated warning label height (single/double-line) | 20px (1 line) or 36px (2-line wrap, `AutoSize=false`) | `lblAutostartWarning` uses 20px for its short message; the new `lblHotkeyWarning` needs 36px because its message (`"Could not register hotkey — it may already be in use by another application. Choose a different combination or close the conflicting app, then click Save again."`) is long enough to wrap to two lines at 396px width |

**Exceptions:** none.

## Color

No hardcoded color appears anywhere in the existing codebase — every control uses WinForms/OS theme defaults, which is why the app already follows the user's Windows light/dark theme automatically with zero theming code. **This phase must not introduce a hardcoded RGB/hex color.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `SystemColors.Control` (OS theme default) | Form background — unchanged |
| Secondary (30%) | `SystemColors.Window` (OS theme default) | `txtHotkey`'s idle/configured background, matching every other textbox/combo in the form |
| Accent (10%) | `SystemColors.Info` | Reserved for exactly one thing this phase: `txtHotkey.BackColor` while actively in the "Recording…" capture state (see Interaction States). Nothing else in this phase may use it. `SystemColors.Info` is the correct choice over a hardcoded highlight color because it is theme-adaptive (renders as the OS's native "tooltip/info" surface color in both light and dark Windows themes), consistent with this app's zero-hardcoded-color rule. |
| Destructive | none | No destructive action exists in this phase (see Copywriting Contract) |

Accent reserved for: the hotkey-capture textbox's "Recording…" background highlight only — never any other control, never a permanent/idle state.

## Interaction States — `txtHotkey` (the one new control this phase's design hinges on)

`txtHotkey` is a `ReadOnly=true`, `TabStop=false` TextBox (D-01). `TabStop=false` is a deliberate, load-bearing choice, not an oversight: if the field were reachable via keyboard Tab-cycling, landing on it via Tab and then pressing Tab/Enter/Escape to continue normal dialog navigation would be indistinguishable from "the user is recording those exact keys as their hotkey." Capture mode must only ever begin via an explicit mouse click (`MouseDown`/`Click` on the control), never via `GotFocus` alone. `Cursor = Cursors.Hand` (not the default I-beam) reinforces that this is a click-to-activate control, not a free-text field.

| State | Trigger | `Text` | `BackColor` | `ForeColor` |
|-------|---------|--------|-------------|-------------|
| Unconfigured (idle) | No hotkey saved; not currently being clicked | `"(No hotkey set — click to configure)"` | `SystemColors.Window` | `SystemColors.GrayText` |
| Configured (idle) | A hotkey is saved; not currently being clicked | The friendly combo string, e.g. `"Ctrl+Alt+R"` (see format below) | `SystemColors.Window` | `SystemColors.WindowText` |
| Recording | User clicks the field (from either idle state above) | `"Press a key combination… (Esc to clear)"` | `SystemColors.Info` (the one Accent use in this phase) | `SystemColors.WindowText` |
| Recording → captured | A non-modifier key is pressed while one or more modifiers are held, during Recording | The new friendly combo string (replaces the prior value) | reverts to `SystemColors.Window` | `SystemColors.WindowText` |
| Recording → bare modifier only | Only a modifier key (Ctrl/Alt/Shift/Win) is pressed and released with no non-modifier key, during Recording | unchanged — stays `"Press a key combination… (Esc to clear)"` | stays `SystemColors.Info` | unchanged |
| Recording → Escape | Esc pressed during Recording (D-01) | Reverts to the **Unconfigured** state's text, regardless of what was previously configured — Escape always clears, never just "cancels back to the old value" | reverts to `SystemColors.Window` | reverts to `SystemColors.GrayText` |
| Recording → focus lost without a completed capture or Escape (e.g. user clicks elsewhere) | `LostFocus`/click-away mid-Recording | Reverts to whatever the field showed **before this Recording attempt started** (Unconfigured or previously-Configured text) — losing focus is a silent cancel, never a clear. Only an explicit Escape clears an existing configured value. | reverts accordingly | reverts accordingly |

**Friendly combo string format:** modifiers in the fixed order `Ctrl+Alt+Shift+Win` (only the ones actually held are included), then the non-modifier key's display name, joined with `+` and no spaces — e.g. `"Ctrl+Alt+R"`, `"Ctrl+Shift+F5"`. This is the same order Windows' own "Customize Shortcut Key" UI uses, so it reads as familiar rather than app-invented. Exact `Keys`-enum-to-display-name mapping for less-common keys (e.g. `Keys.PageUp` → `"PageUp"`) is left to the planner/executor — the ordering and separator convention above is the prescriptive part.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `"Save Settings"` — unchanged existing button; this phase adds no new action button. Hotkey registration is attempted as part of the existing Save flow (D-04), exactly like the autostart write already is. |
| `lblHotkeyCaption` | `"Hotkey:"` — terse, matching the existing `lblAudioNormalCaption`/`lblAudioRigCaption` (`"Normal:"`/`"Rig:"`) style: a short label, colon, no extra punctuation |
| `txtHotkey` — empty state (no hotkey configured, D-02's opt-in default) | `"(No hotkey set — click to configure)"` — parenthetical placeholder style, `SystemColors.GrayText`, so it visually reads as a hint rather than a real value (same visual language convention as a web form's placeholder text, adapted to WinForms) |
| `txtHotkey` — recording state | `"Press a key combination… (Esc to clear)"` — states the action expected (press keys) and the one keyboard escape hatch, so a user who clicks in by accident always has a way out without needing external documentation |
| Error state — Settings inline warning (D-05, locked core wording from `09-CONTEXT.md`, extended with the missing "what to do next" clause to match this codebase's established warning-copy convention, e.g. `ShowStaleWarning`'s `"...please reselect."`) | `"Could not register hotkey — it may already be in use by another application. Choose a different combination or close the conflicting app, then click Save again."` |
| Error state — startup-failure toast body (D-06, locked core wording from `09-CONTEXT.md`, unified in tone with the Settings inline warning above so the same underlying event reads consistently across both surfaces) | `"Rig Toggle: the configured hotkey could not be registered — it may already be in use by another application."` |
| Startup-failure toast title/icon | Title `"Rig Toggle"` (matching the existing non-toggle-result toast precedent — `TrayToggleMenuItem_Click`'s `ToggleInProgressException` branch also titles its balloon `"Rig Toggle"`, not a mode-specific title, since this isn't a toggle outcome); `ToolTipIcon.Warning` (matching the existing partial-failure toast icon convention from Phase 8, not `.Error` — this app never uses `ToolTipIcon.Error` anywhere) |
| Empty state | Covered above under `txtHotkey`'s empty state — this phase adds no list/collection view, so the closest analog is the unconfigured-hotkey placeholder, not a separate empty-state heading/body pair |
| Destructive confirmation | **None.** Clearing a recorded hotkey (Escape, or simply leaving the field unset) is an instantly reversible preference edit — not destructive — consistent with every other `SettingsForm` field having no confirmation dialog. A failed registration also does **not** block or roll back Save (D-05): the user's chosen combination is still persisted as their preference even if it isn't currently active. |
