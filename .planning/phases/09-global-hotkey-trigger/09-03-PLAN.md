Add the hotkey-capture UI to SettingsForm (the one genuinely new interaction this phase introduces), wire load/save of the combo, surface registration failures inline (D-05), and drive registration at startup and Settings-Save through MainForm's shared helper (D-04).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Keyboard capture → stored combo | User keystrokes in the recording textbox become the persisted HotkeyModifiers/HotkeyKey; captured on the user's own machine in their own Settings dialog. |
| SettingsForm → MainForm registration callback | A UI action (Save) invokes MainForm's registration on the app's own window handle. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-06 | Tampering | Malformed key capture (bare modifier, unmodified key) producing an invalid combo | mitigate | The capture state machine only accepts a non-modifier key while at least one modifier is held (HotkeyCombo.IsModifierVirtualKey rejects bare modifiers; an unmodified key stays in Recording). e.SuppressKeyPress prevents captured keys from leaking into normal dialog navigation. |
| T-09-07 | Denial of Service | Registration failure at Save leaving the dialog in a stuck state | accept | DialogResult.None simply keeps the dialog open with a clear "click Save again" warning; Discard/Escape still closes it, and the combo is already persisted — no lockout. Registration is a single attempt per Save click, no loop. |
| T-09-SC | Tampering | Package installs | accept | Zero new dependencies (WinForms BCL only). No NuGet/npm/pip/cargo install; package-legitimacy gate not applicable. |

No HIGH-severity threat applies: capture is local, in-process, on the user's own dialog; no network surface; no privilege change; no untrusted remote input.
</threat_model>
