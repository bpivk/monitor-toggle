# Phase 20 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a native Windows Forms (.NET 10, `net10.0-windows`) desktop application, not a web app. The shadcn/component-registry model from this template is not applicable — see Design System and Registry Safety sections below for the WinForms-equivalent contract. This document follows the same platform-adapted shape established by `12-UI-SPEC.md`/`13-UI-SPEC.md`/`17-UI-SPEC.md`/`19-UI-SPEC.md`.
>
> **Phase framing:** `btnToggle` (`Button`, 288×40, `FlatStyle.Flat`) is **deleted** this phase and replaced by one new custom-drawn `ToggleSwitch : UserControl` occupying the same slot in tab order and layout sequence (tile row → Identify → toggle row → Settings, per `19-CONTEXT.md` D-09). `lblMode` is also **deleted** (D-06) — the switch row becomes MainForm's single mode readout. This phase reuses the **existing static** `AccentColor` placeholder (`Color.FromArgb(0,90,158)` dark / `SystemColors.Highlight` light) unchanged — live Windows-accent reading is Phase 21's scope (THEME-07), explicitly out of scope here. Toggle-switch slide animation is explicitly out of scope (`REQUIREMENTS.md`) — every state change (on/off/hover/press/indeterminate) is an instant redraw, no tween/animation.

## Component: `ToggleSwitch`

The single new control this phase adds. Renders as one row spanning `MainForm`'s existing content-width floor (`ContentWidthFloorPx` = 288px, unchanged) — the whole row is one `UserControl` and therefore one clickable/focusable surface (resolves D-04's "entire row clickable" with no extra click-forwarding plumbing between a separate label and switch). It paints its own "Rig Mode" label text on the left and a compact track+thumb pill on the right; it is a **drop-in replacement for `btnToggle`** in `MainForm`'s Controls collection, tab order, and layout slot.

### Public surface (dumb/presentational, mirrors `MonitorTile`)

| Member | Shape | Notes |
|--------|-------|-------|
| `enum ToggleSwitchState { Off, On, Indeterminate }` | new small enum | Off = Normal mode (D-08), On = Rig mode (D-08), Indeterminate = DISPLAY-11 unknown-mode state (D-07) |
| `State` (get) / `SetState(ToggleSwitchState state)` | property + setter method | The **only** way state is ever pushed in, mirroring `MonitorTile.SetState`. `MainForm.RefreshUi()` calls this instead of setting `lblMode.Text`/`btnToggle.Text` |
| `event EventHandler? ActionRequested` | event | Fired on `OnClick` and on Space/Enter while focused (`ProcessCmdKey`, exact copy of `MonitorTile`'s override) — the control never decides what a click *means* (toggle vs. refuse-and-explain for Indeterminate); `MainForm`'s existing `BtnToggle_Click` body (WR-01 gate, DISPLAY-11 gate, confirmation dialog, orchestrator call) is ported to this handler verbatim, unchanged |
| Theme color properties (`OnColor`, `OffOutlineColor`, `OffHoverFillColor`, `OffPressFillColor`, `IndeterminateColor`, `ThumbColor`, `ThumbOutlineColor`, `LabelColor`, `FocusRingColor`) | `[DesignerSerializationVisibility(Hidden)]` settable properties, each `Invalidate()`s on set | Written **only** by the new `ThemeApplier.ThemeToggleSwitch(ToggleSwitch, bool dark)` method — the control itself never reads `IThemeProvider` (Pitfall 1/Anti-Pattern 3) |

### Geometry Contract

Fixed design constants (expressed in the same "logical px, passed through `MainForm.Scaled()`" convention `TileWidthPx`/`TileHeightPx` already use) — inside `OnPaint`, derive every coordinate from these Scaled() values and `ClientSize`, never a bare pixel literal (Pitfall 9/D-01 discretion resolved below):

| Property | Value | Notes |
|----------|-------|-------|
| Row size | 288px (contentWidth) × 32px (`ToggleRowHeightPx`, replaces the old `TogglePx` = 40) | Row width matches the existing content-width floor so the switch row's left/right edges align with the tile strip/Identify button/Settings-gear column above and below it — same alignment discipline `19-UI-SPEC.md` already established, just a shorter row (32px vs. the old button's 40px) since it no longer needs to look like a big primary-action button (D-01) |
| Track (pill) size | **52px × 28px, fixed** | Within D-01's "~50-60px" range; does not stretch with the row — the compact-switch identity (not a full-width pill, D-01) is preserved regardless of window/content width |
| Track corner radius | 14px (= track height ÷ 2, fully rounded ends) | Geometric derivation, not a spacing-scale token — same treatment `19-UI-SPEC.md` gave its 12px tile gap/4px badge radius |
| Thumb diameter | 20px | |
| Thumb padding (inset from track edge) | 4px | `20 + 2×4 = 28` = track height exactly — thumb always touches both track edges vertically |
| Thumb center X — Off (left) | 14px from track's left edge | `padding(4) + radius(10)` |
| Thumb center X — On (right) | 38px from track's left edge | `trackWidth(52) − padding(4) − radius(10)` |
| Thumb center X — Indeterminate (mid-track) | 26px from track's left edge | `trackWidth ÷ 2` — exactly equidistant (12px) from both the Off and On positions, so it reads as neither (D-07) |
| Thumb center Y | vertically centered in the track, all states | |
| Track position within row | right-aligned, vertically centered in the row | Label occupies the remaining left space |
| Label position within row | left-aligned, vertically centered in the row, "Rig Mode" (static, D-05) | 9pt Segoe UI Regular, `TextRenderer.DrawText` with `VerticalCenter | Left | NoPrefix`, matching `MonitorTile`'s `TextRenderer` usage |
| Focus ring | 2px accent-colored **rounded** rectangle (radius = track's own 14px, i.e. hugging the pill shape, not a plain rectangle) drawn around the track only — not the whole row | Reuses `MonitorTile.BuildRoundedRect`'s exact rounded-rect path builder (or a local copy of it), not `DrawButtonFocusRing` (which draws a plain rectangle — wrong shape for a pill). Drawn only when `Focused` |
| Compositing | Track and thumb are **separate** `GraphicsPath`/`FillPath` calls, stroke-then-fill, back-to-front (track first, thumb on top) | Mandatory — Pitfall 2. Never union track+thumb into one `GraphicsPath` before an outline/stroke pass |

**Discretion resolved (D-01):** row height 32px, track 52×28px — proportionate to the 72×88px tiles and the existing 32px Identify/Settings-gear controls above/below it, and comfortably inside the ~50-60px range D-01 named.

### State → Visual Mapping (D-07, D-08, D-10, D-11 — must never rely on color alone)

| State | Track fill (rest) | Track stroke | Thumb X position | Meaning |
|-------|--------------------|----------------|--------------------|---------|
| **Off** (Normal mode) | none — transparent, row `BackColor` shows through | 2px, `OffOutlineColor` | left (14px) | D-10: hollow/gray-outline = off, matching the tile's D-02 OFF convention exactly |
| **On** (Rig mode) | solid, `OnColor` (= existing `AccentColor` placeholder, D-09) | none | right (38px) | D-09: same accent literal the tile dashboard's ON-state icon fill already uses |
| **Indeterminate** (DISPLAY-11 unknown mode, D-07) | solid, `IndeterminateColor` (a distinct neutral gray — new literal, see Color section) | none | mid-track (26px) | Fill-vs-hollow AND position both differ from both Off and On — two independent, non-color signals, satisfying success criterion #2's "distinguishable by shape/position alone" even more strongly than the two-state case alone requires |

Three states are visually distinguished by **fill-presence** (hollow vs. solid) and **thumb position**, not by color alone — satisfies Phase 20 success criterion #2 even for someone who cannot distinguish the accent blue from the neutral gray.

**Discretion resolved (D-07):** Indeterminate thumb sits at the exact midpoint (26px), equidistant from both real positions; its track is solid-filled (unlike Off's hollow track) specifically so it cannot be mistaken for "Off with a slightly different color" — filled-but-gray is a third, unambiguous visual bucket.

## Color

Every literal below is either reused verbatim from `ThemeApplier`/`MainForm.AccentColor` (D-09/D-10/D-12) or is a small, new, deliberately-isolated literal for the Indeterminate state (D-07), following the exact "no new colors unless a decision explicitly calls for one" discipline `19-UI-SPEC.md` established. This phase's new `ThemeApplier.ThemeToggleSwitch(ToggleSwitch, bool dark)` method sets the properties below and must be called from **both** `MainForm.OnThemeChanged` **and** `MainForm.InitializeTrayState()` (Pitfall 1 — see Component Behavior Contract).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | unchanged (`MainForm` background) | not touched by this phase |
| Secondary (30%) | Light: `SystemColors.ControlLight` / `SystemColors.ControlDarkDark`; Dark: `Color.FromArgb(80,80,86)` / `Color.FromArgb(18,18,20)` | Off-state track's hover/press fill — reused **verbatim, literal-for-literal**, from `ThemeApplier.ThemeButton`'s existing `MouseOverBackColor`/`MouseDownBackColor` (D-12: "copies the existing owner-draw pattern exactly") |
| Accent (10%) | Light: `SystemColors.Highlight`; Dark: `Color.FromArgb(0,90,158)` | **Expands** the accent-reserved list `19-UI-SPEC.md` locked (tile ON-icon fill + tile focus ring) to also include: the switch's **On-state track fill**, its hover/press variants (below), and the switch's own focus ring. Nothing else on this row uses accent — the "Rig Mode" label stays `LabelColor` (plain theme text color), never accent |
| Destructive | not applicable | Toggling mode is a reversible, already-guarded action (DISPLAY-12); no destructive styling, consistent with every prior phase |

On-state track hover/press (new — no existing literal to reuse, since no prior control fills with the raw accent color and needs a hover/press variant of it):

| State | Formula | Rationale |
|-------|---------|-----------|
| Hover | `ControlPaint.Light(OnColor, 0.2f)` | In-box WinForms API (`System.Windows.Forms.ControlPaint`) — computes correctly regardless of whether `OnColor` is the fixed dark-mode literal or the **live, user-set** `SystemColors.Highlight` in light mode (and will continue to work unmodified once Phase 21/THEME-07 replaces this with a truly live-read accent color — no rework needed here, matching D-09's stated rationale) |
| Press | `ControlPaint.Dark(OnColor, 0.2f)` | Same rationale — magnitude chosen to visually match the existing button hover/press deltas' intensity (`ThemeButton`'s dark literals move ±35/±27 per channel; `ControlPaint`'s 0.2f factor produces a comparable visible shift) |

Indeterminate track (new, isolated literal — D-07's "must remain unmistakably distinct" requirement):

| Role | Value | Usage |
|------|-------|-------|
| Indeterminate track fill (rest) | Light: `Color.FromArgb(200,200,200)`; Dark: `Color.FromArgb(90,90,90)` | A neutral gray deliberately positioned between the Off state's hollow-outline treatment and the On state's accent fill — filled (unlike Off) but unmistakably not accent-colored (unlike On). New literal, isolated to this one state, following `19-UI-SPEC.md`'s "deliberate isolated exception" precedent (its primary-badge color) |
| Indeterminate track hover/press | `ControlPaint.Light(IndeterminateColor, 0.2f)` / `ControlPaint.Dark(IndeterminateColor, 0.2f)` | Same mechanism as On-state, applied to the Indeterminate base instead |

Off-state track outline + thumb (reused literals):

| Role | Value | Usage |
|------|-------|-------|
| Off-state track outline | Light: `SystemColors.GrayText`; Dark: `Color.FromArgb(160,160,160)` | Identical literal to `ThemeApplier.ThemeMonitorTile`'s `IconOffColor` / the tile's D-02 OFF convention — same "off" visual language app-wide, reused verbatim per D-10 |
| Thumb fill | `Color.White` (both themes) | D-11 — theme-independent, always high-contrast |
| Thumb outline | Light: `SystemColors.ControlDark`; Dark: `Color.FromArgb(160,160,160)` | 1px stroke keeping the white thumb visible even against a light-mode row background/hover fill that could otherwise read as near-white-on-near-white |
| Label text (static "Rig Mode") | Light: `SystemColors.ControlText`; Dark: `Color.FromArgb(240,240,240)` | Plain theme text color, matching every other label/button text in this codebase — never accent |

Accent reserved for (full, updated list this phase produces): **the tile dashboard's ON-state icon fill + tile focus ring (19-UI-SPEC.md, unchanged) AND the toggle switch's On-state track fill (+ its hover/press variants) + the switch's own focus ring.** Nothing else — not the "Rig Mode" label, not the Off/Indeterminate track fills, not the Identify/Settings buttons.

## Layout Integration (lblMode removal, D-06)

**Discretion resolved:** the ~28px of vertical space `lblMode`'s removal frees (`ModeLabelHeightPx` 20px + `GapSmPx` 8px) is **collapsed, not preserved as breathing room** — `LayoutDashboard()`'s `stripTop` calculation changes from `margin + Scaled(ModeLabelHeightPx) + Scaled(GapSmPx)` to just `margin`, so the tile strip now starts flush with the window's top margin. Rationale: once the switch row is the sole mode-state readout (D-06), an empty gap where `lblMode` used to sit would read as an unexplained layout gap, not intentional whitespace — collapsing keeps the window exactly as tall as its content needs, consistent with `LayoutDashboard()`'s existing "compute everything arithmetically, no dead space" philosophy.

Resulting vertical order (unchanged relative sequence, D-09): tile row (now flush with top margin) → Identify button → toggle switch row (replaces `btnToggle`'s old slot, same `GapSmPx` gap above it) → Settings gear (same `GapLgPx` gap above it, unchanged).

## Component Behavior Contract

- **Dumb/presentational** (Architecture Pattern 1, mirrors `MonitorTile`): `ToggleSwitch` never calls `ToggleOrchestrator`/`IMonitorController`/`ISettingsStore` itself. It exposes `SetState(ToggleSwitchState)` and raises `ActionRequested` on click or Space/Enter; `MainForm` remains the sole owner of the mutation logic (`BtnToggle_Click`'s existing body, ported verbatim into the new handler, unchanged control flow/gates).
- **Theming pipeline (Pitfall 1):** new `ThemeApplier.ThemeToggleSwitch(ToggleSwitch, bool dark)` must be added to **both** `MainForm.OnThemeChanged` and `MainForm.InitializeTrayState()` — a switch themed in only one call site renders correctly at whichever theme Windows happened to be in at startup, then freezes while every other control keeps flipping live. Verify with a live Light↔Dark OS flip while running, and again under `--tray` hidden-start.
- **GraphicsPath seam artifacts (Pitfall 2):** track and thumb are separate `GraphicsPath`/`FillPath` calls, stroke-then-fill, back-to-front — never unioned into one path before an outline pass. Verify with a zoomed screenshot at the thumb/track overlap boundary in both the Off and On positions, not a rig glance alone.
- **Flicker/Mica (Pitfall 3):** constructor sets `ControlStyles.OptimizedDoubleBuffer | AllPaintingInWmPaint | UserPaint | ResizeRedraw`. `ToggleSwitch.BackColor` is set to the same dominant-background literal `MonitorTile.BackColor` already uses (dark `Color.FromArgb(32,32,32)` / light `SystemColors.Control`) — the already-proven-safe pattern for a custom control sitting on `MainForm`'s Mica-backed surface, not a new transparency mechanism.
- **Keyboard (UX Pitfall table):** `TabStop = true`; `ProcessCmdKey` handles Space/Enter identically to `MonitorTile`'s override; a visible focus ring is drawn explicitly in `OnPaint` (a plain `UserControl` gets none of `Button`'s free focus affordances). Verify with a Tab-then-Space/Enter keyboard-only toggle, not just a mouse click.
- **DPI (Pitfall 9):** every `OnPaint` coordinate (track/thumb rects, label rect, focus ring) is derived from the Scaled() constants above and `ClientSize`, never a bare pixel literal inside the paint method itself. Verify at 125%/150% Windows display scale on real rig hardware (unverifiable in this build environment).
- **GDI handle discipline:** cache brushes/pens/paths as instance fields or construct them fresh per `OnPaint` call and dispose via `using`, matching `MonitorTile`'s existing discipline — this is a long tray-resident session control, same handle-leak risk class.
- **Animation:** explicitly none. Every state/hover/press transition is an instant `Invalidate()`-triggered redraw with no interpolation — toggle-switch slide animation is out of scope per `REQUIREMENTS.md`.
- **Deletion order:** `btnToggle` (Designer field, `BtnToggle_Click`/`BtnToggle_Paint`/`BtnToggle_Enter`/`BtnToggle_Leave` handlers, `DrawButtonFocusRing` call site) and `lblMode` (Designer field, all `RefreshUi()`/`LayoutDashboard()` references) are removed together with the new `ToggleSwitch` wiring in place — not left half-migrated.
