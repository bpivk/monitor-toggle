<objective>
Build the two standalone, unwired building blocks of the custom toggle switch: the `ToggleSwitch` owner-drawn `UserControl` and its `ThemeApplier.ThemeToggleSwitch` companion. Nothing on `MainForm` references either yet — Plan 02 swaps them in for `btnToggle`.

Purpose: `btnToggle` is the control that actually performs mode changes. Building its replacement in isolation means the paint geometry, three-state visual contract, keyboard model, and theme surface are settled and compiling before the `MainForm` swap (which simultaneously deletes `btnToggle` AND `lblMode`) starts consuming them. This mirrors Phase 19's Plan 01/02 split exactly, and `ARCHITECTURE.md`'s Recommended Build Order step 7 ("build as its own standalone control, same isolation principle as step 1").
Output: `src/RigToggle.App/Controls/ToggleSwitch.cs` (new) and a new `ThemeToggleSwitch` method appended to `src/RigToggle.App/ThemeApplier.cs`. The solution must still build and all 81 existing tests must still pass — these changes are purely additive and no existing call site changes.
</objective>

<hard_constraints>
Load-bearing rules. Violating any one fails the phase even if the switch looks right.

1. `ToggleSwitch` NEVER references `ToggleOrchestrator`, `IMonitorController`, `ISettingsStore`, `IThemeProvider`, `MonitorConfirmDialog`, or `MessageBox`. It is presentational only (ARCHITECTURE.md Pattern 1 / Anti-Pattern 3): it exposes `SetState(ToggleSwitchState)`, raises `ActionRequested`, and lets `ThemeApplier` write its colors. `MainForm` (Plan 02) owns every gate and every mutation.
2. NO bare pixel literals inside `OnPaint`. Every coordinate, radius, stroke width, and gap is derived from `ClientSize` and a named fractional constant (Pitfall 9 — `RigToggle.App.csproj` sets no `ApplicationHighDpiMode`, and `AutoScaleMode.Font` has zero visibility into custom paint code).
3. The track's size is derived from `ClientSize.Height`, NEVER from `ClientSize.Width`. `MainForm`'s content width grows with monitor count (`contentWidth = Math.Max(Scaled(288), stripW)`), and D-01 requires a compact switch that does not stretch into a full-width pill.
4. Track and thumb are drawn as SEPARATE, non-combined shapes, back to front (track first, thumb on top). Never union them into one `GraphicsPath` before an outline pass — that reproduces the Phase 13 `DrawPath` seam-artifact bug (Pitfall 2).
5. `OnPaint` must never let an exception escape. A WinForms paint exception is process-fatal. Wrap the whole body in try/catch with `Trace.WriteLine`, matching this codebase's swallow-with-trace convention.
6. All three states must be distinguishable by fill-presence AND thumb position, not color (success criterion 2 / D-07). Do not collapse Indeterminate into "Off with a different color".
7. Zero new NuGet packages, zero image assets, zero `.Designer.cs`, zero `.resx`. `ControlPaint.Light`/`ControlPaint.Dark` are in-box `System.Windows.Forms` members.
8. No `SystemEvents` subscription of any kind inside this control (ARCHITECTURE.md Anti-Pattern 2 — accent-color reading is Phase 21's scope, not this phase's).
</hard_constraints>
