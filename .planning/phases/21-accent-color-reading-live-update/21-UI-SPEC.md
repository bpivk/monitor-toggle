# Phase 21 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a native Windows Forms (.NET 10, `net10.0-windows`) desktop application, not a web app. The shadcn/component-registry model from this template is not applicable — see Design System and Registry Safety sections below for the WinForms-equivalent contract. This document follows the same platform-adapted shape established by `12-UI-SPEC.md`/`13-UI-SPEC.md`/`19-UI-SPEC.md`/`20-UI-SPEC.md`.
>
> **Phase framing (D-04):** This phase adds **zero new controls, zero new copy, zero new spacing, zero new typography, and zero new layout**. It is a pure *color-source* swap: the single fixed placeholder literal (`Color.FromArgb(0, 90, 158)` dark / `SystemColors.Highlight` light) that `MainForm.AccentColor` and `ThemeApplier.ThemeMonitorTile`/`ThemeToggleSwitch` already read is replaced by one live-read value — `_themeProvider.AccentColor`, sourced from the Windows registry (primary) or `DwmGetColorizationColor` (fallback), diffed and pushed through the exact same repaint funnel (`OnThemeChanged` → `ApplyDashboardTheming()`) that light/dark flips already use. The accent-tinted element set is locked to exactly what already consumes the placeholder today (D-04) — no new consumer is added. The DWM title bar/window border is explicitly **not** accent-tinted this phase (stays light/dark-only Mica chrome). No toggle-switch animation, no new confirmation dialogs, no new strings.

## Live Accent-Color Contract (this phase's actual scope)

### Source of truth (D-01)

| Priority | Source | Format | Notes |
|----------|--------|--------|-------|
| 1 (primary) | `HKCU\Software\Microsoft\Windows\DWM\AccentColor` registry value | packed DWORD, extracted as `(v>>16)&0xFF`=R, `(v>>8)&0xFF`=G, `v&0xFF`=B, alpha byte discarded | Read fresh on every diff cycle, never cached/persisted |
| 2 (fallback, only if key absent) | `DwmGetColorizationColor` (dwmapi.dll) | `0xAARRGGBB`, same shift/mask arithmetic as above per `21-RESEARCH.md` Pattern 1 | Must never throw — safe default `SystemColors.Highlight` on any failure |

The resolved value is exposed as a single theme-independent `Color AccentColor` on `IThemeProvider` — **not** two per-theme literals. This is the one structural visual change every consumer below must reflect: the existing `dark ? Color.FromArgb(0, 90, 158) : SystemColors.Highlight` ternary is deleted at every call site and replaced by a direct pass-through of the live value. Accent no longer differs by light/dark theme; it differs only by what the user has actually set in Windows.

### Consumers (D-04 — exhaustive, no additions)

| Consumer | Property | Visual role | Call site |
|----------|----------|-------------|-----------|
| `MonitorTile` | `AccentColor` | ON-state icon fill | `ThemeApplier.ThemeMonitorTile` |
| `MonitorTile` | `FocusRingColor` | keyboard-focus ring | `ThemeApplier.ThemeMonitorTile` |
| `ToggleSwitch` | `OnColor` | ON-state (Rig mode) track fill | `ThemeApplier.ThemeToggleSwitch` |
| `ToggleSwitch` | `FocusRingColor` | keyboard-focus ring | `ThemeApplier.ThemeToggleSwitch` |
| `MainForm` | `AccentColor` (private property, line ~184) | Identify button focus ring, Settings button focus ring (`DrawButtonFocusRing`) | `MainForm.AccentColor` getter |

Explicitly **not** a consumer this phase: `DwmTitleBar.cs` (title bar / window border chrome). This was considered and declined (D-04) — stays Mica/light-dark-only.

Explicitly **not** re-derived this phase (already formula-based against whichever `OnColor`/`AccentColor` value is current, so they track the live accent automatically with no code change): the switch's On-state hover/press fills (`ControlPaint.Light(OnColor, 0.2f)` / `ControlPaint.Dark(OnColor, 0.2f)`, per `20-UI-SPEC.md`). No new hover/press formula is introduced.

### Live-update behavior (Success Criterion 2)

- Changing the Windows accent color while the app is running must visibly update every consumer above **without restarting the app**.
- Update path: `WindowsThemeProvider.OnUserPreferenceChanged` (existing, extended per D-02 — not a new `SystemEvents` subscription) reads + diffs the accent value under lock → raises `AccentColorChanged` only on a genuine change → `MainForm`'s existing subscription block gains `_themeProvider.AccentColorChanged += OnThemeChanged` (same handler light/dark already uses) → `ApplyDashboardTheming()` re-runs → all five consumers above repaint together, in one pass, with no per-consumer special-casing.
- Same-color reselection must be a no-op: re-picking the currently-active accent must not cause a spurious repaint/event (`Color` value-equality diff, per `21-RESEARCH.md` Pattern 2).
- No animation/transition on an accent change — the repaint is an instant redraw, consistent with this codebase's existing no-animation convention (Phase 20).

### Accuracy requirement (Success Criterion 3)

The accent-tinted elements' rendered color must match what Settings > Personalization > Colors shows **exactly** (color-picker sampled hex match, not "close"/eyeballed) — including for the rig's actual custom (non-default) accent, per `21-CONTEXT.md` D-03. This is a hard visual-fidelity bar, not a "roughly on-brand" one; see `21-RESEARCH.md`'s Rig-Verification Checklist for the exact steps (registry ground-truth check, static swatch match, saturated-primary R/B-swap check, live multi-flip test, same-color no-op test). Verification is user-owned on the real rig per D-05 — do not mark this phase visually complete without that reported PASS.

## Color

This is the section this phase actually changes. Every other role below (dominant, secondary, destructive, off-state/thumb/label literals) is **unchanged** — only the Accent row's *source* changes, from two fixed per-theme literals to one live-read value.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | unchanged (`MainForm` background) | not touched by this phase |
| Secondary (30%) | unchanged (`ThemeApplier`'s existing hover/press/panel literals) | not touched by this phase |
| Accent (10%) | **live**, `_themeProvider.AccentColor` — resolved from `HKCU\Software\Microsoft\Windows\DWM\AccentColor` (primary) or `DwmGetColorizationColor` (fallback); theme-independent (same value regardless of light/dark) | Exactly the 5 consumers listed in the Consumers table above — nothing else |
| Destructive | not applicable | No destructive action in this phase, unchanged from every prior phase |

**Accent reserved for (unchanged list, D-04 — this phase makes it live, does not expand it):** `MonitorTile`'s ON-state icon fill + focus ring; `ToggleSwitch`'s ON-state track fill (+ its formula-derived hover/press variants) + focus ring; `MainForm`'s Identify-button and Settings-button focus rings. Nothing else — not the "Rig Mode" label, not the Off/Indeterminate track fills, not the DWM title bar, not any button's default (non-focused) appearance.

**Contrast note (non-blocking, flag for rig verification):** because the accent color is now fully user-controlled (any hue the user has picked in Windows, not a designer-chosen fixed blue), a pathologically light or low-contrast accent could in principle reduce the ON-state track fill's contrast against the white thumb, or the focus ring's visibility against the row background. No new contrast-safety mechanism is in scope for this phase (D-04 declines new consumers/logic beyond the live read) — this is called out only so the rig-verification pass (D-05) also does a quick visual sanity check with the user's actual accent, not a hue this project controls.

**Focal point:** unchanged from `19-UI-SPEC.md` — the tile row remains MainForm's primary visual anchor. This phase does not alter layout, hierarchy, or which element draws the eye first; it only changes what color value the existing accent-tinted elements resolve to.

## Registry Safety

Not applicable in the shadcn/component-registry sense. This is a native .NET/WinForms desktop project — there is no npm/shadcn dependency surface. This phase adds zero new NuGet packages; its only new API surface is one `[DllImport("dwmapi.dll")]` P/Invoke declaration (`DwmGetColorizationColor`, Microsoft Learn–documented, HIGH confidence) alongside the existing `DwmSetWindowAttribute` declaration in `NativeMethods.cs`, plus a `Microsoft.Win32.Registry` read (BCL, already referenced by `WindowsThemeProvider`'s existing `AppsUseLightTheme` read).
