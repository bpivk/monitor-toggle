<objective>
Build the one shared effective-theme resolver this phase exists to introduce, wire it in at the composition root so all three of the codebase's `IsDark`/`IsDarkTheme` copies resolve through it without being edited, and stop the application-level color mode from silently following the OS while an override is set.

Purpose: Pitfall 6 names the three independently-mirrored theme-resolution properties as this milestone's highest-risk theme item. The fix is not "add override checks in three places" — it is to make the object those three properties already read from resolve the override itself. This plan delivers that end-to-end: a value persisted in `settings.json` changes what every surface in the app resolves, before any UI to set it exists.
Output: `AppSettings.ThemeOverride`, `RigToggle.Core/OverridableThemeProvider.cs`, the composition-root swap, `ThemeApplier.ApplyEffectiveColorMode`/`ThemeFormSurface`, and unit coverage of the resolver.
</objective>

**Planning correction to PATTERNS.md — read before writing `CurrentTheme`:** PATTERNS.md's "Shared Patterns" section prescribes calling `_settingsStore.Load()` fresh on every `CurrentTheme` read. That prescription is wrong for this codebase and must not be followed literally: `MainForm.IsDark` is read from inside `BtnIdentify_Paint` (MainForm.cs ~line 1266), so a settings-file read per `CurrentTheme` read becomes a `File.ReadAllText` + JSON deserialize per button repaint, on the UI thread, in an app designed to stay tray-resident for hours. The correct reading of the underlying rule (ARCHITECTURE.md Anti-Pattern 3, "never cache `CurrentTheme`") is that the *effective theme* must never be cached — and it is not: `CurrentTheme` recomputes `preview ?? persistedOverride ?? _inner.CurrentTheme` on every read, and `_inner.CurrentTheme` is always live. Only the persisted override value is memoized, and it is re-read on `RefreshOverride()`, which is the only supported way that value changes while the app runs.

**Planning correction to ARCHITECTURE.md line 184 — diff-before-raise is deliberately NOT implemented:** ARCHITECTURE.md suggests re-raising `ThemeChanged` only when the effective theme actually changed. Do not add that suppression. Re-raising unconditionally on an inner OS flip means every subscriber re-applies the effective color mode and re-themes, which actively repairs any native-control drift WinForms' own OS-following may have introduced underneath an override — suppressing the event would leave that drift uncorrected, which is Pitfall 6's leak in its subtlest form. Every subscriber handler in this codebase is idempotent and cosmetic-only, and OS theme flips are rare, so the cost is nil. PATTERNS.md line 86 marks this refinement as "apply only if trivial, do not over-engineer"; this is the documented decision not to.
