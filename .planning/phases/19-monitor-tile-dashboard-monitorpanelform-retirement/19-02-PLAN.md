<objective>
Turn `MainForm` into the monitor-tile dashboard: host the tiles, lay the window out around them, populate them read-only from a single canonical monitor ordering, refresh them on hotplug, and theme every new control from both theming call sites. Tiles are not yet clickable-to-mutate — Plan 03 adds the mutation and Identify behavior.

Purpose: separating "the dashboard renders and re-renders correctly" from "the dashboard mutates monitors" keeps the highest-regression-risk work (the ported lease/confirm/mutate path) in its own plan with its own review surface, matching 19-RESEARCH.md's recommended build order.
Output: modified `ThemeApplier.cs`, `MainForm.Designer.cs`, `MainForm.cs`. `MonitorPanelForm` still exists and is still reachable from the tray menu — deliberately, so the old panel remains available as a side-by-side reference until Plan 04 retires it.
</objective>

<hard_constraints>
Load-bearing rules. Violating any one fails the phase even if the window looks right.

1. Subscribe to `Microsoft.Win32.SystemEvents.DisplaySettingsChanged` ONCE in `MainForm`'s constructor and NEVER unsubscribe on `Hide()`, `Show()`, `VisibleChanged`, or any visibility condition. `MainForm` is hidden-not-closed for most of its runtime; gating the subscription on visibility silently kills hotplug refresh during exactly the tray-resident state the app spends most of its life in (19-RESEARCH.md Pitfall 2). Do NOT copy `MonitorPanelForm`'s subscribe-in-ctor / unsubscribe-on-`FormClosed` pattern — that pattern is correct for a closable-and-reopenable form and wrong here. A `Dispose(bool disposing)` unsubscribe is permitted only as a real-process-exit backstop and must be commented as such.
2. Every new control — each `MonitorTile`, `btnIdentify`, the gear `btnSettings`, and `lblNoMonitors` — must be themed from BOTH `OnThemeChanged` AND `InitializeTrayState()`. A control themed in only one call site freezes at whatever theme Windows was in at startup while its neighbours keep flipping (19-RESEARCH.md Pitfall 1; this codebase already shipped this exact bug twice in Phase 12). `ThemeApplier` is deliberately not a recursive Controls-tree walk — do not turn it into one.
3. Tile numbering and tile order derive from ONE canonical list, sorted `OrderBy(m => m.DevicePath, StringComparer.Ordinal)`, stored in a single field. Plan 03's Identify handler consumes that same field. Never re-derive an independent order anywhere (19-RESEARCH.md Pitfall 6 / Assumption A1) — divergent numbering makes Identify point at the wrong tile.
4. No hardcoded pixel literals in the layout code path. Every position and size passes through a font-derived scale helper, because programmatic layout bypasses `AutoScaleMode.Font` entirely (19-RESEARCH.md Pitfall 5).
5. This plan does NOT mutate monitors. `ActivateMonitors`, `DeactivateMonitors`, `BeginExclusiveMonitorAccess`, and `MonitorConfirmDialog` must not appear in any code this plan writes — Plan 03 adds them.
6. Do NOT restyle `btnToggle`. MAIN-01 repositions it; the custom track+thumb switch is Phase 20's scope (THEME-08). It stays a plain `Button` with its existing `FlatStyle.Flat` + `ThemeApplier.ThemeButton` treatment and its existing dynamic `Switch to Rig Mode` / `Switch to Normal Mode` text.
7. Do NOT delete `MonitorPanelForm.cs`, `MonitorPanelForm.Designer.cs`, `trayMonitorsMenuItem`, `TrayMonitorsMenuItem_Click`, `OpenMonitorPanel()`, the `_monitorPanelForm` field, the `_monitorPanelFormFactory` field, or the constructor parameter in this plan. Plan 04 retires them, after the tile dashboard is proven (TILE-07 deletion order, 19-UI-SPEC.md Component Behavior Contract).
</hard_constraints>
