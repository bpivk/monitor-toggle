# Phase 8 — UI Design Contract

> Visual and interaction contract for Phase 8 (Tray Residency, Autostart & Toast Notification). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** Rig Toggle is a native WinForms desktop utility, not a web app. This project has no design-system tooling (no shadcn, no Tailwind, no component registry) — the template's web-oriented sections (spacing scale, color tokens, registry safety) are adapted below to their literal WinForms equivalents: absolute-position pixel layout, `SystemColors`/default control font, and "not applicable" for anything registry-specific. The governing principle for this phase is **match the existing `MainForm`/`SettingsForm` look exactly** — introduce zero new visual language.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — native WinForms controls only, OS-theme defaults (`SystemColors`), no design-system library applies |
| Preset | not applicable |
| Component library | `System.Windows.Forms` (BCL): `NotifyIcon`, `ContextMenuStrip`/`ToolStripMenuItem`, `CheckBox` — all already used or directly analogous to controls already in `SettingsForm`/`MainForm` |
| Icon library | none — two hand-authored `.ico` files (`normal.ico`, `rig.ico`), embedded as `EmbeddedResource` items per `08-RESEARCH.md` Pitfall 3 (no bitmap-to-icon conversion, no icon font) |
| Font | Default WinForms form font — never explicitly set anywhere in the existing codebase (`MainForm`/`SettingsForm` both leave `Font` unset and rely on `AutoScaleDimensions = (7F, 15F)` / `AutoScaleMode.Font`), which renders as **Segoe UI, 9pt** on all supported Windows versions. New controls added this phase (autostart checkbox) must **not** set an explicit `Font` — inherit from the form, exactly like `chkEnableDebugLogging` does today. |

## Spacing Scale

This app has no CSS-style spacing scale — layout is absolute `Location`/`Size` pixel values on two designer-generated forms. The table below documents the **actual conventions already in use** (verified by reading `SettingsForm.Designer.cs`/`MainForm.Designer.cs`), which every new control added this phase must match:

| Token | Value | Usage / Evidence |
|-------|-------|-------------------|
| Form-edge margin | 12px | `SettingsForm`'s group boxes all start at `x=12, y=12` — use this convention (not `MainForm`'s older 16px) since every new control this phase adds lands in `SettingsForm` or the tray, not `MainForm`'s fixed 320×200 client area |
| Content width (`SettingsForm`) | 396px | `ClientSize.Width (420) − 2×12px margin`; every full-width control (group boxes, `chkEnableDebugLogging`) uses `Width=396` — the new autostart checkbox must too |
| Vertical gap, same-group controls | 8px | `btnToggle` bottom (100) → `btnSettings` top (108) in `MainForm` |
| Vertical gap, checkbox-to-checkbox | 8px | Apply between `chkEnableDebugLogging` (bottom 524) and the new `chkStartWithWindows` |
| Checkbox row height (multi-line text) | 40px, `AutoSize=false` | `chkEnableDebugLogging`: `Size(396,40)` — its text wraps to two lines |
| Checkbox row height (single-line text) | 24px, `AutoSize=false` | New pattern for this phase — see "New `SettingsForm` Control" below; `chkStartWithWindows`'s text is short enough to need only one line |
| Tray icon canvas | 16×16 px logical, with 32×32 (and ideally 48×48) frames embedded in the same `.ico` | Windows System Tray's native rendering size; a multi-resolution `.ico` (not a single fixed bitmap) avoids blurry upscaling on HiDPI displays — required regardless of exact glyph art |

**Exceptions:** none.

### New `SettingsForm` Control Placement (prescriptive)

The new "Start with Windows" checkbox (`chkStartWithWindows`) is inserted directly below the existing `chkEnableDebugLogging`, pushing the Save/Discard buttons and the form's bottom edge down by the same amount. Recommended exact values (planner/executor may adjust by a few px to satisfy WinForms Designer snapping, but must preserve this order, the 8px gap convention, and full 396px width):

| Control | Location | Size |
|---------|----------|------|
| `chkEnableDebugLogging` (unchanged) | `(12, 484)` | `(396, 40)` |
| `chkStartWithWindows` (**new**) | `(12, 532)` | `(396, 24)` |
| `btnSaveSettings` (moves down) | `(180, 566)` | `(110, 32)` (unchanged size) |
| `btnDiscardChanges` (moves down) | `(298, 566)` | `(110, 32)` (unchanged size) |
| `SettingsForm.ClientSize` (grows) | — | `(420, 614)` (was `420, 582`) |

Checkbox text: `"Start with Windows"` — short enough for one line, unlike `chkEnableDebugLogging`'s wrapped two-line label; no tooltip needed (the label is self-explanatory, matching the plain, unadorned style of the existing checkbox).

## Typography

Only one text role exists anywhere in this app — there is no heading/display hierarchy in `MainForm` or `SettingsForm` today, and this phase introduces none.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / all form controls (labels, checkboxes, menu items) | 9pt Segoe UI (inherited default, never explicitly set) | Regular (400) — no bold used anywhere in either existing form | WinForms default (not explicitly set) |
| Tray tooltip (`NotifyIcon.Text`) / balloon title & body (`ShowBalloonTip`) | OS-rendered — drawn by the Windows shell (`Shell_NotifyIcon`), not by this app's WinForms font stack; **not stylable from app code** | OS default (the shell renders the balloon title in a bold weight; the app has no control over this) | OS default |

**Exception:** the tray tooltip and balloon notification's visual typography is entirely outside this app's control (Windows shell-rendered) — the design contract for those two surfaces is limited to *text content* (see Copywriting Contract), not font/size/weight.

## Color

No hardcoded color appears anywhere in the existing codebase — every control (`MainForm`, `SettingsForm`) uses WinForms/OS theme defaults (`SystemColors.Control`, `SystemColors.Window`, `SystemColors.ControlText`, etc.), which is exactly why the app already follows the user's Windows light/dark theme automatically with zero theming code. **This phase must not introduce the app's first hardcoded color** for any `SettingsForm`/`MainForm` control.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `SystemColors.Control` (OS theme default) | Form backgrounds — unchanged |
| Secondary (30%) | `SystemColors.Window` (OS theme default) | GroupBox/TextBox/DataGridView backgrounds — unchanged |
| Accent (10%) | none | No accent color exists anywhere in this app; buttons/checkboxes use default OS chrome. The new autostart checkbox follows suit — no custom color. |
| Destructive | none | No destructive-red styling anywhere in the app; the tray "Exit" item is a plain, unstyled menu entry (see Copywriting Contract — no confirmation, no warning color) |

Accent reserved for: nothing — this app deliberately has no accent color anywhere.

### Tray Icon Glyph Color (the one genuinely new visual asset this phase adds — D-01, Claude's Discretion)

Since no brand palette exists for this personal tool, the contract fixes the *requirement*, leaving exact glyph art to whoever produces the two `.ico` files:

| Icon state | Direction |
|------------|-----------|
| Normal-mode icon | A neutral, unremarkable monitor/display pictogram — should read as "default/idle," not warning-colored |
| Rig-mode icon | The **same base silhouette**, distinguished by either (a) a different accent color (e.g. amber/orange) or (b) a distinct glyph detail (e.g. a small steering-wheel/checkered-flag accent) |
| **Hard requirement** | The two icons must differ by **silhouette or shape detail**, not color alone — at 16×16px, a color-only difference is not reliably distinguishable (including for colorblind users), so color is a secondary signal at most, never the sole one. This directly satisfies TRAY-04 ("tray icon's appearance changes to reflect the current mode"). |

## Copywriting Contract

| Element | Copy |
|---------|------|
| Tray context menu — toggle item (dynamic, D-04) | `"Switch to Rig Mode"` / `"Switch to Normal Mode"` — sourced from the exact same string as `MainForm.btnToggle.Text` (via the shared mode-derivation logic), never a second hardcoded copy |
| Tray context menu — settings item | `"Settings"` |
| Tray context menu — exit item | `"Exit"` |
| Tray context menu order | Toggle item → `"Settings"` → separator → `"Exit"` (per `08-CONTEXT.md` Specific Ideas) |
| Tray tooltip (`NotifyIcon.Text`, D-01) | `"Rig Toggle — Normal Mode"` / `"Rig Toggle — Rig Mode"` |
| Toast title (`BalloonTipTitle`, D-09) | `"Switched to Rig Mode"` / `"Switched to Normal Mode"` (`ToggleResultFormatter.FormatModeTitle`) |
| Toast body, full success (`BalloonTipText`) | Same per-step checklist format as the GUI's existing `MessageBox`: one line per step, e.g. `"Monitor: OK"` / `"Audio: OK"` / `"App: OK"` (`ToggleResultFormatter.FormatChecklist`) |
| Toast body, partial failure (`BalloonTipText`) | Same checklist with `"FAILED (<reason>)"` per failed step — **defensively truncate** the combined body to stay under ~250 chars (see `08-RESEARCH.md` Pitfall 4: `ShowBalloonTip` silently truncates past 255 chars with no ellipsis) so a verbose exception `Reason` never gets cut off mid-word with no indication; append `"…"` when truncating |
| Toast icon (`BalloonTipIcon`) | `ToolTipIcon.Info` on full success, `ToolTipIcon.Warning` on partial failure — mirrors the GUI's existing `MessageBoxIcon.Information`/`MessageBoxIcon.Warning` split exactly (D-09: "matching the GUI's existing partial-failure detail") |
| `SettingsForm` checkbox — autostart (D-05) | `"Start with Windows"` — terse, no trailing parenthetical, matching `chkEnableDebugLogging`'s own plain labeling style (that checkbox's parenthetical `"(writes to %LOCALAPPDATA%\RigToggle\debug.log)"` is describing a side-effect path, which the autostart checkbox has no equivalent of — no parenthetical needed) |
| Empty/first-run state | Not applicable — this phase adds no list/collection view. The closest analog is the tray icon's very-first-paint state: it must show the *correct current mode* immediately at process start (constructor-time initialization, not `OnLoad` — see Pitfall 6), never a blank/default placeholder icon while waiting for the first toggle |
| Error state — autostart registry write fails | Follow the existing `SettingsForm` inline-error convention (`errApp`/`lblAppWarning` pattern) rather than a `MessageBox`: surface `"Could not enable Start with Windows: <reason>"` as an inline warning near the checkbox, and **revert the checkbox to its prior checked state** so the UI never claims a success that didn't happen |
| Destructive confirmation — tray "Exit" | **None.** Deliberately no confirmation dialog, matching D-04's literal "performs a real `Application.Exit()`." Exiting never discards unsaved state — this app has no unsaved-state concept (every Settings change is written on Save; current mode is always persisted to disk on every toggle) |
| Destructive confirmation — unchecking "Start with Windows" | **None.** A plain, instantly-reversible checkbox toggle — no confirmation warranted, consistent with `chkEnableDebugLogging` having none either |
