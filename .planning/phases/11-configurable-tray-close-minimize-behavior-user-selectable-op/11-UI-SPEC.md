# Phase 11 — UI Design Contract

> Visual and interaction contract for Phase 11 (Configurable Tray Close/Minimize Behavior). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** Rig Toggle is a native WinForms desktop utility, not a web app. This project has no design-system tooling (no shadcn, no Tailwind, no component registry) — the template's web-oriented sections (spacing scale, color tokens, registry safety) are adapted below to their literal WinForms equivalents: absolute-position pixel layout, `SystemColors`/default control font, and "not applicable" for anything registry-specific. The governing principle for this phase is the same one Phases 8 and 9 used: **match the existing `SettingsForm`/`MainForm` look exactly** — introduce zero new visual language. This phase adds no new control *type* (two more `CheckBox` instances, identical pattern to `chkStartWithWindows`) — its real design surface is (a) exact layout/placement of those two checkboxes relative to the existing tray-behavior checkbox (D-07, left to this UI-SPEC), and (b) the behavioral contract for the tray icon's derived visibility (D-08–D-11), which has no dedicated control of its own but must be specified precisely so planner/executor implement one consistent rule.

## Spacing Scale

This app has no CSS-style spacing scale — layout is absolute `Location`/`Size` pixel values on designer-generated forms. The table documents the **actual conventions already in use** (verified by reading the current `SettingsForm.Designer.cs`, which already reflects Phase 8's autostart checkbox and Phase 9's hotkey-capture row), which the two new controls this phase adds must match:

| Token | Value | Usage / Evidence |
|-------|-------|-------------------|
| Form-edge margin | 12px | Every `SettingsForm` group box and loose control starts at `x=12` |
| Content width (`SettingsForm`) | 396px | `ClientSize.Width (420) − 2×12px margin`; every full-width control (`chkStartWithWindows`, `lblAutostartWarning`, `chkEnableDebugLogging`) uses `Width=396` — the two new checkboxes must too |
| Vertical gap, checkbox-to-checkbox (or checkbox-to-adjacent-control) | 8px | Existing precedent: `lblHotkeyWarning` bottom (592) → `chkStartWithWindows` top (600) is exactly 8px in the current file |
| Checkbox row height (single-line text) | 24px, `AutoSize=false` | `chkStartWithWindows`: `Size(396,24)` — both new checkboxes' text is short enough to fit one line at this width, same as `chkStartWithWindows` |
| Checkbox-to-its-own-warning-label gap | 0px (tight pair) | `chkStartWithWindows` (ends y=624 in its current position) → `lblAutostartWarning` (starts y=624) — no gap, they read as one visually-paired unit. **Not applicable to this phase's two new checkboxes** — neither has a runtime failure path, so neither gets a warning label (see Copywriting Contract) |

**Exceptions:** none.

### D-07 Resolution: New `SettingsForm` Control Placement (prescriptive)

D-07 locks the grouping intent ("same section as `chkStartWithWindows`, a shared tray-behavior grouping") but leaves exact layout to this UI-SPEC. Resolution: **no new `GroupBox` is introduced.** Wrapping these three checkboxes in a formal titled `GroupBox` (matching `grpMonitor`/`grpAudioDevices`/`grpAppPath`'s style) would mean relocating the existing, already-shipped `chkStartWithWindows`/`lblAutostartWarning`/`errAutostart` wiring into a new parent container — a larger, riskier diff than this phase's scope warrants, and it would contradict the "introduce zero new visual language" principle every prior tray-behavior UI-SPEC in this project has followed. Instead, the "shared grouping" is expressed the same way `chkEnableDebugLogging` + `chkStartWithWindows` already read as a loosely-related cluster today: **tight, contiguous vertical stacking with the established 8px gap, immediately above `chkStartWithWindows`**, with no blank/oversized gap separating them. This directly satisfies D-07 ("not a new separate section") without inventing a new container type.

The two new checkboxes are inserted directly below the existing `lblHotkeyWarning` (Phase 9's hotkey-capture warning label) and directly above `chkStartWithWindows`, pushing `chkStartWithWindows`, `lblAutostartWarning`, both buttons, and the form's bottom edge down by 64px total. Order (top to bottom): **Close-to-tray checkbox (D-03) → Minimize-to-tray checkbox (D-06) → existing Start-with-Windows checkbox** — the two new window-behavior preferences read together as one cluster, with the pre-existing autostart preference immediately following as a closely related (but conceptually distinct) fourth tray-adjacent setting, exactly mirroring how Phase 9 inserted its new hotkey row directly above `chkStartWithWindows` without a container.

Planner/executor may adjust by a few px to satisfy WinForms Designer snapping, but must preserve this order, the 8px gap convention, and the 12px left margin / 396px width:

| Control | Location | Size | Notes |
|---------|----------|------|-------|
| `lblHotkeyWarning` (unchanged, Phase 9) | `(12, 556)` | `(396, 36)` | ends at y=592 |
| `chkCloseMinimizesToTray` (**new**) | `(12, 600)` | `(396, 24)` | Text: `"Closing the window (X) minimizes to tray"` — `AppSettings.CloseMinimizesToTray` (D-01/D-03) |
| `chkMinimizeToTray` (**new**) | `(12, 632)` | `(396, 24)` | Text: `"Minimizing the window also sends it to tray"` — `AppSettings.MinimizeToTray` (D-04/D-06) |
| `chkStartWithWindows` (moves down) | `(12, 664)` | `(396, 24)` | was `(12, 600)` |
| `lblAutostartWarning` (moves down) | `(12, 688)` | `(396, 20)` | was `(12, 624)` — 0px gap from `chkStartWithWindows` preserved (tight pair, unchanged relationship) |
| `btnSaveSettings` (moves down) | `(180, 720)` | `(110, 32)` | was `(180, 656)` |
| `btnDiscardChanges` (moves down) | `(298, 720)` | `(110, 32)` | was `(298, 656)` |
| `SettingsForm.ClientSize` (grows) | — | `(420, 768)` | was `(420, 704)` |

Neither new checkbox gets a dedicated `ErrorProvider`/warning label. Unlike autostart (registry write can fail) or the hotkey (`RegisterHotKey` can fail), both `CloseMinimizesToTray` and `MinimizeToTray` are pure in-memory `AppSettings` boolean writes with no I/O and no failure mode — there is nothing to surface inline. Do not add `errCloseMinimize`/`errMinimizeToTray` or equivalent; that would be dead code with no failure path to ever populate it.

## Interaction States — Derived Tray Icon Visibility (D-08–D-11)

This phase's real interaction-design surface is not the two checkboxes themselves (they are plain, stateless, always-enabled toggles with no idle/hover/disabled variants beyond default WinForms `CheckBox` behavior) but the **derived, reactive rule governing `notifyIcon.Visible`** that both checkboxes now jointly control. This is not optional/discretionary — it must be implemented exactly as follows so the tray icon's presence never lags or contradicts the two settings:

| Condition | `notifyIcon.Visible` | Consequence |
|-----------|----------------------|--------------|
| `CloseMinimizesToTray == true` OR `MinimizeToTray == true` (either or both) | `true` | Tray icon shown; TRAY-03 (context menu), TRAY-04 (mode icon), TRAY-05 (left-click restore) all reachable as today |
| `CloseMinimizesToTray == false` AND `MinimizeToTray == false` (both off) | `false` | Tray icon fully absent (D-09) — app behaves like a fully normal desktop app with no tray presence. This is the **default state on first upgrade** (D-02): a user who has not yet opened Settings after this phase ships will see the tray icon disappear entirely, since Phase 8's unconditional close-to-tray default no longer applies. |

**Recompute points (both required, not just one):**
1. **Startup** — inside/alongside the existing `InitializeTrayState()` (unconditionally called before either `Application.Run` branch, per Phase 8's D-... precedent for "always correct on first paint"), so a `--tray` hidden autostart launch with both settings off does not leave a ghost-visible tray icon, and a launch with either setting on does not start with a missing one.
2. **Settings-Save** — applied live the moment Settings closes with changes saved, via a small `MainForm` helper (e.g. `ApplyTrayVisibility()`) called from the same place `RefreshUi()` is already called after the Settings dialog closes. The tray icon must appear/disappear **immediately**, never only after an app restart (explicit D-08 requirement).

**The `NotifyIcon` component itself is always instantiated** at startup regardless of these settings (D-11) — only `.Visible` is conditional. Do not guard `notifyIcon.Icon =` / `notifyIcon.Text =` / `ShowBalloonTip(...)` calls elsewhere in the codebase behind a null-check or a "is tray enabled" flag; they must keep running exactly as today even while `Visible == false`. The one accepted, already-decided visual consequence: `ShowBalloonTip` silently renders nothing when `Visible == false` (a WinForms/Shell_NotifyIcon constraint, not a bug), so hotkey-registration-failure toasts (Phase 9, D-06) and toggle-result toasts (NOTIF-01) will not visually appear whenever both settings are off. **Do not add compensating UI for this** — no "flash the icon briefly to show a toast," no substitute `MessageBox`, no inline warning near the checkboxes explaining the tradeoff. D-11 explicitly chose this as an accepted consequence during discussion; re-introducing a workaround here would contradict a locked decision.

**Existing `notifyIcon.Visible = false` shutdown guard (`MainForm_FormClosing`, non-`UserClosing` reasons, "T-08-GHOST" ghost-icon prevention):** unaffected by this phase — it remains a defensive belt-and-suspenders call on process exit regardless of the derived-visibility rule above, since setting `Visible = false` on an already-`false` icon is a harmless no-op.

**Minimize interception mechanism (D-04, implementation left to planner per CONTEXT.md):** whatever `Resize`/`SizeChanged` mechanism is chosen, it must call through the **same shared "hide to tray" helper** the existing `MainForm_FormClosing` handler's `Hide()` call uses (per CONTEXT.md's Reusable Assets note) — do not duplicate the `Hide()` line in two places. This is a code-structure constraint, not a new visual state: the window's hidden appearance while minimized-to-tray is pixel-identical to the existing closed-to-tray hidden state (it is literally the same `Hide()` call), so no new "minimized" visual variant needs to be designed.

## Copywriting Contract

| Element | Copy |
|---------|------|
| `chkCloseMinimizesToTray` label (D-03, locked wording from `11-CONTEXT.md`) | `"Closing the window (X) minimizes to tray"` — unchecked reads as "exit the app" by omission, matching the terse, unadorned style of `chkStartWithWindows`/`chkEnableDebugLogging` (no parenthetical explaining the unchecked state — the checkbox's own checked/unchecked binary is self-explanatory, same convention as every other `SettingsForm` checkbox) |
| `chkMinimizeToTray` label (D-06, locked wording from `11-CONTEXT.md`) | `"Minimizing the window also sends it to tray"` — the word "also" deliberately implies a relationship to the checkbox above it (visually adjacent, per the D-07 layout resolution), without needing an explicit "(requires the option above)" — no such requirement exists (D-08's OR logic means either can be on independently) |
| Primary CTA | `"Save Settings"` — unchanged existing button; this phase adds no new action button. Both new fields are written to `AppSettings` as part of the existing Save flow, exactly like `EnableDebugLogging` already is (a direct, unconditional field write — no validation, no failure path) |
| Empty/first-run state | Not applicable — this phase adds no list/collection view. The closest analog is the **default-both-off tray-icon-absent state** (D-02/D-05's defaults), which is covered under Interaction States above, not a copy element — there is no "no tray icon configured yet" placeholder text anywhere in the UI, because a fully normal desktop app with no tray icon is not treated as an error/empty state, just the expected default |
| Error state | **None for either new checkbox.** Neither field has a runtime failure path (see Spacing Scale note on omitting `ErrorProvider`s) — do not invent one |
| Destructive confirmation | **None for either checkbox.** Both are instantly reversible preference edits, consistent with every other `SettingsForm` checkbox (`chkEnableDebugLogging`, `chkStartWithWindows`) having no confirmation dialog. Per D-10, the "autostart + X-set-to-exit" combination and per D-11 the "both off, toasts go silent" combination are both explicitly accepted tradeoffs with **no Settings-time warning copy** — do not add inline text near either checkbox warning about these interactions |
