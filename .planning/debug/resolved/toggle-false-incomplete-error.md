## Symptoms

expected: Toggling to Rig mode succeeds without error when a monitor that's manually disabled beforehand is also supposed to be disabled in Rig mode's own config — no actual state change is needed for that monitor, so it should not be treated as a failure.
actual: The toggle reports "toggle did not fully complete," citing the already-disabled monitor as "not currently active." The check appears to require every monitor involved in the toggle to end up active, rather than only the monitors that are supposed to be active in the target mode.
errors: "toggle did not fully complete" (user-paraphrased; exact string not yet confirmed verbatim — needs the literal error text/dialog wording from the user or from `ToggleResultFormatter`/`ToggleService` source).

## Prior Context

- The project's toggle-step outcome model distinguishes `Skipped`/`NotAttempted`/`Failed` explicitly (v2.0 Phase 15 decision, `.planning/PROJECT.md`: "Distinct `Skipped` toggle-step outcome, never conflated with `NotAttempted` or `Failed`... a configured-but-broken target must still fail loudly"). This bug looks like a monitor-mutation postcondition check applying a blanket "must be active" assertion to a monitor whose *target* state for this toggle direction is actually "disabled" — i.e. the check isn't reading the per-monitor target state for the mode being toggled to before deciding pass/fail.
- DISPLAY-12's shared "at least one monitor must remain enabled" safety guard (v2.0 Phase 17, enforced identically across Rig toggle, Normal toggle, and tile clicks) is a different check and should NOT be the source of this — the report describes a single specific monitor being flagged as wrongly required active, not an all-monitors-disabled safety rejection. Worth explicitly ruling out DISPLAY-12's guard as the cause vs. a separate post-toggle verification step.
- `ToggleOrchestrator`/`ToggleService` sequence monitor mutation steps and verify outcomes (v1.1 Phase 7 extraction, v2.0 Phase 16 mode-store redesign). The bug is most likely in whatever step verifies "did the monitor set apply correctly" after a CCD `ApplyPathInfos` call — probably comparing against a hardcoded "should be active" expectation instead of the actual per-monitor target from the mode's configured monitor set.
- This is a Windows-only bug; this sandbox has no Windows runtime — root-cause confirmation via static code reading is possible, but live behavioral confirmation and fix verification are gated on the user testing on the actual rig.

## Resolution

root_cause: "WindowsMonitorController.DeactivateMonitors()'s pre-mutation 'missing' guard (src/RigToggle.Windows/WindowsMonitorController.cs, ~L296-306) determines whether a requested-to-disable device path is an error using the wrong oracle: it checks only whether the path is currently ACTIVE (via GetActivePaths()), not whether Windows detects the device AT ALL (via GetAllPaths()+IsAvailable, the oracle ActivateMonitors already uses for the equivalent check). A monitor that was manually disabled before the toggle — and is also in the target mode's disable-set, meaning its correct end-state is already met — is indistinguishable, under this guard, from a monitor that is genuinely unplugged/undetected. Both throw the same 'Configured monitor(s) not currently active' error, which ToggleService's Monitor step surfaces as a Failed step, producing the 'toggle did not fully complete' dialog even though no real state change was needed or missed for that monitor."
fix: "In WindowsMonitorController.DeactivateMonitors(): (1) the missing-guard's oracle changed from 'is every requested path currently active' (GetActivePaths()-only) to 'is every requested path detected at all' (GetAllPaths()+IsAvailable — mirrors ActivateMonitors' own established missing-target pattern), extracted as a new pure seam ComputeUndetectedDevicePaths(requested, available) for testability; error message updated from 'not currently active' to 'not detected' to match the corrected semantics. (2) Added an early-return skip-optimization (targets.Length == 0 -> return) mirroring ActivateMonitors' existing Pitfall-3 optimization: when every requested device path is already inactive, nothing needs deactivating, so the method returns without calling ApplyPathInfos at all rather than needlessly reapplying the unchanged current topology. No change to the method's existing behavior for any device path that IS currently active (targets/survivors/primary-shift/ApplyPathInfos/verify-and-throw logic is untouched)."
