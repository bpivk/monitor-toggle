## Symptoms

**Expected behavior:** Toggling from Rig Mode back to Normal Mode should restore the disable-set monitor (VG248) to its exact prior state AND turn the enable-set monitor (Dell U2415) back off (D-02 teardown) — all three steps (Monitor, Audio, App) succeed.

**Actual behavior:** Monitor step reports FAILED with `Configured monitor(s) not currently active: \\?\DISPLAY#DELA0B8#7&16485deb&0&UID516#{e6f07b5f-ee97-4a90-b076-33f57bf4eaa7}`. Audio: OK. App: not attempted. The user's screen visually looked correct after the toggle (they initially reported it as passing), and only noticed the background error afterward.

**Error messages:** `Monitor: FAILED (Configured monitor(s) not currently active: \\?\DISPLAY#DELA0B8#7&16485deb&0&UID516#{e6f07b5f-ee97-4a90-b076-33f57bf4eaa7})` / `Audio: OK` / `App: not attempted`.

**Timeline:** First occurrence — this is the first time the combined disable-set + enable-set scenario (Phase 6's DISPLAY-05 "enable a normally-OS-disabled monitor" feature) has been rig-tested end-to-end, including the toggle-back direction. Toggle-to-rig-mode with the same configuration worked cleanly (no errors) immediately before this failure.

**Reproduction:**
1. Configure Settings: disable-set = VG248 (previously GDI-primary), enable-set = Dell U2415.
2. Switch to Rig Mode — succeeds cleanly (VG248 goes off, Dell U2415 comes/stays on, no errors).
3. Switch back to Normal Mode — Monitor step fails with the error above.

## Prior Investigation (via source read only — no dotnet SDK in this dev session, repro only reachable on the user's Windows rig)

Traced the exact call path in `ToggleService.ToggleToNormalMode()` (`src/RigToggle.Core/ToggleService.cs`):
```csharp
_monitorController.Restore(snapshot.Monitor);
_monitorController.DeactivateMonitors((settings.MonitorsToEnable ?? new List<string>()).ToHashSet());
```
Both calls are wrapped in one try/catch; the exception text confirmed (via exact string match against `DeactivateMonitors`'s own error text in `src/RigToggle.Windows/WindowsMonitorController.cs`) originates from `DeactivateMonitors`'s pre-mutation "not currently active" guard, NOT from `Restore()` (whose own error messages have different text: "Monitor restore did not reproduce the exact prior configuration...", "Cannot restore '...' — no longer detected.", etc. — none match). This confirms `Restore()` returned successfully (no throw) immediately before `DeactivateMonitors` threw.

**Candidate root cause (unconfirmed):** `Restore()`'s verify-and-throw — in BOTH its in-process fast path (lines ~379-401) and its crash-recovery fallback path (lines ~471-492 verify section) — only checks `previousState.TargetDevicePath`'s position/primary match, plus a general bounding-box overlap check across all currently-active paths. It never explicitly verifies that *every* device in `previousState.Paths` (which includes Dell, part of the full-topology snapshot captured by `CaptureState()`) is actually active afterward. This means `Restore()` can report success even if Dell silently failed to end up active as a side effect of the `ApplyPathInfos(_originalPathsCache, ...)` mutation — and the failure only surfaces moments later via the unrelated `DeactivateMonitors` call, with a confusing, mis-attributed error message.

**Alternative candidate (also unconfirmed):** A CCD settling/timing race — Windows might not have fully "settled" Dell's active state by the time `DeactivateMonitors`'s own fresh `GetActivePaths()` re-query runs, moments after `Restore()`'s mutation.

Both candidates are plausible from source alone; live rig evidence is needed to distinguish them, and either way `Restore()`'s verify is under-scoped relative to Phase 6's N-generalization (it was only extended with an overlap check, not per-device active-state verification, per `06-RESEARCH.md`/`06-06-SUMMARY.md`).

## Resolution

root_cause: "Two compounding defects, discovered across two investigation rounds. Round 1: Restore()'s in-process fast-path cache-acceptance guard originally required `cachedDevicePaths.SetEquals(expectedDevicePaths)` — an exact match between the pre-disable cache's device-path set and previousState.Paths. Since Phase 6/DISPLAY-05 introduced ActivateMonitors() running before DeactivateMonitors() within the same 'Monitor' step, the cache legitimately also contains any enable-set monitor (already activated moments earlier) — a device that, by construction, is never part of previousState.Paths. This made SetEquals fail unconditionally whenever an enable-set was configured.
