## moza-foreground-focus — Moza Companion window not foregrounded / wrong window focused / app won't relaunch after full close
- **Date:** 2026-07-26
- **Error patterns:** SetForegroundWindow, MainWindowHandle, wrong window focused, minimized window not appearing, foreground lock restriction, window does not come to foreground, tray-hidden window, app does not relaunch after close, IsRunning stays true, headless helper process, close button inert, X button no-op, WM_SYSCOMMAND, system menu grayed
- **Root cause:** Two distinct, sequentially-discovered root causes. (1) `Process.MainWindowHandle` is a first-match-wins heuristic — for a process owning multiple top-level windows (e.g. a main dashboard plus a secondary utility window), it can return the wrong window, or return Zero for a legitimately hidden/tray-only window, causing RigToggle's foreground/focus calls to act on nothing or on the wrong HWND. (2) The "already running" branch had no fallback to relaunch — once a same-named headless helper process kept `IsRunning()` true after the real UI instance fully exited, the toggle could never bring up a window again.
- **Fix:** (1) Replaced trust in `Process.MainWindowHandle` with `FindBestMainWindow`: enumerate all owner-less top-level windows for the resolved PID via `EnumWindows`/`GetWindowThreadProcessId`, score each by caption presence + restored window area (via `GetWindowPlacement`'s `rcNormalPosition`, not `GetWindowRect`, which reports a degenerate rect for minimized windows), and select the largest titled candidate. Applied to both the already-running focus path and the minimize-on-toggle-back path. (2) Added a bounded (~3s) poll/recheck loop in the already-running branch before falling back to a fresh `Process.Start` + poll (via a shared `LaunchFreshAndFocus` helper) instead of silently no-op'ing forever when no window is found across all matched processes.
- **Files changed:** src/RigToggle.Windows/WindowsAppController.cs, src/RigToggle.Windows/NativeMethods.cs, src/RigToggle.App/Program.cs (debug.log wiring)
- **Known limitation — H9 fully resolved, rig-verified 2026-07-26, both directions:** Moza Companion's own close (X) button / Alt+F4 / taskbar "Close window" became inert specifically on windows RigToggle brought to foreground (minimize unaffected). Investigated across 10 rounds; every passively-observable Win32 mechanism a separate process can query (WS_DISABLED, system-menu MF_GRAYED via `GetMenuState`, FormClosing-visible-revert) was tested and eliminated. Most likely cause: Moza intercepting close input at the message level (WM_NCHITTEST/WM_NCLBUTTONDOWN/WM_SYSCOMMAND) inside its own window procedure — outside what a separate Win32 utility can observe or fix without hooking Moza's message loop.
  - **(a) Toggle-TO-rig-mode direction — fixed:** follow-up quick task `.planning/quick/260726-idx-redesign-companion-app-launch-focus-mech` redesigned the launch path to an app-agnostic, relaunch-based activation (unconditional `Process.Start` with `UseShellExecute = true`, relying on the target's own single-instance self-activation) that never enumerates or foregrounds the target's window at all — since the trigger for this limitation was specifically "windows RigToggle brought to foreground," removing all foreground/focus calls from the launch path removes the trigger on this path.
  - **(b) Toggle-TO-normal-mode (toggle-back) direction — separate bug, now fixed:** follow-up quick task `.planning/quick/260726-ixu-add-targeted-diagnostic-logging-to-windo` added pre/post `IsWindowVisible`/`IsIconic`/`ShowWindow`-return diagnostic logging around `MinimizeIfRunning`'s minimize call and captured rig evidence that it was doing an unconditional raw Win32 `ShowWindow(SW_MINIMIZE)` that, when the target window was already hidden/tray-only, forced it back to a visible minimized state (pre `IsWindowVisible=False` → post `True`) — retriggering this same close-inert symptom on toggle-back. Quick task `.planning/quick/260726-j9y-fix-minimizeifrunning-to-skip-showwindow` fixed this by gating the `ShowWindow` call on `preVisible`, skipping it entirely when the window is already hidden.
  - **(c) Current overall status — fully resolved, rig-verified 2026-07-26:** the user rig-tested both directions in the same session (debug.log 16:05–16:06) and confirmed "Yes. This works now." Evidence: 16:05:57 toggle-back — `MinimizeIfRunning: pre-minimize hWnd=0x2811EC, IsWindowVisible=False, IsIconic=False` followed by `skipped minimize hWnd=0x2811EC — window already hidden (IsWindowVisible=false)` (fixed skip path fires correctly); 16:06:12 normal minimize — `pre-minimize ... IsWindowVisible=True, IsIconic=False` followed by `post-minimize ... IsWindowVisible=True, IsIconic=True, ShowWindowReturned=True` (unchanged normal minimize path still works). H9 is closed; no further rig-test action needed. If a similar symptom recurs in the future, do not re-chase the same read-only diagnostics; a further fix would require message-loop-level interception in the target process, which is out of scope for a standalone utility.

## ccd-topology-restore-findings — WindowsDisplayAPI CCD topology restore — rig-discovered constraints (code removed Phase 18, knowledge retained)
- **Date:** 2026-08-09
- **Error patterns:** Not a bug report — this is a knowledge-preservation record extracted from doc comments before the code they describe was deleted. Search terms for future reference: `PathTargetInfo.OutputTechnology`, `<OutputTechnology>k__BackingField`, `SDC_ALLOW_CHANGES`, source-ID renumbering, `PathDisplaySource` collision, `GetAllPaths`, `DevicePath`, `WindowsMonitorController.Restore`, `RestoreViaReconstruction`, `CopyOutputTechnology`, `AssignSource`.
- **Root cause:** N/A (not a bug). `WindowsMonitorController`'s `Restore`/`RestoreViaReconstruction`/`CopyOutputTechnology`/`AssignSource` doc comments were the only written record of five hard-won WindowsDisplayAPI CCD findings, each obtained by live rig testing across multiple rig rounds. CLEANUP-01 (Phase 18) requires this rig-specific knowledge to be reviewed and preserved elsewhere before the dead snapshot-restore code that encoded it is deleted — Phase 16 already replaced snapshot-restore with explicit Normal-mode target application, making the restore path unreachable in production.
- **Fix:** Five rig-discovered CCD constraints, preserved verbatim enough to act on without the deleted code:
  1. **`OutputTechnology` has no public constructor parameter.** In WindowsDisplayAPI 1.3.0.13, `PathTargetInfo.OutputTechnology` cannot be set via any public constructor — every manually constructed `PathTargetInfo` instance defaults to `DisplayConfigVideoOutputTechnology.Other` regardless of the target's real connector type. The only correction that does not require the library's internal constructor overload is patching the compiler-generated backing field directly via reflection: field name `<OutputTechnology>k__BackingField`, obtained via `typeof(PathTargetInfo).GetField("<OutputTechnology>k__BackingField", BindingFlags.NonPublic | BindingFlags.Instance)`. That exact field-name string is the fragile part — a future WindowsDisplayAPI upgrade could rename it, so any reimplementation should throw loudly (not silently no-op) if the field is ever not found.
  2. **Source-collision assignment rule.** When manually assigning `PathDisplaySource` values across a batch of targets being applied together: an already-active target must keep its own current `PathDisplaySource` (never reassign it). An inactive target must be given the first source not already claimed by another target in the same apply batch — walk the set of all available sources, skip any already recorded as used, and record the chosen one as used before moving to the next target. If every source is already claimed, throw rather than silently reusing a source — two targets sharing one `PathDisplaySource` causes the apply to silently mis-land (one target ends up inactive with no error).
  3. **Source-ID renumbering across a mutation boundary.** After `DeactivateMonitors` reduces the active topology (removing one or more targets), the CCD driver commonly compacts the surviving monitor's native source index downward, freeing the disabled target's former source. Consequently, any `PathInfo[]` array captured *before* that reduction holds a `PathDisplaySource` assignment for the survivor that is stale by the time of a later replay — the array looks valid but no longer reflects the driver's current source numbering.
  4. **`SetDisplayConfig` with `SDC_ALLOW_CHANGES` silently accepts a stale path array.** Calling `PathInfo.ApplyPathInfos(..., allowChanges: true)` (which sets `SDC_ALLOW_CHANGES`) with a `PathInfo[]` containing a stale `PathDisplaySource` (per finding 3) does **not** return an error — but it does not reliably keep the mis-sourced target active either. This is why replaying a cached pre-mutation `PathInfo[]` is unsafe in the general case, and why the in-process fast-path cache-acceptance check was gated back to a strict `SetEquals` comparison against the expected device-path set (the simple case where no monitor was newly enabled alongside the disable-set) rather than the broader `IsSupersetOf`, which had been rig-disproven for the case where an intervening mutation could have renumbered a surviving source.
  5. **Reconstruction rules, rig-proven across three failed manual-reconstruction attempts before this shape was found stable:** (a) always re-resolve target identity live via `PathInfo.GetAllPaths()` matched on the target's stable, stored `DevicePath` — never on a persisted, session-scoped LUID, which does not survive across process/driver-state boundaries; (b) take mode/signal values (position, resolution, pixel format, rotation, scaling, frequency, scan-line ordering) from the stored snapshot taken while the path was active — never from an inactive live path's own `TargetsInfo`, because Microsoft's own CCD documentation states inactive-path mode/signal info is "set to default values," not real data; (c) never use the WinForms screen-enumeration API (`Screen.AllScreens`) as the verification oracle for whether a CCD change took effect (D-04) — only a fresh `PathInfo.GetActivePaths()`/`GetAllPaths()` re-query is trustworthy; (d) never attempt automatic rollback on verification failure (D-05) — surface the mismatch as a thrown exception and let the caller decide, rather than trying to auto-correct CCD state with more mutation calls.
- **Files changed:** `src/RigToggle.Windows/WindowsMonitorController.cs` — the code these findings came from (`Restore`, `RestoreViaReconstruction`, `CopyOutputTechnology`, `AssignSource`, and the `_originalPathsCache` field) was deleted in Phase 18 (CLEANUP-01) because Phase 16 replaced snapshot-restore with explicit Normal-mode target application, making the restore path dead/unreachable in production. This knowledge-base entry, not the source file, is now the durable record of findings 1-5. If a future phase ever needs to reconstruct CCD topology from a snapshot again (e.g. reintroducing a restore-style feature), findings 1-5 above are the starting point — each was obtained by live rig testing on real DisplayPort/AMD hardware, not from Microsoft's public documentation, which is largely silent on these specific behaviors.

## monitor-enable-affects-other — Enabling one disabled monitor via the tile dashboard also reactivated another still-disabled monitor (3-monitor rig)
- **Date:** 2026-08-19
- **Error patterns:** tile click enables wrong monitor, extra monitor reactivated, both disabled monitors turn on, ApplyTopology Extend whole-topology side effect, single monitor enable reactivates unrelated monitor, 3-monitor rig regression, DISPLAY-05, ActivateMonitors, PathInfo.ApplyTopology(Extend)
- **Root cause(s):** `WindowsMonitorController.ActivateMonitors(devicePaths)` reactivates a single OS-disabled monitor via `PathInfo.ApplyTopology(DisplayConfigTopologyId.Extend, allowPersistence: false)` — a whole-topology CCD operation that restores the OS's *entire* last-known extend layout from the CCD persistence database, not one scoped to the caller's requested device path(s) (WindowsDisplayAPI's `PathInfo` has no per-target Extend overload). With only one disabled monitor (pre-upgrade 2-monitor rig) this coincidentally only ever reactivated the requested monitor; with >=2 simultaneously-disabled-but-available monitors (post-upgrade 3-monitor rig), Extend reactivated ALL of them, not just the one selected via the tile dashboard.
- **Fix:** Capture the active device-path set immediately before and immediately after the `ApplyTopology(Extend)` call inside `ActivateMonitors`; compute which device paths became active that were neither previously active nor part of the caller's requested set (`ComputeUnexpectedlyActivated`, a pure extracted seam); turn any such unexpectedly-activated paths back off via the already rig-proven `DeactivateMonitors` CCD-removal path before `ActivateMonitors`' own verify-and-throw runs. No change to the Extend call itself or to the previously-abandoned manual `PathTargetInfo`/mode reconstruction path (see `ccd-topology-restore-findings` above — that path is proven unsafe and must not be reintroduced).
- **Files changed:** src/RigToggle.Windows/WindowsMonitorController.cs, src/RigToggle.Windows.Tests/WindowsMonitorControllerTests.cs
- **Why not caught:** No gate existed for this class. `ActivateMonitors`/`DeactivateMonitors` were explicitly excluded from unit testing (class doc comment: they call live CCD APIs — `GetActivePaths`/`GetAllPaths`/`ApplyPathInfos`/`ApplyTopology` — with no injectable seam, "verified only via live rig testing"). Separately, the app's own full-toggle flow (`ToggleService.ToggleToRigMode`/`ToggleToNormalMode`) always calls `DeactivateMonitors(disableSet)` immediately after `ActivateMonitors(enableSet)` in the same step, which incidentally turned any over-activated monitor back off — masking the defect on the primary QA path (the Rig/Normal toggle buttons). Only the tile dashboard's single-monitor action (no compensating `DeactivateMonitors` call) exposed it, and only once the rig had >=2 simultaneously-disabled monitors to reveal Extend's whole-topology behavior (the 2->3 monitor upgrade).
- **Recurrence guard:** Regression tests at `src/RigToggle.Windows.Tests/WindowsMonitorControllerTests.cs` covering the pure `ComputeUnexpectedlyActivated` seam: `ComputeUnexpectedlyActivated_RigRegressionScenario_ExtendReactivatesOtherDisabledMonitor_FlagsIt` (reproduces the exact reported 3-monitor scenario), `ComputeUnexpectedlyActivated_ExtendOnlyActivatesRequestedMonitor_ReturnsEmpty` (2-monitor / well-behaved case), `ComputeUnexpectedlyActivated_AlreadyActiveBeforeExtend_NotFlaggedEvenThoughUnrequested`, and `ComputeUnexpectedlyActivated_NoNewActivations_ReturnsEmpty`. Plus this knowledge-base entry itself, so a future Phase-0 recall surfaces "Extend is whole-topology, not scoped to the requested device path(s)" before re-deriving it from scratch for any future N-monitor CCD work (e.g. if `ActivateMonitors` is ever refactored, or if a similar whole-topology hazard is suspected elsewhere in this file).
- **Superseded 2026-08-22 by `monitor-enable-reactivates-others-again` below:** the fix recorded here (detect-and-correct AFTER `ApplyTopology(Extend)` runs) was rig-confirmed correct for FINAL state but was later found insufficient to prevent a brief, visible CCD-active flash on the unrelated monitor before correction could run. Read the newer entry for the complete picture; this entry's root-cause finding (`Extend` is whole-topology, not per-target-scoped) remains true and is the shared foundation both fixes build on.

## monitor-enable-reactivates-others-again — Enabling one disabled monitor via the tile dashboard briefly, visibly flashed another still-disabled monitor on/off before settling correct (5-round investigation, 3-monitor rig)
- **Date:** 2026-08-22
- **Error patterns:** tile click enables wrong monitor, extra monitor reactivated, monitor briefly turns on then off, flash, icon disappears then reappears, ApplyTopology Extend whole-topology side effect, PathInfo.ApplyPathInfos scoped activation, SDC_USE_SUPPLIED_DISPLAY_CONFIG, forceModeEnumeration, IsPathActive backing field, reflection-patch readonly backing field, debug log empty, EnableDebugLogging checkbox no effect until restart, TextWriterTraceListener wired once at startup, DebugLog.Configure, WriteStartupBanner, 3-monitor rig regression, DISPLAY-05
- **Root cause(s):** Two distinct, sequentially-discovered root causes, both required to reach the final confirmed fix. (1) **Structural CCD cause:** `PathInfo.ApplyTopology(Extend)` (already flagged whole-topology, non-per-target-scoped in `monitor-enable-affects-other` above) doesn't just risk leaving an unrelated monitor active in the FINAL state -- calling it AT ALL momentarily brings every monitor in the OS's persisted last-known-extend layout CCD-active, including ones the caller never requested, BEFORE any application-level detect-and-correct code (settle-poll loop, post-return watchdog) gets a chance to run. Detect-and-correct-after-the-fact (the `monitor-enable-affects-other` fix, plus this session's own rounds 2/3 bounded-retry-loop and out-of-call-boundary reactive-watchdog extensions) can converge on the correct final state and even shorten the exposure window, but structurally cannot prevent the window from opening at all -- because the event (the OS bringing the unrelated path active) happens synchronously inside the `Extend` call, before the correcting code's next line ever executes. On hardware where a CCD-active transition lasting ~1-2s corresponds to a real physical monitor wake (backlight/signal-detect), this is user-visible as a brief flash even though the dashboard settles to the correct state within seconds. (2) **Orthogonal diagnostic-pipeline cause (round 4, blocked investigation before the above could be found):** `Program.cs` wired the file `TextWriterTraceListener` into `Trace.Listeners` exactly once, at process startup, keyed off `AppSettings.EnableDebugLogging` as read AT THAT MOMENT; `SettingsForm.cs`'s Save handler persisted a new value to `settings.json` but had no code path to re-wire `Trace.Listeners` for an already-running process. Because this app's designed usage pattern is long-lived tray-resident operation (not per-action relaunch), the natural operator workflow -- toggle the Settings checkbox on an already-running instance, reproduce immediately -- silently produced a completely empty `debug.log` with zero other symptom (no exception, no crash), blocking evidence collection for two full investigation rounds before this gap itself was diagnosed and fixed.
- **Fix:** (1) **Scoped CCD activation** (`src/RigToggle.Windows/WindowsMonitorController.cs`): `ActivateMonitors` now attempts a new `TryBuildScopedActivationPlan` BEFORE its existing (unchanged) `ApplyTopology(Extend)` call. The plan constructs a `PathInfo[]` of every currently-active survivor path (queried fresh) plus one newly-active `PathInfo` per requested-but-inactive device path, built via `WindowsDisplayAPI`'s public `PathInfo(PathDisplaySource, PathTargetInfo[])` constructor (deliberately supplies no mode info) using a `PathTargetInfo` reused directly from a fresh `PathInfo.GetAllPaths()` read (never manually reconstructed -- see `ccd-topology-restore-findings` for why manual reconstruction is unsafe) with only its `IsPathActive` field flipped true via the same reflection-patch-a-readonly-backing-field technique already rig-proven for `OutputTechnology` in `ccd-topology-restore-findings` finding 1 (confirmed present in WindowsDisplayAPI 1.3.0.13 via `ilspycmd` IL decompilation, not assumed). This plan is applied via the existing `PathInfo.ApplyPathInfos(..., forceModeEnumeration: true)` -- which internally selects `SDC_USE_SUPPLIED_DISPLAY_CONFIG` rather than `SDC_TOPOLOGY_SUPPLIED`, and is a Microsoft-documented, intended mechanism (`nf-winuser-setdisplayconfig`: "SetDisplayConfig uses best mode logic...") for adding one path to an existing topology without whole-topology re-negotiation -- so the previously-flashing monitor is structurally never a candidate path at all. Any failure to build a valid plan, or an `ApplyPathInfos` exception, falls through to the byte-for-byte-unchanged `ApplyTopology(Extend)` call, logged on every branch. The settle-poll-then-correct loop, `ComputeUnexpectedlyActivated`, `DeactivateMonitors`, and `MainForm`'s intent-guard/reactive-watchdog (rounds 2/3 of this session) are all left completely unmodified as the safety net regardless of which activation path is taken. (2) **Live-reconfigurable diagnostic logging** (`src/RigToggle.Core/Diagnostics/DebugLog.cs` [new], `src/RigToggle.App/Program.cs`, `src/RigToggle.App/SettingsForm.cs`): extracted trace-listener wiring into `DebugLog.Configure`, called both from `Program.cs` at startup and from `SettingsForm.cs`'s Save handler, so toggling "Enable debug logging" takes effect immediately on an already-running instance without requiring a restart. Added `DebugLog.WriteStartupBanner()` -- unconditional (not gated on `EnableDebugLogging`), written via direct `File.AppendAllText` at the earliest safe point in `Program.Main()`, recording the exe's own path/build timestamp and the resolved log path -- so a future "log is empty" report is self-diagnosing (distinguishes "never reached Main" from "reached Main but logging was off" from "logging was on but nothing else ran") without another guessing round. Also substantially expanded `Trace.WriteLine` coverage across `ActivateMonitors`/`DeactivateMonitors` (ENTER/EXIT/every branch) and `MainForm`'s tile-action/intent-guard/watchdog paths.
- **Files changed:** src/RigToggle.Windows/WindowsMonitorController.cs, src/RigToggle.Core/Diagnostics/DebugLog.cs, src/RigToggle.App/Program.cs, src/RigToggle.App/SettingsForm.cs, src/RigToggle.App/MainForm.cs
- **Why not caught:** No gate existed for either cause. The CCD-activation cause is a variant of the same untestable-without-live-hardware class already documented in `monitor-enable-affects-other` ("verified only via live rig testing") -- existing unit tests cover only the pure `ComputeUnexpectedlyActivated` function, never the live sequencing/timing of the real `ApplyTopology`/`ApplyPathInfos` calls, so a fix that converges on the correct final state (round 2/3 of this session) passed every executable check while still leaving a real, uncaught visible-flash defect. The logging-pipeline cause had no gate because it's a live-reconfiguration/process-lifecycle behavior with no unit-testable seam and no existing convention requiring Settings changes to take effect without a restart; nothing short of an actual rig trial with logging toggled mid-session would have surfaced it.
- **Recurrence guard:** (1) For the CCD-activation cause: this knowledge-base entry itself, so a future Phase-0 recall surfaces "detect-and-correct-after-Extend can converge on final state but cannot prevent a momentary CCD-active window on unrelated monitors -- prefer a scoped `ApplyPathInfos` plan when one specific target needs activating" before re-deriving it from scratch for any future CCD activation work in this codebase. No automated regression test exists or is planned for `TryBuildScopedActivationPlan` itself (same "verified only via live rig testing" class as `ActivateMonitors`/`DeactivateMonitors` per that class's own doc comment) -- rig-trial confirmation (2026-08-22, see resolved debug session) is the durable evidence of record. (2) For the logging-pipeline cause: `DebugLog.WriteStartupBanner()` is now unconditional and permanent, so any future "log is empty" report is self-diagnosing directly from the next log's presence/absence of the startup banner line, without needing to re-discover this exact mechanism from scratch.
- **Re-confirmed 2026-08-31 by `monitor-activation-extend-only-redesign-rejected` below:** a full Phase 27 redesign attempt tried to REMOVE the scoped-`ApplyPathInfos` path this entry recommends, in favor of `Extend` alone. It was rejected after conclusive real-rig and isolated-CLI evidence that `Extend` cannot activate this rig's Odyssey G5 at all. This entry's recurrence guard ("prefer a scoped `ApplyPathInfos` plan when one specific target needs activating") stands confirmed, not reversed -- read the newer entry for the full evidence trail before ever reconsidering an Extend-only design again.

## monitor-activation-extend-only-redesign-rejected — Phase 27 attempted to replace scoped activation with whole-topology Extend; conclusively rejected by rig + isolated CLI evidence
- **Date:** 2026-08-31
- **Error patterns:** ApplyTopology Extend fails to activate monitor, Odyssey G5 won't turn on, SAM7489 monitor enable did not take effect, InvalidOperationException Monitor enable did not take effect, D-05 no further automatic recovery, whole-topology activation redesign, Extend-only architecture, monitor activation logic redesign, root_cause (2), DisplayProbe, standalone CCD diagnostic tool
- **Root cause(s):** NOT a bug -- an architectural hypothesis, tested and disproven. `.planning/debug/resolved/monitor-position-regre.md`'s round 22 proposed replacing the scoped-`ApplyPathInfos`-primary/`Extend`-fallback split with `ApplyTopology(Extend)` as the SOLE activation mechanism, on the theory that 20+ rounds of incremental correction/retry machinery had become disproportionate to the actual value delivered. Phase 27 Plan 01 implemented this (`ActivateMonitorsCore` rewritten to call only `ApplyTopology(Extend)`, commit `6b3058b`) and rig-tested it per the plan's own designed gate. Result: **whole-topology `Extend` cannot activate the Samsung Odyssey G5 (device path `SAM7489`) on this rig, at all, under any circumstance tested** -- 0 of 6 real-app activation attempts succeeded (identical `InvalidOperationException: Monitor enable did not take effect` every time, both via single-tile enable and via the Rig-mode toggle swap), and a follow-up standalone diagnostic CLI (`tools/DisplayProbe`, calling the identical `PathInfo.ApplyTopology(DisplayConfigTopologyId.Extend, allowPersistence: false)` primitive directly, with zero RigToggle code, zero correction loop, zero retry, no app process at all) reproduced the identical failure in complete isolation. This rules out RigToggle's execution context (threading, timing, WinForms message pump, prior API call ordering) as a contributing factor and confirms the failure is a raw Windows CCD/driver-level incompatibility between whole-topology `Extend` and this specific monitor on this hardware. This is exactly `root_cause (2)` -- flagged as a known, real risk in the round-22 proposal's own §22.3 honest risk note, and previously decompilation-confirmed as a structural limitation back in the original `monitor-position-resets-to-de` session (round 3): `ApplyTopology` calls `SetDisplayConfig(0, null, 0, null, ...)` with no path/mode arrays at all, so Windows' own opaque internal algorithm picks the entire resulting topology with zero ability for calling code to constrain or target a specific monitor. The monitor also has no exposed power-saving settings and is DisplayPort-only (confirmed by the operator), closing off the two alternative "cheap experiment" workarounds the round-22 proposal's own §21.5 had suggested trying (power/firmware settings, HDMI as a workaround) before reaching for a bigger redesign.
- **Fix:** Reverted commit `6b3058b` (revert commit `fd9f49b`), restoring the scoped-`ApplyPathInfos`-primary/`Extend`-fallback architecture unchanged. `dotnet build` clean, `RigToggle.Tests` 249/249 after the revert. Plan 02 (deleting the "orphaned" scoped-activation helpers) and Plan 03 (doc rewrite assuming the redesign shipped) never ran -- both were gated behind Plan 01's rig-verification checkpoint by deliberate design (Task 1's staged-two-commit decision), specifically so a failure like this one would have a clean single-commit revert point rather than requiring recovery from a combined behavior-change-plus-deletion diff.
- **Files changed:** src/RigToggle.Windows/WindowsMonitorController.cs (rewritten then reverted -- net change: none, back to pre-Phase-27 state), tools/DisplayProbe/ (new standalone diagnostic CLI, NOT part of RigToggle.sln or the shipped app -- retained in the repo for any future CCD-level investigation needing a bare, app-free repro harness).
- **Why not caught before implementation:** The round-22 redesign proposal was itself honest about this exact risk (`root_cause (2)` was named and cited in its own §22.3), but treated it as a plausible-but-unconfirmed trade-off rather than a known-blocking one, because no round of the original two debug sessions had specifically re-tested bare `Extend` against SAM7489/SAM748A in isolation since round 3 (which found the same failure for the differently-numbered device path `SAM748A` -- likely the same physical monitor after a Windows CCD re-enumeration changed its last few device-path hex digits). The redesign's own rig-gate design (Plan 01 Task 3, `gate="blocking"`, halts before Plan 02) is precisely the safety mechanism that caught this before any code was deleted -- it worked as designed.
- **Recurrence guard:** This entry, plus the re-confirmation note appended to `monitor-enable-reactivates-others-again` above, so a future Phase-0 recall for any monitor-activation work surfaces "an Extend-only redesign was already tried and conclusively rig-rejected for this exact monitor (SAM7489/Odyssey G5) -- do not re-attempt without new hardware, a new driver, or a different monitor" before re-deriving the same conclusion from scratch. `tools/DisplayProbe` (retained in the repo, not part of the shipped app) is available for any future investigator who needs to test a raw CCD call against real hardware without spinning up the full app -- run `dotnet run --project tools/DisplayProbe -- list` to enumerate available targets and `dotnet run --project tools/DisplayProbe -- extend <device-path-substring>` to test bare `Extend` activation in isolation.

## promote-to-origin-collision-not-resolved — Re-adding a monitor that was previously solo-active alongside another monitor threw PathChangeException every time, permanently, until app restart
- **Date:** 2026-08-31
- **Error patterns:** PathChangeException Invalid paths information, monitor stuck after Rig mode toggle, scoped activation fails after using Rig/Normal toggle switch, manual tile re-enable fails repeatedly, works after app restart then breaks again, TryBuildScopedActivationPlan modeInfoAvailable=True position=(0,0) for two different sources, PromoteToOriginIfNeeded, origin collision, cached mode Position mismatch
- **Root cause:** `PromoteToOriginIfNeeded`'s guard (`if (keptActiveSurvivors.Any(IsAtOrigin) ||
  newPaths.Any(IsAtOrigin)) return ... unchanged;`) only ever checked "does AT LEAST ONE entry
  across both lists claim the desktop origin (0,0)" -- it never checked for TWO independent
  claimants. A device's cached live-mode position (`_lastKnownActiveModeByDevicePath`) can equal
  (0,0) simply because it was SOLO-ACTIVE the last time its mode was captured (trivially at the
  origin, since nothing else was on screen) -- e.g. immediately after a Rig-mode toggle where one
  monitor is the only one enabled. When that monitor is later re-added alongside a DIFFERENT
  monitor that is CURRENTLY, genuinely primary at (0,0), the scoped plan submits BOTH entries with
  `modeInfoAvailable=True position=(0,0)` simultaneously -- confirmed directly in a real-rig debug
  log's own `TryBuildScopedActivationPlan` entry dump, not inferred. `SetDisplayConfig` requires
  exactly one active path at the origin and rejects a plan violating that with
  `PathChangeException("Invalid paths information.")`, which fell through to the already-confirmed-
  broken `Extend` fallback (see `monitor-activation-extend-only-redesign-rejected` above), producing
  a D-05 `InvalidOperationException` the app surfaced to the user. This reproduced 100% of the time
  after using the Rig/Normal toggle switch, and cleared only on a full app restart (which discards
  the in-memory `_lastKnownActiveModeByDevicePath` cache) -- the restart-clears-it behavior is what
  distinguished this from genuine external driver nondeterminism and pointed straight at an
  in-process cache bug.
- **Fix:** `PromoteToOriginIfNeeded` (`src/RigToggle.Windows/WindowsMonitorController.cs`): when a
  kept survivor already holds the origin, any `newPaths` entry that ALSO independently claims it
  now has its stale cached mode dropped to blank (same effect as if no cache entry existed), letting
  the driver pick a fresh position for it instead of colliding. The kept survivor's claim wins
  because it reflects the CURRENT arrangement; the new target's cached claim reflects a different,
  unrelated prior arrangement -- the same principle this method's own pre-existing remarks already
  applied to cached positions generally, just not to this specific two-claimant case.
- **Files changed:** `src/RigToggle.Windows/WindowsMonitorController.cs`,
  `src/RigToggle.Windows.Tests/WindowsMonitorControllerTests.cs` (new test
  `PromoteToOriginIfNeeded_SurvivorAndNewTargetBothClaimOrigin_NewTargetsStaleClaimDropped`).
- **Why not caught:** `PromoteToOriginIfNeeded` has 6 pre-existing unit tests (added round 4 of the
  original `monitor-position-resets-to-de` session) covering "nobody at origin" and "exactly one
  entry at origin" shapes, but none exercised "two independent entries both at origin" -- the
  specific shape this bug lives in. `ActivateMonitors`/`DeactivateMonitors` themselves are excluded
  from unit testing (live CCD calls, no injectable seam), so this was only reachable via a real rig
  trial with a specific history (solo-active, then re-added alongside another monitor) that the
  original round-4 rig verification never happened to exercise.
- **Recurrence guard:** The new test above locks in the fix. This entry, so a future Phase-0 recall
  surfaces "a newly-reactivated target's cached position can collide with a currently-active
  survivor's real origin claim if the target was previously solo-active -- `PromoteToOriginIfNeeded`
  must resolve ties, not just detect their absence" before re-deriving this from scratch. If a
  similar `PathChangeException: Invalid paths information` recurs for a DIFFERENT repro shape, check
  whether it is a third, still-undiscovered origin-collision variant before assuming it is the
  already-fixed one.
