## Symptoms

### Symptom 1: Monitor position resets to default
- **Expected:** A monitor's position, as configured in Windows Display Settings, is preserved when it is disabled and then re-enabled through Rig Toggle.
- **Actual:** The monitor's position resets to its default position after being disabled and re-enabled. Happens silently, no error/warning surfaced anywhere in the app.
- **Reproduction:** Disable a monitor (via either the dashboard monitor tile or the Rig/Normal mode toggle) and re-enable it (either control). User confirmed it happens via both controls.
- **Timeline:** Started recently (not "always happened") — user is unsure of the exact trigger commit but reports it as a regression, not a longstanding issue.
- **Severity:** major (user confirmed) — always needs re-setting up after the monitor wakes.
- **Status: RESOLVED** — rig-confirmed fixed by the position-mode cache described in Resolution below.

### Symptom 2: Rig mode switch partially fails when one monitor is already disabled
- **Expected:** Switching to Rig mode (via the Rig/Normal toggle) completes normally regardless of whether a monitor is already disabled going in.
- **Actual:** "Partial toggle" — some steps happen (e.g. audio switches, app launches) but the monitor part doesn't complete correctly, or ends up in a wrong/inconsistent state.
- **Reproduction:** Have one monitor already disabled (e.g. via the dashboard tile), then flip the Rig/Normal toggle to switch to Rig mode.
- **Timeline:** Also reported as new ("we broke something") — noticed in the same session as Symptom 1.
- **No errors surfaced**, no crash — silent partial failure.
- **Status:** fix implemented, self-verified, awaiting rig verification (see Current Focus / Resolution below). Root cause turned out to be DIFFERENT from the original shared-cause hypothesis — see Eliminated.

### Suspected relationship
Both symptoms involve monitor enable/disable state handling and both surfaced together, recently. Originally hypothesized to share a single root cause in the scoped-activation path's missing mode data — confirmed true for Symptom 1, refuted for Symptom 2 by a post-fix rig trial (see Eliminated and Evidence below). Symptom 2's real root cause is a distinct reliability problem with the same scoped-activation path, specific to the full Rig/Normal monitor-swap usage shape.

## Resolution

root_cause: "Two distinct root causes, both located in WindowsMonitorController's round-5 scoped-activation path (TryBuildScopedActivationPlan, commit dc93b66), confirmed via two separate rig trials:
(1) Symptom 1: TryBuildScopedActivationPlan originally constructed the newly-reactivated target's PathInfo via a mode-less constructor (no Position/Resolution/PixelFormat), letting the driver's best-mode-logic pick a default instead of the monitor's own prior position. Rig-confirmed FIXED by the position-mode cache described below.
(2) Symptom 2: independently of (1), TryBuildScopedActivationPlan's plan construction (`currentActivePaths.Concat(newPaths)`) unconditionally keeps every already-active survivor active alongside the newly-activated target(s). When ActivateMonitors is the first half of a full Rig/Normal monitor swap (immediately followed by DeactivateMonitors removing a different, largely-disjoint set within the same ToggleService 'Monitor' step), this creates a transient topology with MORE simultaneously-active monitors than either the pre- or post-toggle state. Rig-log evidence shows this transient state is unreliable: the OS/driver either silently reverts the whole apply ~3 seconds after an apparently-successful, verified apply (forward/Rig direction, 1 new target added to 2 survivors), or the apply is rejected outright with PathChangeException('Invalid paths information.') at call time (reverse/Normal direction, 2 new targets added to 1 survivor -- TryBuildScopedActivationPlan's greedy per-target 'first unclaimed PathDisplaySource' candidate selection does not validate that multiple newly-claimed sources are mutually compatible to activate together). ApplyTopology(Extend) does not have this failure mode for this shape and has been the sole, rig-proven activation mechanism for this exact swap pattern across every round of this file's history (rounds 1-4, and still today's fallback in round 5)."
fix: "Symptom 1 fix (src/RigToggle.Windows/WindowsMonitorController.cs): added an instance-level cache (`_lastKnownActiveModeByDevicePath`, Dictionary<string, PathInfo>) scoped to the WindowsMonitorController singleton (constructed once at the composition root, Program.cs:282, shared by both the tile dashboard and the Rig/Normal toggle flow). DeactivateMonitors now populates this cache with each target's real, live PathInfo (carrying Position/Resolution/PixelFormat) immediately before that target is removed -- while the data is still genuinely live, per the ccd-topology-restore-findings KB entry's finding 5b. TryBuildScopedActivationPlan (converted from a static to an instance method so it can read the cache) now checks this cache first when building the PathInfo for a target being reactivated: if a cached mode exists, it supplies the real Position/Resolution/PixelFormat via the same PathInfo(source, position, resolution, pixelFormat, targets) constructor overload DeactivateMonitors' own survivor-repositioning code already uses safely elsewhere in this file; if no cache entry exists, it falls back unchanged to round 5's original blank-mode constructor.
Symptom 2 fix (src/RigToggle.Core/Abstractions/IMonitorController.cs, src/RigToggle.Windows/WindowsMonitorController.cs, src/RigToggle.Core/ToggleService.cs, src/RigToggle.App/MainForm.cs, plus test doubles): ActivateMonitors now takes an explicit `bool isPartOfMonitorSwap` parameter. Does not touch, weaken, or remove TryBuildScopedActivationPlan itself, the position-mode cache, the settle-poll-then-correct loop, ComputeUnexpectedlyActivated, or DeactivateMonitors -- all left fully in place for the still-valid single-target case."
