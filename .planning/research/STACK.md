# Technology Stack

**Project:** Rig Toggle — v2.1 "Modern UI Redesign & Theme Backlog"
**Scope:** Stack additions/techniques for THEME-08 (custom-drawn toggle switch), THEME-07 (live Windows accent-color follow), THEME-09 (manual light/dark override), and the new MainForm per-monitor tile dashboard. Already-shipped mechanisms (CCD monitor control, `IPolicyConfig` audio, tray/hotkey, light/dark theme-follow infrastructure) are NOT re-researched here — see `.planning/research/STACK.md`'s prior milestone sections in git history and `CLAUDE.md` for those.
**Researched:** 2026-08-09
**Confidence:** HIGH for all four areas — every API surfaced below was verified against current Microsoft Learn documentation (fetched directly, not from training-data recall) and cross-checked against this repo's own existing source (`ThemeApplier.cs`, `WindowsThemeProvider.cs`, `DwmTitleBar.cs`, `NativeMethods.cs`, `MainForm.cs`, `MonitorPanelForm.cs`).

## Headline Finding

**Zero new NuGet packages are needed for any of the four v2.1 UI targets.** All four are pure WinForms/GDI+/P-Invoke techniques that extend this project's existing, already-proven patterns:

- The toggle switch is a hand-rolled `Control` subclass with `OnPaint` GDI+ drawing — the same `Graphics`/`SmoothingMode.AntiAlias`/`SolidBrush` idiom already used in `MonitorPanelForm.CreateStatusDot` and `RigToggle.IconGen`.
- The accent color is read via `DwmGetColorizationColor` (dwmapi.dll) — a **second** export from the exact same DLL `DwmTitleBar`/`NativeMethods` already P/Invoke into for `DwmSetWindowAttribute` — with live-change delivered via `WM_DWMCOLORIZATIONCOLORCHANGED`, using the same "intercept a window message" pattern `MainForm.WndProc` already implements for `WM_HOTKEY`.
- The manual theme override is pure application-layer logic on top of the existing `IThemeProvider`/`AppSettings`/`System.Text.Json` stack — no new library, no new Windows API.
- The monitor-tile dashboard reuses the `FlowLayoutPanel` + hand-rolled tile `UserControl` approach already recommended (and now folded from the retiring `MonitorPanelForm` directly into `MainForm`), extended with click-to-toggle and icon+number rendering.

This keeps the project's zero-new-dependency track record intact across three milestones running.

## Recommended Stack Additions

### 1. Custom-Drawn Toggle-Switch Control (THEME-08)

|-----------|-------|---------|------------------|
| New `ToggleSwitch : Control` class (own file, e.g. `RigToggle.App/Controls/ToggleSwitch.cs`) overriding `OnPaint` | `RigToggle.App` (WinForms is UI-only in this solution; Core/Windows stay UI-agnostic) | Renders the track (rounded-rect via `GraphicsPath` + `FillPath`) and thumb (`FillEllipse`), positioned by a `Checked` bool, entirely in owned pixels | Derive from `Control`, **not** `Button` or `CheckBox` — deriving from `Control` means there is no native visual-styles rendering pipeline to fight (no `FlatStyle.System` gotcha, no `dotnet/winforms#13897` hover-color bug like this project hit with `Button` in Phase 12). Every pixel is drawn explicitly with the same palette colors `ThemeApplier` already uses, so it is themed exactly like the rest of the app with zero extra API surface. |
| `SetStyle(ControlStyles.UserPaint \| ControlStyles.AllPaintingInWmPaint \| ControlStyles.OptimizedDoubleBuffer \| ControlStyles.ResizeRedraw \| ControlStyles.Selectable, true)` in the constructor | Same class | Flicker-free repaint on resize/hover/click; `Selectable` lets it receive keyboard focus (Tab) and Space/Enter to toggle for accessibility | Documented, current pattern for owner-drawn WinForms controls (`learn.microsoft.com/dotnet/desktop/winforms/controls/overriding-the-onpaint-method`) — unchanged mechanism, no .NET-10-specific caveats found. `AllPaintingInWmPaint=true` means `WM_ERASEBKGND` is skipped and both background+foreground paint happen from a single `WM_PAINT`, which combined with `OptimizedDoubleBuffer` eliminates the flicker a naive `OnPaint`-only override would show while dragging/hovering. |
| `GraphicsPath` rounded-rect track + `Graphics.FillEllipse` thumb, `SmoothingMode.AntiAlias` | Same class, `OnPaint` | Clean, non-jagged rendering matching the smooth pill shape users expect from a modern toggle | Same technique already proven in this codebase — `MonitorPanelForm.CreateStatusDot` uses `Graphics.FromImage` + `SmoothingMode.AntiAlias` + `SolidBrush`/`FillEllipse` for its status dots, and `RigToggle.IconGen` already does stroke-then-fill `GraphicsPath` compositing (Phase 13 gap-closure) — this is a smaller instance of the exact same GDI+ discipline, not a new skill for the codebase. |
| Explicit hover/pressed/checked color states set from a `bool dark` parameter, mirroring `ThemeApplier.ThemeButton`'s signature shape | New `ThemeApplier.ThemeToggleSwitch(ToggleSwitch, bool dark)` method | Track/thumb colors for On (ideally tinted with the accent color — see #2) vs Off, in both light and dark mode | Because the control paints itself, "theming" it is just picking the right colors per state, exactly like every other `ThemeApplier.Theme*` method already does for the grid, hotkey box, buttons, and combos. No `ControlStyles.ApplyThemingImplicitly` opt-in/opt-out is needed here (see Integration section below) — that flag only matters for controls that either compose native Win32 common controls or inherit an existing themed pipeline (e.g. `Button`), neither of which applies to a `Control`-derived, fully owner-drawn class. |
| `MouseEnter`/`MouseLeave`/`MouseDown`/`MouseUp`/`Click` overrides + `Invalidate()` on each, plus a `Checked`-changed `CheckedChanged` event | Same class | Hover/pressed visual feedback and the actual toggle semantics (replaces the plain `Button.Click` the current Rig/Normal button uses) | Standard WinForms custom-control event wiring; `MainForm`'s existing `TrayToggleMenuItem_Click`/hotkey toggle handler dispatch pattern (already structurally duplicated 3 ways per its own doc comments) can subscribe to `CheckedChanged` the same way it subscribes to the current button's `Click`. |

### 2. Windows Accent-Color Reading + Live-Change Detection (THEME-07)

| Technique | Where | Purpose | Why Recommended |
|-----------|-------|---------|------------------|
| `DwmGetColorizationColor(out uint pcrColorization, out bool pfOpaqueBlend)` — new `[DllImport("dwmapi.dll")]` sibling next to the existing `DwmSetWindowAttribute` declaration | `RigToggle.Windows/NativeMethods.cs` | One-shot read of the current Windows accent/colorization color as `0xAARRGGBB` | Confirmed directly against Microsoft's official Win32 API reference (`learn.microsoft.com/windows/win32/api/dwmapi/nf-dwmapi-dwmgetcolorizationcolor`, `Minimum supported client: Windows Vista`, no deprecation notice, still current) — same DLL (`dwmapi.dll`) this project already P/Invokes into for `DwmSetWindowAttribute`, so this is one more export off an already-proven, already-loaded native library, not a new dependency surface. Community cross-checks (accent-color tooling discussions) confirm this is the same underlying value Windows 10/11's Settings > Personalization > Colors accent swatch and the `HKCU\Software\Microsoft\Windows\DWM\AccentColor` registry value both reflect — MEDIUM-HIGH confidence on the "same value as the Settings swatch" claim (corroborated by multiple independent community sources, not an official Microsoft statement), HIGH confidence on the API itself being current and correctly documented. |
| `WM_DWMCOLORIZATIONCOLORCHANGED` (message value `0x0320`) intercepted via a message-only `NativeWindow` owned by a new `WindowsAccentColorProvider` | `RigToggle.Windows/WindowsAccentColorProvider.cs` (new) | Live notification the instant the user changes their accent color in Windows Settings, while the app is running | Confirmed directly against Microsoft's docs (`learn.microsoft.com/windows/win32/dwm/wm-dwmcolorizationcolorchanged`): *"Informs all top-level windows that the colorization color has changed... A window receives this message through its WindowProc function."* `wParam` already carries the new `0xAARRGGBB` value, so the handler doesn't even need to re-call `DwmGetColorizationColor` on the change path (though calling it once at construction time for the initial value is still correct). **Recommended primary implementation:** give `WindowsAccentColorProvider` its own message-only `NativeWindow` (create via `NativeWindow.CreateHandle(CreateParams)` with `cp.Parent = (IntPtr)(-3)` i.e. `HWND_MESSAGE` — a documented, BCL-only pattern, `learn.microsoft.com/dotnet/api/system.windows.forms.nativewindow.createhandle`), override its `WndProc` to catch `0x0320`, and raise `AccentColorChanged`. This makes the new provider **structurally symmetric with the already-shipped `WindowsThemeProvider`**: both are self-contained, constructor-subscribing, DI-injectable classes that own their own event source and don't depend on any particular `Form` being alive — `WindowsThemeProvider` self-subscribes to `SystemEvents.UserPreferenceChanged`; `WindowsAccentColorProvider` self-subscribes via its own hidden window. **Lower-effort fallback if the message-only window proves troublesome in practice:** extend `MainForm.WndProc` (which already intercepts `WM_HOTKEY` for TRIG-01) to also catch `0x0320` and forward it into the same event source — simpler, but couples the provider's liveness to `MainForm` specifically, unlike every other `IThemeProvider`-shaped abstraction in this codebase. |
| New `IAccentColorProvider` interface: `Color CurrentAccentColor { get; }` + `event EventHandler? AccentColorChanged;` | `RigToggle.Core/Abstractions/IAccentColorProvider.cs` (new) | Cross-assembly contract, mirroring `IThemeProvider`'s exact shape | Keeps `RigToggle.App` decoupled from the Windows-specific mechanism (same reasoning `IThemeProvider` already documents), and gives `RigToggle.Tests` a trivial `FakeAccentColorProvider` double for free, following the existing `FakeThemeProvider` precedent. |
| Discard the returned alpha byte; build the usable `Color` as `Color.FromArgb(255, (raw >> 16) & 0xFF, (raw >> 8) & 0xFF, raw & 0xFF)` | Inside `WindowsAccentColorProvider` | Produces a fully-opaque `Color` suitable for painting UI elements | Per Microsoft's own remarks on `DwmGetColorizationColor`: the returned alpha is a **glass-composition blend value**, not a UI transparency value — using it as-is for a solid accent fill/border would (depending on the current blend) render partially see-through in a way that has nothing to do with the user's actual chosen color. This is a real, easy-to-miss gotcha; treat the RGB triplet as the accent color and always force alpha to `255` for solid UI use, matching how every other color in `ThemeApplier` (e.g. `Color.FromArgb(45, 45, 48)`) is already a fully-opaque literal. |

ThemeOverride` property on the existing `AppSettings` model | `RigToggle.Core/Models/AppSettings.cs` | Persists the user's manual choice: `null` = follow Windows (current default behavior, unchanged), `Light`/`Dark` = pin regardless of the live OS value | Zero new stack surface — `AppSettings` is already, by this project's own documented convention, "all fields nullable: null means never configured." `System.Text.Json` (already the only serializer in use) round-trips a new nullable enum property with no code beyond the property declaration itself, exactly like every prior optional-setting addition (v2.0's `CompanionAppPath`/audio device IDs). |

Two trigger sources (live OS event, manual Settings-Save) converging on one re-theme method is a smaller surface than two independent theming code paths. |

## Integration with Existing Theme Architecture

- **`IThemeProvider`/`WindowsThemeProvider` stay unchanged.** Their job (report the OS `AppsUseLightTheme` registry value, live) is orthogonal to accent color (a separate DWM concept) and orthogonal to the manual override (an application-layer setting). Do not fold accent-color or override logic into this class — keep the three concerns (OS light/dark, accent color, manual override) as three separate, independently-testable pieces that `MainForm`/`SettingsForm` compose together, matching how `IThemeProvider` was deliberately scoped narrowly in Phase 12 (it reads `AppsUseLightTheme` only, not the sibling taskbar-coloring value, on purpose).
- **`DwmTitleBar` stays unchanged** (still only sets `DWMWA_USE_IMMERSIVE_DARK_MODE`/corner/backdrop attributes). The new `DwmGetColorizationColor` P/Invoke is a sibling addition to the same `NativeMethods.cs` file and gets its own façade class (`WindowsAccentColorProvider`, or a thin static wrapper if a full provider class is judged unnecessary) — do not bolt accent-color reading onto `DwmTitleBar`, which is scoped to window-chrome attributes, not colors.
- **`ThemeApplier` grows two new methods** (`ThemeToggleSwitch`, `ThemeMonitorTile`) following the exact shape of its existing five (`ThemeMonitorGrid`, `ApplyHotkeyIdleConfigured/Unconfigured/Recording`, `ThemeButton`, `ThemeComboBox`): static, try/catch-wrapped, idempotent, taking the control instance plus a `bool dark` (and now also `Color accent` for the two new methods, since these are the first two controls in the app whose theming genuinely depends on accent color, not just light/dark).
- **`ControlStyles.ApplyThemingImplicitly` does not need to be touched** for either new custom control. Per .NET 10's own WinForms release notes (`learn.microsoft.com/dotnet/desktop/winforms/whats-new/net100`), that flag exists for two specific cases neither of which applies here: (1) a control that *composes* native Win32 common controls (e.g., one hosting a scrollbar) and needs to opt in to theming before `CreateParams` is read, or (2) a control that inherits from an already-theming-aware base (like `Button`) and wants to opt *out* to fully control its own drawing. `ToggleSwitch`/`MonitorTile` derive straight from `Control` and paint 100% of their own pixels with explicit colors already — there is no native pipeline to opt in or out of.
- **Startup ordering**: construct `WindowsAccentColorProvider` alongside `WindowsThemeProvider` in the composition root (`Program.cs`), inject both into `MainForm` (and `SettingsForm` if it also hosts an accent-tinted element), and subscribe to `AccentColorChanged` the same way `ThemeChanged` is already subscribed in `MainForm`'s constructor — including the same "may fire off the UI thread, marshal via `InvokeRequired`/`BeginInvoke`" caveat `WindowsThemeProvider`'s own doc comment already calls out, since `WM_DWMCOLORIZATIONCOLORCHANGED` delivery threading has the same "don't assume UI thread" posture as `SystemEvents.UserPreferenceChanged`.
- **Contrast caveat worth flagging for the build phase (not a stack blocker):** the user's chosen accent color can be very light (poor contrast against a light background) or very dark (poor contrast against dark-mode backgrounds) — do not hardcode white or black text on top of the raw accent color; compute a legible foreground (e.g., a simple relative-luminance threshold) the same deliberate way `ThemeApplier`'s other methods hardcode specific light/dark-safe pairs rather than deriving colors on the fly.

## Alternatives Considered

| Recommended | Alternative | Why Not for This Project |
|-------------|-------------|---------------------------|
| `DwmGetColorizationColor` + `WM_DWMCOLORIZATIONCOLORCHANGED` (plain P/Invoke, dwmapi.dll) | `Windows.UI.ViewManagement.UISettings.GetColorValue(UIColorType.Accent)` (WinRT projection) | Technically a zero-NuGet option too (classic WinRT/UWP contracts project directly from .NET 5+ when the TFM is `net10.0-windows10.0.19041.0` or higher, no separate package needed) — but it requires **changing the project's TFM** from the current `net10.0-windows` to a Windows-10-SDK-versioned TFM, a solution-wide change with self-contained-publish implications this milestone has no other reason to make. It also introduces WinRT COM apartment/activation concerns (`RoInitialize`) this codebase has never needed anywhere else. `DwmGetColorizationColor` needs none of that — it is one more export off the exact same `dwmapi.dll` already loaded for `DwmSetWindowAttribute`. |
| `DwmGetColorizationColor`/`WM_DWMCOLORIZATIONCOLORCHANGED` | Polling `HKCU\Software\Microsoft\Windows\DWM\AccentColor` on a timer, or reading it once alongside the existing `SystemEvents.UserPreferenceChanged` handler | The registry value's format/location is corroborated only by community sources, not official docs (the search results explicitly note this path is "more or less undocumented and might break in the future"), and a timer-poll wastes cycles for something Windows already pushes as a message. `SystemEvents.UserPreferenceChanged` (the mechanism `WindowsThemeProvider` uses) is a documented, broad-category BCL event, but is not documented anywhere as firing specifically for accent-color changes the way `WM_DWMCOLORIZATIONCOLORCHANGED` explicitly is — using the message Microsoft's own docs name for exactly this purpose is the higher-confidence choice. Keep the registry value only as a manual-debugging cross-check, not as the app's live source of truth. |
| Hand-rolled `ToggleSwitch : Control` with owner-draw `OnPaint` | Any third-party WinForms toggle-switch/"metro switch" control (e.g. community `ToggleSwitch` CodeProject controls, Guna UI's toggle button, MetroFramework's switch, Krypton Toolkit) | Same reasoning already recorded in this project's Phase 12/13 stack decisions for tray icons and control theming: a third-party control adds real dependency surface and a **second** theming API this project would have to keep in sync with `Application.SetColorMode`/`ThemeApplier`'s own palette — for a single control whose full behavior (track, thumb, hover/pressed/checked states, ~150-200 lines of GDI+) is well within what this project has already hand-rolled elsewhere (icons, status dots, per-control theme overrides). Explicitly out per this project's zero/near-zero-dependency track record. |
| Hand-rolled `MonitorTile : Control`/`UserControl` in `FlowLayoutPanel` | Third-party WinForms dashboard/tile component suites (Krypton `TilePanel`, Infragistics `TilePanel`, MetroFramework tiles) | Identical reasoning to the v2.0 stack pass's rejection of the same category for the now-retiring `MonitorPanelForm` — 2-4 status tiles for a personal multi-monitor rig remain simple enough to hand-roll, and Infragistics specifically is a commercial/licensed dependency class this project has none of. |
| Hand-rolled `MonitorTile` in `FlowLayoutPanel` | `ListView` in `View.Tile` mode (built-in WinForms, zero extra code) | Same reasoning already recorded in the v2.0 stack pass: `ListView` composes native Win32 common controls, which per .NET 10's own dark-mode docs needs the manual `ControlStyles.ApplyThemingImplicitly` opt-in this codebase has never used or rig-tested, plus its selection/`ItemActivate` conventions fit "click anywhere on the tile to toggle it" worse than a custom `Click` handler does. |
| Deriving the toggle switch from `Control` | Deriving from `Button`/`CheckBox` and heavily re-styling via `FlatStyle.Flat` + `FlatAppearance` overrides (the same technique `ThemeApplier.ThemeButton` already uses for the plain button being replaced) | Possible, but inherits the exact fragility this project already rig-discovered and had to work around in Phase 12 (`dotnet/winforms#13897`: `FlatStyle.Flat`'s hover/pressed `FlatAppearance` colors don't reliably apply once dark mode is active without the `BorderSize=0` workaround). A toggle switch's visual (rounded track + circular thumb, not a rectangular button face) doesn't map cleanly onto `Button`'s rendering model anyway — full owner-draw sidesteps both the visual mismatch and the known theming bug at once. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Any third-party WinForms UI component/control-suite NuGet package (Krypton Toolkit, MetroFramework, Guna.UI2, Infragistics, DevExpress, MaterialSkin, etc.) for the toggle switch, accent-color reading, or the tile dashboard | Breaks this project's documented zero/near-zero-dependency track record (CLAUDE.md's "Alternatives Considered"/"What NOT to Use" already reject this category for tray icons and control theming for the same reasons: extra dependency surface, a second theming system to keep in sync with `Application.SetColorMode`, and for some of these, commercial licensing this project has never taken on) | Hand-rolled `Control`-derived custom controls with GDI+ `OnPaint`, exactly as this project already does for its status dots and procedurally-generated icons |
| `Windows.UI.ViewManagement.UISettings` (WinRT) as the accent-color source | Requires retargeting the TFM to a Windows-SDK-versioned one (`net10.0-windows10.0.19041.0`+), a solution-wide change with no other justification this milestone, plus WinRT COM activation concerns this codebase has never needed | `DwmGetColorizationColor` P/Invoke — same `dwmapi.dll` already in use, no TFM change |
| Reading/depending on the raw `pfOpaqueBlend`/alpha byte from `DwmGetColorizationColor` as a UI transparency value | Documented as a glass-composition blend flag, not a UI alpha value — using it directly could render accent-tinted UI elements unexpectedly translucent depending on the user's current blend state | Discard the returned alpha byte; construct the usable `Color` with alpha forced to `255` |
| A new `IThemeProvider`-implementing decorator class to represent "effective theme after manual override" | Adds an extra abstraction layer and a second implementation of an interface whose only real implementation (`WindowsThemeProvider`) is working correctly and shouldn't be touched | A one-line `settings.ThemeOverride ?? themeProvider.CurrentTheme` expression at the handful of existing `IsDarkTheme`-style call sites |
| `FindWindow`-style title/class matching, or any new window-manipulation P/Invoke, for accent-color notification | Already forbidden project-wide per CLAUDE.md ("What NOT to Use"); also unnecessary here — `WM_DWMCOLORIZATIONCOLORCHANGED` is delivered automatically to any window's `WndProc`, no window lookup needed | Message-only `NativeWindow` (self-owned) or `MainForm.WndProc` extension, both of which passively receive the message Windows already sends |
| `PublishTrimmed=true` (still, unchanged from prior milestones) | Unrelated to this milestone's UI work but worth restating: none of the new P/Invoke (`DwmGetColorizationColor`) or `NativeWindow`/message-only-window code changes this project's existing, hard-documented trimming constraint — new P/Invoke surface is exactly the kind of code IL trimming's reachability analysis has already been shown to misidentify as dead and strip | Leave `PublishTrimmed` false, as already configured |
