# Technology Stack

**Project:** Rig Toggle — v2.2 "Auto-Update, Single-Instance Guard & Smaller Footprint"
**Scope:** Stack additions/techniques for the three NEW v2.2 capabilities only — (1) GitHub-Releases-based auto-update with in-place self-replace, (2) a mutex-based single-instance guard that focuses the existing window, (3) further self-contained-exe size reduction with no IL trimming. Already-validated stack (.NET 10/C# 13/WinForms, self-contained single-file win-x64 publish, `WindowsDisplayAPI`, `NAudio.Wasapi`, hand-rolled `IPolicyConfig` COM interop, `System.Text.Json` settings, hand-rolled Win32 P/Invoke for focus/minimize and `RegisterHotKey`) is **not** re-researched here — see `CLAUDE.md` and this file's git history for that.
**Researched:** 2026-08-18
**Confidence:** MEDIUM overall. No curated research-provider (Context7/Exa/Tavily/etc.) was configured in this session — `classify-confidence` returned LOW for the raw `websearch`/`webfetch` tool tier used throughout. Individual findings are upgraded to MEDIUM/HIGH in-line below where corroborated directly against official Microsoft Learn docs, `dotnet/runtime`/`dotnet/docs` source, or this repo's own `.csproj`/`.pubxml`/workflow files (read directly, not inferred).

## Headline Finding

**Zero new NuGet packages are the right choice for all three v2.2 targets, and this is a deliberate recommendation, not a gap.** Consistent with this project's established pattern of hand-rolling small, stable Win32/COM/HTTP surfaces instead of taking on niche or heavyweight third-party dependencies (the `IPolicyConfig` precedent), all three capabilities below are implementable with BCL-only code (`HttpClient`, `System.Text.Json`, `System.Threading.Mutex`, `System.IO.File`) plus a handful of hand-written `DllImport`s in the same style as the existing `RegisterHotKey`/`ShowWindow` P/Invoke. The one "package" candidates researched (Velopack, NetSparkle, AutoUpdater.NET, Onova, GitHubReleaseUpdater) were all evaluated and rejected — see Alternatives Considered — because every one of them assumes a directory-of-files or installer-based deployment model that conflicts with this project's "one raw self-contained exe attached directly to a GitHub Release" distribution model.

**The size-reduction target has a hard ceiling without trimming/AOT.** Research into a real-world case study (a .NET self-contained exe shrunk 98%) shows essentially all large wins — 50+ MB from `PublishTrimmed`, several more MB from Native AOT/ILC flags — come from exactly the two techniques this project has explicitly and correctly excluded (IL trimming's static analysis breaks COM/P-Invoke marshalling; Native AOT does not officially support WinForms at all as of .NET 10). The four MSBuild levers already applied at v2.0 (compression, satellite-language trim, invariant globalization, NAudio package split) captured the large non-trimming win (57.79%). What remains is genuinely marginal — see the Size Reduction section for what's real and what's a wash.

## Recommended Stack Additions

### 1. GitHub-Releases Auto-Update (Self-Replacing Exe)

| Technique | Where | Purpose | Why Recommended |
|-----------|-------|---------|------------------|
| `System.Net.Http.HttpClient` (BCL) calling `GET https://api.github.com/repos/bpivk/monitor-toggle/releases/latest` with a required `User-Agent` header | New `RigToggle.Windows` or `RigToggle.App` class, e.g. `GitHubUpdateChecker` | Fetch the latest published (non-prerelease, non-draft) release's tag and asset list | This endpoint is documented to return "the most recent non-prerelease, non-draft release" automatically — exactly the "is there a newer real version" semantics the milestone wants, with zero extra filtering logic needed. It is publicly readable with no auth token for a public repo (confirmed: `bpivk/monitor-toggle` is public since v1.2). GitHub's API rejects requests with no `User-Agent` header (well-established GitHub API requirement) — must be set explicitly on the `HttpClient`. Unauthenticated rate limit is 60 requests/hour/IP, which is not a concern for a once-per-launch check on a single-user tool. |
| `System.Text.Json` (already a project dependency) deserializing the response into a small `GitHubRelease { string TagName; GitHubAsset[] Assets }` / `GitHubAsset { string Name; string BrowserDownloadUrl }` DTO pair | Same class | Parse `tag_name` and the exe asset's `browser_download_url`/`name` out of the JSON response | No new dependency — the project already uses `System.Text.Json` for settings persistence; the same `JsonSerializer.Deserialize<T>` call shape applies here. Only 2 fields are needed from a much larger response payload, so hand-written minimal DTOs (matching only the consumed fields, ignoring the rest) are sufficient — `System.Text.Json` silently ignores unmapped JSON properties by default. |
| Semantic version embedded via `-p:Version=<tag-without-leading-v>` passed into `dotnet publish` from `release.yml`'s own trigger tag, compared at runtime via `Assembly.GetExecutingAssembly().GetName().Version` (or `AssemblyInformationalVersionAttribute`) | `release.yml` (new step) + a `VersionComparer` using `System.Version` | Know "am I already on the latest version" without hardcoding a version string in source | **Integration gap found:** `release.yml` currently does *not* pass a `-p:Version=` (or `-p:AssemblyVersion=`/`-p:FileVersion=`) into its `dotnet publish` call — the built exe has no version identifier tied to the git tag that triggered the release. This must be added as part of this milestone's work (e.g. `-p:Version=${{ github.ref_name }}` with the leading `v` stripped, since `<Version>` requires a numeric-dotted string) or the update checker has nothing reliable to compare against. `System.Version`'s `CompareTo` handles standard `major.minor.patch[.build]` comparison natively — no semver library needed as long as release tags stay to that shape (which `v1.0`/`v1.1`/`v1.2`/`v2.0`/`v2.1` already do). |
| Download the new exe directly into the **same directory** as the running exe (e.g. `RigToggle.App.update.exe`, not `%TEMP%`) via `HttpClient.GetStreamAsync` → `FileStream` | New `UpdateApplier` class | Avoids any cross-volume `File.Move` ambiguity during the swap step | Keeping the temporary download on the same volume as the installed exe guarantees the subsequent rename/move operations are same-volume renames (fast, atomic-ish, no copy-fallback edge cases), and sidesteps needing to reason about whether `%TEMP%` and the install directory share a drive letter on this particular machine. |
| Self-replace via the classic Windows "rename the running exe, then move the new one into its place" trick: `File.Move(currentExePath, currentExePath + ".old")` → `File.Move(downloadedExePath, currentExePath)` → `Process.Start(currentExePath)` → exit the current (old, now-renamed) process | New `UpdateApplier.ApplyAndRestart()` | Perform the actual in-place update of a currently-executing single-file exe without any separate updater/helper process | **This is the answer to "how a running self-contained single-file exe can safely replace itself":** Windows does not allow *overwriting or deleting* a running executable's file by default, but it explicitly *does* allow **renaming** it — this is long-established, documented Windows NT file-locking behavior (the image loader opens the running exe with sharing flags that permit rename, not delete/write) and is the mechanism virtually every "portable Windows app that self-updates" relies on instead of a separate updater process. No helper `.exe`, no zip extraction, no separate process needed — `File.Move` alone accomplishes both the rename and (for the new-exe-into-place step) the "install." On the *new* process's next startup, have it check for and delete any leftover `RigToggle.App.old.exe`/`.update.exe` sitting next to it (self-cleanup on the following launch, since the old process may still be mid-shutdown at the moment the new one starts). |
| Prompt-then-apply flow: check on launch → if newer found, show a confirm dialog (existing `MessageBox`-style pattern already used elsewhere in the app, e.g. Settings validation dialogs) → only download/apply on explicit user confirmation | `MainForm` startup path | Matches the milestone's explicit requirement: "prompt the user to confirm before downloading and applying" | No new UI framework needed — this is a `DialogResult.Yes`/`No` `MessageBox.Show` exactly like existing confirm dialogs in the codebase (`MonitorConfirmDialog` precedent), not a new capability. |

**Do this update check on a background thread / async, off the UI thread**, the same way the app already keeps monitor-hotplug and audio-device work off `Application.Run`'s message loop — a synchronous `HttpClient` call on `MainForm.Load` would visibly stall startup if GitHub is slow/unreachable, and a failed/unreachable check must be a silent no-op (log to the existing gated `debug.log`, don't block or error-dialog on "couldn't check for updates" — treat it like the optional companion-app/audio-device "skip cleanly" pattern already established for unset targets).

### 2. Single-Instance Guard + Focus-Existing-Window

| Technique | Where | Purpose | Why Recommended |
|-----------|-------|---------|------------------|
| `System.Threading.Mutex` (BCL), named `Global\RigToggle-{fixed-GUID}` | `Program.cs`, first line of `Main()`, before any `Application.Run`/form construction | Detect whether another instance of this exact app is already running, anywhere on the machine | This is still the current, standard .NET mechanism for single-instance detection (confirmed against current `System.Threading.Mutex` docs — unchanged, not deprecated). Use `new Mutex(true, name, out bool createdNew)`: if `createdNew` is `false`, another instance already holds it. The `Global\` prefix (vs. the default `Local\` session-scoped namespace) matters specifically because this app can be launched non-interactively via Registry `Run`-key autostart *and* interactively by the user in the same or a different session context — `Global\` guarantees the check holds across Remote Desktop / multi-session edge cases, whereas an unprefixed (session-local) mutex would silently fail to block a second instance launched from a different session. Use a fixed, hardcoded GUID (not derived from anything reflectable) baked into source, matching how a single-purpose personal tool's identity should be pinned. |
| Hold the `Mutex` object alive for the process lifetime (static field or `using` scoped around `Application.Run`), `ReleaseMutex()`/`Dispose()` in a `finally` around `Application.Run` | `Program.cs` | Prevent premature GC of the mutex handle and ensure it's released deterministically on normal exit (OS also reclaims it automatically if the process dies/crashes, so a crash doesn't permanently wedge future launches) | Standard defensive pattern for this exact primitive — an unreleased-but-abandoned mutex is not a leak risk here because Windows always releases mutex ownership when the owning process terminates, by design, whether or not `ReleaseMutex` was called. |
| Hand-written `RegisterWindowMessage("RigToggle_ShowExisting")` (once, at startup, by every instance) + `PostMessage(HWND_BROADCAST, registeredMsg, 0, 0)` from the *second* (rejected) instance, received by the *first* instance's `MainForm.WndProc` override | New `NativeMethods` P/Invoke additions (`RegisterWindowMessage`, `PostMessage`) alongside the existing hotkey/window-control ones; a new `case` in `MainForm.WndProc` | Signal the already-running instance to restore/focus/show itself when a duplicate launch is rejected | This is the standard, well-established WinForms single-instance pattern (Mutex-for-detection + `RegisterWindowMessage`/`PostMessage(HWND_BROADCAST,...)`-for-signaling), and it fits this codebase's existing conventions unusually well: `MainForm.WndProc` already intercepts a custom message (`WM_HOTKEY`) for the global-hotkey feature (Phase 9), so adding one more `case` for a second registered message is the same established pattern, not a new one. `RegisterWindowMessage` guarantees a machine-wide-unique message ID (Microsoft's own documented purpose for the API — exactly "for communication between two cooperating applications"), avoiding collisions with any other app's custom `WM_USER+n` messages. On receipt: if minimized/hidden (tray-only), restore + `Show()` + `SetForegroundWindow` (reuse the existing focus-related P/Invoke used for the Moza Companion relaunch, since `SetForegroundWindow` is already proven to work reliably for *this app's own* window — the H9 bug that ruled it out was specifically about manipulating a foreign process's window, not the app's own). |
| Do the Mutex check *before* `WindowsFormsApplicationBase`/tray/hidden-startup logic, so a rejected second launch (including a second `--tray` autostart-triggered launch) exits immediately without ever creating a `NotifyIcon`, hidden form, or hotkey registration | `Program.cs` `Main()` | Prevent duplicate tray icons, duplicate global hotkey registration attempts (which would fail loudly since `RegisterHotKey` cannot be double-registered by two processes for the same key), and duplicate autostart races | A second instance that got past the mutex check far enough to call `RegisterHotKey` would hard-fail that call (Win32 returns `ERROR_HOTKEY_ALREADY_REGISTERED`), which the existing TRIG-01 registration-failure-surfacing code would then show as a spurious user-facing error on every accidental double-launch — checking the mutex first avoids ever reaching that code path. |

**What this deliberately does *not* need:** any inter-process argument-passing, named pipes, or a full IPC protocol. `RegisterWindowMessage`/`PostMessage` here carries zero payload — it is a pure "wake up and show yourself" signal, not a channel for passing data between instances. This matches the project's own prior decision (v1.1 close) to permanently rule out CLI-trigger + single-instance IPC (TRIG-02/TRIG-03) as unnecessary complexity; that decision was about *external tools driving the app via CLI args*, which is a different, larger problem than *the app noticing it's already running and refocusing itself* — this section only solves the latter, and solves it with the smallest possible mechanism.

### 3. Further Self-Contained Exe Size Reduction (No IL Trimming)

| Technique | Verdict | Why |
|-----------|---------|-----|
| `<DebugType>none</DebugType>` + `<DebugSymbols>false</DebugSymbols>` in the publish profile | **Apply — free, zero risk, but confirm it's a housekeeping win, not a size win** | The project's Release build already produces a *separate* portable `.pdb` (SDK default `DebugType=portable`), which is never bundled into the single-file exe in the first place — the bundler only embeds assemblies actually needed at runtime, not companion debug symbol files. So this setting won't shrink `RigToggle.App.exe` itself; its value is skipping .pdb generation entirely in CI (smaller build artifacts, marginally faster publish), and guarding against ever accidentally switching to `DebugType=embedded` (which *would* bloat the DLL/bundle by baking debug info directly into it) — worth setting explicitly for the same "guard against a future accidental regression" reason `PublishTrimmed=false` is already set explicitly in the current `.pubxml`. |
| `PublishReadyToRun` / `PublishReadyToRunComposite` | **Do not use** | Confirmed directly against current Microsoft Learn docs: R2R ahead-of-time-compiled assemblies are "between two to three times larger" than IL-only assemblies, because they embed *both* the IL and the equivalent native code side by side. This is a startup-latency-vs-size tradeoff that points the wrong direction for this milestone's explicit size-reduction goal — R2R would very likely *increase* the exe size, not decrease it, even after compression. (It remains a legitimate lever for a future *startup-time* milestone, just not this one.) |
| Native AOT (`PublishAot`) | **Do not use, not officially supported for this app's UI framework** | WinForms is not officially supported under Native AOT as of .NET 10 — Microsoft/`dotnet/runtime` maintainers have acknowledged community interest but there is no supported path, and the unofficial community workarounds that exist rely on a `WinFormsComInterop` shim plus static-reachability analysis stricter than IL trimming, i.e. it carries the exact same "silently strips reachable COM/P-Invoke marshalling code" risk this project already ruled out `PublishTrimmed` for — arguably worse, since NativeAOT's analysis is less forgiving than the trimmer's. Not worth the risk for a personal tool with two fragile, undocumented-interface call sites (`IPolicyConfig`, CCD `SetDisplayConfig`). |
| .NET runtime "feature switches" (`EventSourceSupport=false`, `HttpActivityPropagationSupport=false`, `UseSystemResourceKeys=true`, etc.) | **Skip — no effect without trimming** | These `RuntimeHostConfigurationOption` switches work by telling the *trimmer* which code paths are provably dead so it can strip them; without `PublishTrimmed=true` enabled, setting them to `false` only flips a runtime behavior flag (e.g., disables event tracing at runtime) — the IL for that code is still fully present in the bundle either way, so there's no exe-size benefit to claim here while trimming stays off. Do not spend time on these for this milestone. |
| Keep the current bare `net10.0-windows` TFM — do **not** add a Windows-SDK-versioned suffix (e.g. `net10.0-windows10.0.19041.0`) even if a future feature tempts it | **Guard, not a new lever** | A Windows-SDK-versioned TFM pulls in the CsWinRT/Windows Runtime projection layer (needed only for WinRT/UWP-surface APIs like modern toast notifications, which this project has already explicitly ruled out — "Full Windows App SDK / MSIX toast packaging" is Out of Scope). Flagging this here because it's exactly the kind of edit a future "let's add a nicer toast" change could introduce without realizing it silently works against this milestone's size goal. |
| Keep `IncludeNativeLibrariesForSelfExtract=true` as-is; do not add `IncludeAllContentForSelfExtract` | **No change needed** | The former is already required (confirmed in the existing `win-x64.pubxml`) to get a literal single `.exe` with no companion native DLLs sitting next to it — removing it would *reduce* the main exe's bytes but reintroduce loose files, breaking the "one exe" distribution model, which is not the milestone's intent. The latter bundles arbitrary `Content` items too, which this project doesn't need and would only add bytes. |
| Optional, out-of-MSBuild-scope idea for a *future* milestone: replace the `NAudio.Wasapi` package reference with a second small hand-rolled `IMMDeviceEnumerator`/`IMMDeviceCollection`/`IPropertyStore` COM interop, following the exact precedent already set by the hand-rolled `IPolicyConfig` audio-switching interop | **Not recommended for v2.2 — code-level change, out of this milestone's explicitly MSBuild-only scope** | This project's only use of NAudio is device enumeration (`MMDeviceEnumerator`/friendly names/IDs) via `NAudio.CoreAudioApi`, which lives in the `NAudio.Wasapi` package — a package whose WASAPI capture/render classes this app never touches. Since the underlying `IMMDeviceEnumerator` COM interface is public, documented, and small, dropping the package dependency entirely (mirroring how `IPolicyConfig` was embedded rather than depending on the unmaintained `AudioSwitcher.AudioApi`) would shrink the bundle further than any MSBuild flag can. Surfaced here for visibility, but the milestone's own scoping ("safe MSBuild-level levers only") correctly excludes it — a code rewrite of the audio-enumeration layer is a bigger, riskier, differently-shaped change than a build-config tweak, and belongs in its own future-milestone decision, not bundled into this one under a "size reduction" label. |

**Honest ceiling:** after the four levers already shipped at v2.0 (57.79% reduction: compression, satellite-language trim, invariant globalization, NAudio meta-package split), the *only* remaining large wins documented anywhere (a real-world .NET self-contained-exe shrink case study reduced a 62 MB build to ~1 MB, 98.37%) came almost entirely from `PublishTrimmed` (the single biggest line item by far) and Native AOT/ILC-specific flags (`IlcDisableReflection`, `IlcFoldIdenticalMethodBodies`, `IlcOptimizationPreference:Size`, etc.) — both categories this project has correctly and deliberately excluded. Set expectations for this milestone's PERF requirement accordingly: `DebugType=none` is worth doing for hygiene, everything else in the table above is a guard against regression rather than a further cut, and the real next lever (NAudio→hand-rolled interop) is a code change, not a build flag, and is out of this milestone's stated scope.

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|--------------------------|
| Hand-rolled GitHub-Releases HTTP check + self-rename-and-relaunch (no package) | **Velopack** (successor to Squirrel.Windows, `Velopack` NuGet, actively maintained, `GithubSource` built-in) | If this project ever moves to a proper installer-based distribution (Setup.exe, install-to-`%LocalAppData%`) instead of a single portable exe. Velopack's own docs confirm it expects a formal "installed" app structure and throws `NotInstalledException` for apps run outside that structure — its "Portable" package mode exists but is still oriented around Velopack owning the app's on-disk layout (a separate `Update.exe` applies updates, not the running exe renaming itself). Adopting it now would mean restructuring `release.yml` around `vpk pack`/`vpk upload github` instead of the current plain `dotnet publish` + attach-exe-to-release flow — a bigger change than this milestone's "add auto-update to the existing distribution model" framing calls for. |
| Hand-rolled updater | **NetSparkleUpdater/NetSparkle** (`NetSparkleUpdater.SparkleUpdater` + `NetSparkleUpdater.UI.WinForms.NetCore`, actively maintained, Ed25519-signed appcasts, has a GitHub-appcast-generation tool) | If update integrity/authenticity verification becomes a real requirement (e.g. distributing to other users, not just yourself) — NetSparkle's Ed25519 signature verification is a genuinely stronger security posture than this project's plan (HTTPS-only, no additional package-signing) provides. For a single-user personal tool downloading its own exe over TLS from its own public GitHub repo, that extra signing/appcast-hosting machinery is overhead without a corresponding threat this project actually faces. |
| Hand-rolled updater | **Onova** (`Onova` NuGet, `GithubPackageResolver`, MIT, last released March 2025) | Closest in spirit to what's needed (portable-app-focused, GitHub-releases-aware), but its update-application model extracts a zip package and uses a *separate* updater executable that "will wait until all instances of the application have exited before applying an update" — i.e. it still assumes multi-file/zip packages and an external helper process, not a bare single exe renaming itself in place. Worth revisiting only if the app ever ships more than one file (e.g. a companion config schema, licenses, docs) that needs coordinated versioned replacement. |
| Hand-rolled updater | **AutoUpdater.NET** / **GitHubReleaseUpdater** | Both are smaller, older, single-maintainer libraries oriented around downloading and running an installer or unzipping a multi-file package, with less recent/less certain .NET 10 validation than the BCL-only approach. Neither offers enough over hand-rolled `HttpClient` + `File.Move` to justify taking on a third-party dependency for a mechanism this project can implement in well under 200 lines using only the BCL, matching the `IPolicyConfig` precedent. |
| `Mutex` + `RegisterWindowMessage`/`PostMessage(HWND_BROADCAST,...)` | Named `EventWaitHandle` + a background listener thread that `Invoke`s onto the UI thread on signal | Equally valid, slightly less Win32-P/Invoke-heavy alternative if a future maintainer prefers to avoid one more `DllImport` pair. Functionally interchangeable for this narrow "wake up and show yourself" need; chosen the `PostMessage` route here specifically because it reuses `MainForm.WndProc`'s already-established "intercept a custom window message" pattern from the hotkey feature, rather than introducing a second concurrency primitive (a background wait thread) alongside the `Mutex` already in play. |
| MSBuild-flag-only size levers | Replacing `NAudio.Wasapi` with hand-rolled `IMMDeviceEnumerator` COM interop | See the size-reduction table above — legitimate, but a code-level change explicitly out of this milestone's "MSBuild-level levers only" scope. Candidate for a future milestone if further size reduction is prioritized again. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| `Microsoft.VisualBasic.ApplicationServices.WindowsFormsApplicationBase.IsSingleInstance` | Pulls in the `Microsoft.VisualBasic` runtime assembly as a dependency purely for one boolean flag, and requires restructuring `Program.cs`/`Main()` around VB's `ApplicationBase` model instead of the project's existing plain `Application.Run` entry point — a disproportionate structural change (and an odd dependency for a C# codebase) for what a 10-line `Mutex` check already solves. | Hand-rolled `Mutex` check, as above. |
| Windows App SDK's `Microsoft.Windows.AppLifecycle.AppInstance.FindOrRegisterForKey`/`RedirectActivationTo` (the "modern" single-instance API) | Requires either MSIX packaging or at minimum bundling the Windows App SDK runtime — this project's constraints already explicitly rule out "Full Windows App SDK / MSIX toast packaging" as conflicting with the standalone self-contained-.exe distribution model. This API is designed for packaged/identity-bearing apps, which this app deliberately is not. | `Mutex` + `RegisterWindowMessage`/`PostMessage`, as above. |
| A full named-pipe or socket-based IPC channel for the single-instance signal | Overkill for a payload-free "you're already running, please show yourself" signal — and this project already made a permanent, explicit decision at v1.1 close to not build a CLI-trigger/IPC mechanism (TRIG-02/TRIG-03), for a related-but-larger problem. Building real IPC now for a strictly smaller need would quietly re-open a door the project closed on purpose. | `RegisterWindowMessage`/`PostMessage(HWND_BROADCAST,...)` — zero-payload, no persistent channel. |
| `PublishReadyToRun`/`PublishReadyToRunComposite` as a "size" lever | Increases assembly size 2-3x per current Microsoft Learn documentation — it is a startup-latency optimization, not a size optimization, and using it here would actively work against this milestone's PERF goal. | Leave `PublishReadyToRun` unset/false, as it already is. |
| `PublishAot` (Native AOT) | Not officially supported for WinForms as of .NET 10; unofficial community workarounds rely on static-reachability analysis at least as aggressive as the IL trimming this project already ruled out for its COM/P-Invoke-heavy surface, for the same underlying reason. | Leave trimming and AOT both off, as already decided; rely on the MSBuild-flag levers documented above. |
| Downloading the update .exe into `%TEMP%` and `File.Move`-ing it across volumes into the install directory without a copy-fallback | Cross-volume moves are not guaranteed to be a simple atomic rename on Windows and add unnecessary failure-mode surface (different drive letters, `%TEMP%` sometimes redirected to a different volume than the install directory) to a step that's already the most fragile part of the whole feature. | Download the new exe directly into the same directory as the currently-running exe, so every subsequent `File.Move` is guaranteed same-volume. |
