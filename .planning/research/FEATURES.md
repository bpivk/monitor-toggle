# Feature Research

**Domain:** Windows desktop utility maintenance features — self-update (GitHub Releases), single-instance guarding, self-contained exe size reduction
**Scope:** v2.2 milestone only. This is a maintenance/DX milestone, not a user-facing capability milestone — "features" here are operational behaviors of the app itself (how it stays current, how it prevents duplicate launches, how large it ships), not rig-toggle domain features. No competitor landscape applies; findings are drawn from .NET ecosystem standard practice for tray-resident desktop utilities.
**Researched:** 2026-08-18
**Confidence:** MEDIUM-HIGH. Two of three areas (self-update, exe size) verified directly against this repo's actual `.csproj`/`.pubxml`/CI workflow files (HIGH confidence, primary source — not inference). Ecosystem claims (Velopack behavior, GitHub API limits, Mutex/foreground patterns) are corroborated across multiple independent web sources (MEDIUM) but not cross-checked against official Microsoft Learn API reference pages directly (one fetch attempt 403'd; treat GitHub-rate-limit specifics as MEDIUM, not HIGH).

## Feature Landscape

### Table Stakes (Users Expect These)

For a tray-resident, autostart, GitHub-distributed personal utility, these are the "of course it should do this" baseline — a single user running it daily across months would notice their absence immediately.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Startup update check against GitHub Releases `tag_name` vs running version | Any tool distributed via tagged GitHub Releases that a user runs indefinitely (this one autostarts on boot) needs a way to notice it's stale, or it silently rots — exactly the failure mode v2.2 exists to close | LOW-MEDIUM | GitHub REST API: `GET https://api.github.com/repos/{owner}/{repo}/releases/latest` returns JSON with `tag_name` and `assets[].browser_download_url`. **Must set a `User-Agent` header** — GitHub returns 403 "Please make sure your request has a User-Agent header" on requests without one (confirmed via GitHub's own troubleshooting docs and multiple corroborating issue threads). Unauthenticated rate limit is 60 requests/hour per source IP (GitHub Docs, fetched directly — HIGH confidence on this specific number) — trivially fine for a once-per-launch check by a single-user tool, no auth token needed. |
| Confirm-before-install prompt (not silent, not manual-only) | Already the user's explicit, locked-in choice (PROJECT.md) — matches how most personal/prosumer tray utilities behave (not enterprise silent-patch, not "check menu item only") | LOW | A simple modal/toast: "vX.Y.Z is available — update now?" Yes/No. No new UI framework needed — this project already has `MessageBox`/toast (`NotifyIcon.ShowBalloonTip`) precedent from Phase 8 (NOTIF-01). |
| Version comparison that tolerates the `v` prefix GitHub tag convention | This repo's own tags are `v1.0`, `v1.1`, `v2.0`, `v2.1` (per `release.yml`'s `tags: ['v*']` trigger and PROJECT.md's own version history) — a naive string-equality or unstripped-`v` comparison will silently never detect an update, or always detect one | LOW | Strip leading `v`, parse as `System.Version` or `NuGet.Versioning.SemanticVersion` (BCL `System.Version` is sufficient here — this project's tags are plain `MAJOR.MINOR`, not full semver with pre-release suffixes). |
| Applying the downloaded exe and relaunching without requiring the user to manually delete/replace the old file | "Prompt then apply" implies apply actually completes the swap — a prompt that just opens a browser to the releases page is not what was scoped (explicit: "download and applying it, then relaunch") | MEDIUM | The genuinely fiddly part — see Differentiators/Complexity notes below. Windows cannot overwrite a running exe's file *contents*, but **can rename it while running** (well-established, multiple independent sources) — this is the standard technique, not a helper-process requirement in this specific case (single exe, no companion DLLs to swap). |
| Detecting an already-running instance and refusing to start a second one | Standard, decades-old expectation for any tray-resident app — most users' mental model is "double-clicking the exe again either does nothing new or shows me the window that's already there," never "now there are two icons in my tray" | LOW | `System.Threading.Mutex` with a fixed, GUID-based name (e.g. `Global\\RigToggle-{fixed-guid}`) checked at the very top of `Main()`, before `Application.Run()`. This is the textbook .NET pattern, unchanged across .NET Framework → .NET 10 (corroborated by multiple independent sources: AutoIt Consulting guide, KomuraSoft guide, Microsoft TechNet wiki archive). |
| Focusing (not just detecting) the existing instance on a duplicate launch attempt | Already the user's explicit, locked-in choice — "focus existing instance" not "silent exit" | LOW-MEDIUM | `Process.GetProcessesByName(...).MainWindowHandle` + `ShowWindow(SW_RESTORE)` (in case it's minimized/tray-only) + `SetForegroundWindow`. This app already has the exact analogous pattern for the Moza Companion app (`LaunchOrFocus`) — same shape, reusable mental model, not a new technique for this codebase. One real gotcha: if the first instance is fully hidden (tray-only, window destroyed rather than minimized, e.g. launched via `--tray`), `MainWindowHandle` can be `IntPtr.Zero` — same "running but no window to manipulate" edge case this project's own CLAUDE.md already documents for the Moza Companion detection logic; the fix there generalizes here too (need the first instance's message-loop to `Show()` itself in response to a signal, not rely purely on an external `SetForegroundWindow` against a handle that may not exist). |

### Differentiators (Where the Real Complexity Lives)

Not "nice to have" in the product sense — these are the parts of otherwise-standard features that are genuinely tricky for *this* codebase specifically, and where a naive implementation will pass a quick manual test but fail on the rig later.

| Feature | Why It's Actually Complex | Complexity | Notes |
|---------|-------------------|------------|-------|
| Version-stamping the running exe so it has something to compare against | **This is a real, currently-unmet prerequisite, not a hypothetical.** Verified directly against this repo: no `<Version>`, `<AssemblyVersion>`, or `<InformationalVersion>` property exists anywhere in `RigToggle.App.csproj`, `RigToggle.Core.csproj`, `RigToggle.Windows.csproj`, or any `Directory.Build.props` (none exists). `release.yml` publishes via `dotnet publish ... -p:PublishProfile=win-x64` with no `-p:Version=` override tied to the pushed tag. The running exe today has no reliable, self-contained way to know "what version am I" at runtime. | MEDIUM | This has to be solved *before* "compare running version to latest release" can work at all — it's a hard dependency, not a parallel task. Standard fix: have `release.yml` pass `-p:Version=${{ github.ref_name }}` (stripped of the `v` prefix) into the publish step, so `Assembly.GetExecutingAssembly().GetName().Version` (or `InformationalVersion` via `AssemblyInformationalVersionAttribute`, which supports full semver strings unlike `AssemblyVersion`) reflects the actual tag at build time. Flag this explicitly for roadmap sequencing — it's infrastructure, not user-facing, and easy to under-scope as "just call the GitHub API" without noticing there's nothing local to compare it to yet. |
| Actually replacing a self-contained single-file exe while it's running, then relaunching | The general "self-update on Windows" problem (file lock) is well-documented and has three common solution shapes: (1) separate tiny helper exe/process that waits for the main process to exit then swaps files, (2) a dynamically-written batch/PowerShell script that does the same with a `timeout`/retry-delete loop, (3) rename-in-place (Windows permits renaming an in-use exe/DLL even though it forbids overwriting its content) followed by copying the new download to the original filename and spawning it. | MEDIUM-HIGH | For **this specific app** (one exe, no companion DLLs since it's `PublishSingleFile`), rename-in-place is the lowest-risk option: on confirm, download new exe to a temp path → verify it's a valid PE / non-zero size → rename running exe (`RigToggle.App.exe` → `RigToggle.App.exe.old`) → move downloaded exe into the original path → `Process.Start` the new exe with a "just updated" flag → `Environment.Exit` the old process. Clean up the `.old` file on the *next* launch (can't delete it while the just-exited process might still hold a lingering handle in some AV-scanning edge cases) — check-and-delete-if-exists at startup, same shape as this project's own `ToggleInProgressMarker` crash-recovery pattern (DISPLAY-13, Phase 16), which is a nice structural precedent to reuse. Batch-script and separate-helper-exe approaches both work but add a second artifact to build/ship/trust — unnecessary complexity for a single-portable-exe app; reserve for a future where the app grows companion files. |
| Whether to adopt a ready-made update framework (Velopack) vs. hand-roll the above | Velopack (the actively-maintained 2026 successor to the now-effectively-abandoned Squirrel.Windows) is the closest thing to a "just use this" answer, and does support GitHub Releases as an update source natively (`GithubSource`). **But its packaging model is fundamentally an installer model**, not a portable-exe model: it produces `Update.exe` + versioned app subfolders under `%LocalAppData%`, with the "real" exe living several directories deep and Start Menu shortcuts created on install. A community issue thread (`velopack/velopack#314`) shows other developers hitting exactly this friction wanting a true single-portable-exe result and not getting one out of the box. | N/A (decision, not implementation) | **Recommendation: do not adopt Velopack for this milestone.** It would mean abandoning the "standalone .exe" distribution constraint (CLAUDE.md, unchanged since v1.0) and the existing `release.yml` asset-attachment flow (`files: .../RigToggle.App.exe`) in favor of Velopack's own release-asset shape (`releases.win.json` + squashed installer packages) — a bigger, riskier change than the milestone's own scope implies, for a single-user personal tool that doesn't need delta updates, multi-channel releases, or auto-managed uninstall registry entries. The hand-rolled rename-in-place approach above is roughly 60-100 lines of code against APIs this codebase already uses elsewhere (`HttpClient`, `Process.Start`, file I/O) — smaller footprint than taking on a new packaging paradigm. Revisit Velopack only if a future milestone drops the standalone-.exe constraint. |
| Reliably stealing foreground focus for the existing instance from a freshly-launched second process | Windows deliberately restricts `SetForegroundWindow` to prevent background apps from stealing focus — a naive call from an arbitrary already-running background process silently fails (flashes the taskbar icon instead). **This project has direct prior scar tissue here**: the Moza Companion focus bug (H9, resolved 2026-07-26) was caused by exactly this class of Win32 focus-manipulation fragility, and the eventual fix there was to *avoid* raw `SetForegroundWindow`/`ShowWindow` against a stale external window entirely, relaunching via `ShellExecute` instead. | MEDIUM | The single-instance case is meaningfully *different* from H9 in one important way: the process calling `SetForegroundWindow` here is the **freshly-launched second instance itself** (not a long-running third-party process reaching into another app later) — Windows generally grants a just-launched process foreground-change rights for a brief window, which is why "second instance calls `SetForegroundWindow` on the first instance's handle, then exits" is the standard, working pattern cited across multiple independent sources. Still worth a real rig-hardware verification pass given this project's own history of Win32 focus assumptions not holding up in practice (Phase 12's `Application.SetColorMode`/`FlatStyle.System` bet was also rig-disproven despite being "documented" behavior) — do not treat this as risk-free just because it's the textbook pattern. |
| Squeezing further exe-size reduction without IL trimming, when the easy MSBuild levers are already spent | v2.0 (Phase 18) already claimed the obvious wins: `EnableCompressionInSingleFile`, `SatelliteResourceLanguages=en`, `InvariantGlobalization=true`, and splitting the NAudio meta-package down to `NAudio.Wasapi` only — a 57.79% cut. The remaining safe (non-trimming) lever pool is thinner and lower-yield. | LOW-MEDIUM (small effort, correspondingly modest additional gain — set expectations accordingly) | **Candidate additional levers, all MSBuild-property-only, no IL trimming:** (1) `UseSystemResourceKeys=true` — replaces embedded exception-message strings with resource key lookups, a documented, safe (non-trimming) size lever, real but small. (2) `DebugType=none` — **verified against this repo's actual csproj: no `DebugType` is currently set, meaning the SDK default (`portable`, i.e. a *separate* sidecar `.pdb` file) is already in effect, not `embedded`.** This means `DebugType=none` would only stop generating the loose `.pdb` next to the exe — it would **not** shrink the bundled single-file exe itself, since portable PDB content was never inside it. Flag this explicitly so a future phase doesn't spend effort expecting an exe-size win that structurally can't happen under the current (default) `DebugType`. (3) Double-check whether `WindowsDisplayAPI` or `NAudio.Wasapi` pull in any further per-RID native asset bloat beyond what the v2.0 satellite-language trim already addressed — worth a `dotnet publish` output audit (inspect the pre-bundle `bin/Release/.../publish` folder contents) before assuming there's nothing left, rather than guessing. **Anti-lever, explicitly do not pursue:** `PublishReadyToRun=true` — confirmed via multiple sources to *increase* exe size (it embeds AOT-compiled native code images alongside/instead-of IL, trading size for cold-start speed) — the opposite of this milestone's goal, and irrelevant to it (v2.0 already accepted a compression-driven cold-start cost tradeoff going the other direction, per `18-RESEARCH.md` Pitfall 1). |

### Anti-Features (Commonly Reached For, Wrong Fit Here)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|------------------|-------------|
| Velopack / Squirrel.Windows / ClickOnce / MSIX-based update+install framework | "Don't reinvent the wheel, use the mature library" is generally sound advice, and Velopack specifically is the current, well-maintained SOTA for .NET desktop auto-update | All of these are fundamentally *installer* frameworks — they assume (and often enforce) an installed-app model: versioned subfolders under `%LocalAppData%`/`Program Files`, Start Menu shortcuts, uninstall registry entries, and (for MSIX) app package identity. This project's constraint has been "standalone .exe, no separate runtime install" since v1.0 and "distributed via a public GitHub repo... tagged GitHub Releases" (a single attached `.exe` asset) since v1.2 — adopting any of these frameworks means abandoning that distribution model mid-milestone for a benefit (delta updates, multi-channel, rollback) a single-user personal tool doesn't need | Hand-rolled rename-in-place self-update (~60-100 LOC) against APIs already used elsewhere in this codebase — see Differentiators above |
| `Microsoft.VisualBasic.ApplicationServices.WindowsFormsApplicationBase`'s built-in `IsSingleInstance`/`StartupNextInstance` for single-instance guarding | It's a genuine BCL-adjacent, fully supported-on-.NET-10 mechanism that "just works" with an event hook, and shows up as the "one line" answer in a lot of single-instance guides | Requires taking a project reference on the `Microsoft.VisualBasic` assembly inside a C# WinForms project — works technically, but is a legacy-flavored dependency surface for a codebase with an otherwise deliberately minimal, hand-rolled Win32/P-Invoke style (per this project's own STACK.md philosophy of avoiding unnecessary packages). Multiple community sources note this as functionally fine but stylistically the less common choice for pure-C# projects in 2026 | `System.Threading.Mutex` + `Process.GetProcessesByName`/`MainWindowHandle` — 2 BCL types, no extra assembly reference, matches the codebase's existing hand-rolled Win32-interop conventions (P/Invoke `IPolicyConfig`, `WindowsDisplayAPI` usage style) |
| Silent background auto-update (download + apply with no prompt) | "Modern apps just update themselves, why bother the user" — this is genuinely how Chrome/most browsers and many SaaS-adjacent tools behave, and it is less friction | **Already explicitly rejected by the user for this milestone** (PROJECT.md: "notify then confirm," not silent). Silent updates for a tool that directly controls display topology and audio routing carry real risk if a bad release ships — a confirm step gives the user a natural moment to notice/skip a known-bad version before it lands on the rig mid-session | The scoped "notify → confirm → download → apply → relaunch" flow, already the locked-in design |
| Manual-check-only ("Check for Updates" menu item, no automatic prompt) | Simpler to implement, zero risk of an unwanted popup interrupting a session, common in more conservative/enterprise tooling | **Already explicitly rejected by the user for this milestone** (PROJECT.md: check happens automatically "on launch," not only on manual request) — and given this app autostarts on boot and is often tray-resident for long stretches, a manual-only check means updates are discovered rarely, defeating the "keep the app current" goal stated in the milestone Goal | On-launch automatic check (already scoped), with a manual "Check for Updates" menu item as a reasonable *addition*, not a *replacement* — cheap to add given the check logic already exists, worth considering as a small bonus if time allows, but not a substitute for the automatic on-launch check |
| PublishReadyToRun for size reduction | "AOT/ReadyToRun sounds like it should make things smaller and faster, it's a common .NET perf lever" | Confirmed via multiple independent sources: R2R **increases** self-contained exe size (it adds native-compiled code images on top of/instead of IL) — it's a startup-*speed* lever, not a size lever, and moves the metric in the wrong direction for this milestone's PERF-03-equivalent goal | The MSBuild levers already listed under Differentiators (`UseSystemResourceKeys`, verifying `DebugType`'s actual effect, auditing per-package native asset bloat) |
| IL trimming (`PublishTrimmed=true`) or NativeAOT (`PublishAot=true`) for size reduction | Both are the single biggest documented .NET size-reduction levers by a wide margin, and it's tempting to reconsider "just this once" given how much smaller they make output | **Explicitly out of scope per the milestone's own framing** ("safe MSBuild-level levers only — no IL trimming") and per this project's own established, already-validated CLAUDE.md guidance: this codebase's COM interop (`IPolicyConfig`) and P/Invoke marshalling (`WindowsDisplayAPI`/CCD) code paths are exactly the kind static reachability analysis misidentifies as unreachable and strips — and NativeAOT relies on the *same* underlying trim-style static analysis, so it inherits the identical risk, not a safer alternative | Continue restricting exe-size work to non-trimming MSBuild properties only, as already decided |

## Feature Dependencies

```
Version-stamp the exe at build time (release.yml -p:Version=<tag>)
    └──requires (hard prerequisite)──> Runtime version comparison against GitHub Releases tag_name
                                            └──requires──> Auto-update check-on-launch
                                                               └──requires──> Confirm-prompt UI
                                                                                  └──requires──> Download + rename-in-place apply
                                                                                                     └──requires──> Relaunch new exe

Single-instance Mutex guard (independent, no dependency on the above)
    └──enhances──> Focus-existing-instance-on-duplicate-launch
                       └──touches shared ground with──> Moza Companion's existing LaunchOrFocus pattern (reusable precedent, not a hard dependency)

Exe-size levers (fully independent of both auto-update and single-instance work)
    └──conflicts with (already-resolved, do not revisit)──> IL trimming / NativeAOT
```

### Dependency Notes

- **Version-stamping requires updating `release.yml` before any runtime check code has something real to compare.** This is the single most important sequencing fact in this research: a phase that writes the "check GitHub Releases, compare version, prompt" logic without first confirming `-p:Version=` (or equivalent `AssemblyInformationalVersionAttribute` wiring) flows from the git tag through to the running exe will either hardcode/stub the current-version value or silently always/never detect an update. This should be its own early sub-step or explicit prerequisite check within the auto-update phase, not assumed already-solved.
- **Rename-in-place apply requires the confirm-prompt and download steps to already exist** — it's the last link in a strictly linear chain (check → prompt → download → apply → relaunch), each step depending on the previous succeeding; there's no meaningful way to build "apply" before "download" exists to hand it a file.
- **Single-instance guarding is fully independent of auto-update** — no shared code, no ordering constraint between them. They can be built as two unrelated phases in either order, or even in parallel by different contributors, without conflict.
- **Exe-size reduction is fully independent of both other features** — pure MSBuild/`.csproj`/`.pubxml` configuration work with no runtime code dependency on the update or single-instance logic. Natural candidate for a small, low-risk, easily-sequenced-anywhere phase (e.g., done first as a quick win, or last as cleanup) — unlike the other two, it has no other phase gating it or gated by it.
- **Focus-existing-instance conflicts with nothing but shares idiom, not code, with the existing Moza Companion `LaunchOrFocus`/H9 precedent** — worth having whoever implements it read that resolved-debug writeup (`.planning/debug/resolved/moza-foreground-focus.md`) first, since it's the closest prior art this specific codebase has for "Win32 focus manipulation that looked fine in testing and then wasn't."

## MVP Definition

Given this is a scoped maintenance milestone (not an MVP-from-zero product), "MVP" here means the minimum that satisfies the milestone's stated Goal — not a further-reduced subset.

### Launch With (v2.2)

All three target features as scoped in PROJECT.md — none of them decompose further into a smaller shippable slice without leaving the milestone's own stated goal unmet:

- [ ] Version-stamping infrastructure (`release.yml` tag → build-time `Version`/`InformationalVersion`) — hard prerequisite for auto-update, must land first within that feature's phase(s)
- [ ] On-launch GitHub Releases version check + confirm prompt — the actual user-facing "auto-update" behavior
- [ ] Download + rename-in-place apply + relaunch on new version — completes the update loop; a check-only implementation without this does not satisfy "download and applying it, then relaunch" as scoped
- [ ] Named-Mutex single-instance guard at process startup — prevents duplicate instances
- [ ] Focus-existing-instance-on-duplicate-launch — the user's explicit choice over silent-exit or message-then-exit
- [ ] Additional safe MSBuild exe-size levers (`UseSystemResourceKeys`, verified `DebugType` audit, per-package native asset check) — "just smaller is better," no target number, so any measurable additional reduction satisfies this

### Add After Validation (v2.2.x / backlog, not this milestone)

- [ ] Manual "Check for Updates" menu item (in addition to, not instead of, the automatic on-launch check) — cheap add-on once the check logic exists, but not scoped this milestone
- [ ] WM_COPYDATA/named-pipe IPC between instances (richer than bare focus-stealing — e.g., passing along CLI args from the second launch attempt to the first instance) — explicitly the TRIG-02/TRIG-03 territory this project already decided (v1.1 close) is permanently out of scope; the v2.2 single-instance guard should stay a pure focus-and-exit mechanism, not reopen that door

### Future Consideration (beyond v2.2)

- [ ] Reconsidering Velopack or another packaging framework — only if a future milestone deliberately drops the standalone-.exe constraint (would be a distribution-model change, not an incremental feature)
- [ ] Delta/differential update downloads — meaningless overhead for a single-user tool checking its own GitHub repo, not worth the complexity a full update framework would bring just to get it
