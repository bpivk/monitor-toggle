# Rig Toggle

## What This Is

A Windows GUI utility that switches between "normal desktop mode" and "Moza rig mode" with one click — from the GUI, a tray menu, or a global keyboard shortcut. Toggling to rig mode disables the primary monitor at the OS level (so games default to the rig monitor instead), switches the default audio output to the rig speakers, and launches the Moza Companion app. Toggling back applies Normal mode's own explicitly configured monitor set and audio device — symmetric with how Rig mode already works — and minimizes the Moza Companion app. Both the companion app and either mode's audio device can be left unset, in which case that toggle step is skipped cleanly with no error, while a target that's configured but genuinely broken (missing file, removed device) still surfaces as a real failure. MainForm is a monitor-tile dashboard — one clickable tile per detected monitor with live on/off status, keyboard-navigable, an Identify action, and hotplug-reactive refresh — that lets the user enable/disable any monitor on demand, independent of the Rig/Normal toggle; the standalone Manual Monitor Panel this absorbed has been retired. The Rig/Normal toggle is a custom-drawn, accent-tinted toggle-switch control sitting directly below the tile row. A `Help > About` menu shows the running version and a "Check for Updates" button with always-visible inline feedback (up to date / update found / check failed) — the app's sole manual update-check entry point, reached from a `MenuStrip` on the main window rather than the tray menu or Settings. The app runs tray-resident with autostart, refuses to launch a second instance (focusing the existing one instead), and checks GitHub Releases on launch for a newer version, prompting to confirm before downloading, verifying (SHA256), applying in place, and relaunching — with a retained-backup/auto-rollback safety net so a failed or crash-looping update can never leave the app stranded. The app supports arbitrary multi-monitor configurations (not just a single primary monitor). The GUI follows the Windows system light/dark theme live by default, with an optional manual System/Light/Dark override that locks the theme independent of the OS setting; interactive elements pick up the live Windows accent color. SettingsForm uses an intentional two-column-plus-shared layout instead of the earlier organically-grown one. The tray/exe icons use a shape-distinct monitor-vs-steering-wheel motif. Distributed via a public GitHub repo (`bpivk/monitor-toggle`) with a GitHub-ready README, CI, tagged releases (now three-component semver, `vX.Y.Z`), and a self-contained exe roughly 58% smaller than pre-v2.0. Built for a single user's personal sim-racing rig setup.

## Core Value

A single reliable action that disables the primary monitor (not just powers it off) and switches audio output — so games that mishandle secondary-monitor launches (e.g. BeamNG.drive minimizing itself) reliably open on the rig monitor — and just as reliably applies Normal mode's own explicitly configured monitor/audio state on toggle-back. (Revised at v2.0: the original "restores everything to exactly how it was before" framing described snapshot-restore, which v2.0 replaced with an explicit, symmetric Normal-mode configuration — see DISPLAY-10/AUDIO-04 and the v2.0 archive below.)

## Current State

**Shipped: v2.2 Auto-Update, Single-Instance Guard & Smaller Footprint (2026-08-29)**

v2.2 closed three independent gaps in the app's lifecycle as a background/tray-resident tool. A named cross-process Mutex now guarantees exactly one Rig Toggle process ever runs, focusing the existing instance on a duplicate launch attempt. The self-contained exe shrank a further 5.26% via an MSBuild deny-list target excluding unused WinForms Design/VB assemblies (no trimming/AOT). And the app now checks GitHub Releases on launch, prompts before downloading, verifies the download's SHA256 before touching anything, self-replaces at its original path, and relaunches — with a retained-backup/applied-but-unconfirmed-marker/auto-rollback state machine so a failed or crash-looping update can never leave the app stranded. Two follow-up quick tasks (built after the phase itself closed) added a `Help > About` dialog as a more discoverable update-check entry point and then consolidated onto it exclusively, fixing a real bug along the way: the tray/Settings "Check for Updates" paths relied entirely on a tray-balloon toast that silently no-ops whenever the tray icon isn't visible (the default) — the About dialog now reports its result inline, guaranteed. `UpdateVersionComparer` was also extended from Major.Minor-only to full three-component semver (`vX.Y.Z`) to support ongoing patch releases.

The milestone's single riskiest mechanism — renaming a running self-contained single-file exe and relaunching it — was **genuinely rig-verified live** against a real `v2.2.1 → v2.2.2` release cut for that purpose, not just code-reviewed. Four remaining UAT scenarios (interrupted-update recovery, auto-rollback timing under a 10s window, the `--tray` on-launch check path, and real-release-notes Markdown rendering) were closed by explicit operator sign-off rather than independent testing — recorded as genuine open follow-up items, not fabricated passes (see `26-UAT.md` and `26-VERIFICATION.md`'s "Post-Verification Update").

**Not yet done:** the four README screenshot placeholders (`docs/screenshots/*.png`) are still broken-image links from v1.2 — real screenshots must be supplied by the user from the rig (no Windows GUI in this build environment). Now more out of date than ever given the MainForm redesign.

### Out of Scope

- Guaranteed true "close main window, keep process running" — not reliably possible to force externally on an arbitrary app; best-effort minimize is the fallback, not a guarantee
- Elevated/Task-Scheduler autostart — would reintroduce the UIPI cross-process-focus problem the v1.0 H9 debug session worked around; plain non-elevated Registry `Run` key is sufficient
- Hotkey chord/sequence engine — unused complexity for a single binding, single action
- Full Windows App SDK / MSIX toast packaging — conflicts with the standalone self-contained-.exe distribution constraint
- Per-monitor sets keyed by index/position instead of stable `DevicePath` — already burned once in v1.0
- Toggle history/log (LOG-01) — deferred twice now (v1.0, v1.1); tracked in v2 backlog, still lower priority
- CLI trigger + single-instance IPC (TRIG-02/TRIG-03) — scoped as Phase 10 for v1.1, never built. Tray (Phase 8) and global hotkey (Phase 9) already cover toggling without the GUI open; decided permanently out of scope at v1.1 close, not a v2 candidate.

## Context

## Constraints

- **Platform**: Windows only — no cross-platform requirement
- **Distribution**: Standalone .exe — implies a compiled/self-contained runtime (e.g. .NET self-contained publish), not a bare interpreted script requiring a separately-installed runtime
- **Monitor control**: Must achieve true OS-level display disable/enable (Windows CCD API or equivalent), not merely a monitor power signal — power-off leaves Windows still treating the display as connected/active
- **Audio control**: Must be able to set the Windows default audio playback device programmatically
- **App control**: Must be able to detect if the Moza Companion app is already running (to avoid duplicate launches) and manipulate its window (focus / minimize) via Win32 window APIs
- **Target state**: Both Rig mode and Normal mode apply an explicit, independently configured monitor set and audio device (revised at v2.0 — superseded the original v1.0 "snapshot the state before toggle and restore it exactly" constraint; the snapshot-restore mechanism itself was removed in Phase 18/CLEANUP-01)
