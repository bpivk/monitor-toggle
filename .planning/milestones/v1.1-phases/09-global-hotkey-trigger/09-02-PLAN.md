<objective>
Add the global-hotkey registration mechanism and its window-message handler to MainForm — the third trigger source alongside the GUI button (Phase 5) and tray menu (Phase 8) — plus the shared register/unregister helpers every entry point calls.

Purpose: RegisterHotKey needs the message-pump window MainForm already owns; WM_HOTKEY (0x0312) must be intercepted in a WndProc override and dispatched to a handler structurally identical to TrayToggleMenuItem_Click (D-03). Centralizing the register/unregister logic as reusable MainForm methods lets both the startup path (09-03 Program.cs) and the Settings-Save path (09-03 SettingsForm) drive registration through one helper (D-04), and lets OpenSettingsDialog suppress the hotkey while Settings is open (D-07).

Because `NativeMethods` is `internal` to `RigToggle.Windows` and `RigToggle.App` is NOT granted `InternalsVisibleTo`, MainForm cannot call the P/Invoke directly (CS0122). A thin `public` wrapper class (`GlobalHotkey`) is added in `RigToggle.Windows` — matching the existing public-adapter convention (`WindowsAutostartConfigurator`, `WindowsAppController`, `WindowsAudioController`, `WindowsMonitorController` are all `public` precisely because they are the cross-assembly surface `RigToggle.App` consumes). MainForm calls `GlobalHotkey.*`, never `NativeMethods.*`.

Output: internal P/Invoke signatures in NativeMethods; a public GlobalHotkey wrapper in RigToggle.Windows; WndProc override, WM_HOTKEY handler, three registration helper methods, and Settings-dialog bracketing in MainForm.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Other local processes → MainForm HWND | Any local process running as the same user can PostMessage a WM_HOTKEY to MainForm's window, or itself RegisterHotKey the same combination first. |
| settings.json → RegisterHotKey args | HotkeyModifiers/HotkeyKey ints flow from a user-editable file into the fsModifiers/vk P/Invoke arguments. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-02 | Spoofing | Forged WM_HOTKEY from another local process triggering an unwanted toggle | accept | Single-user local desktop utility: any process running as this user already has the user's full privileges and could invoke the same monitor/audio toggle by many other means; the toggle is not a security-sensitive operation. The forged message still routes through ToggleOrchestrator's reentrancy guard, so a message flood cannot corrupt state — it is bounded to at most sequential, non-overlapping toggles. |
| T-09-03 | Denial of Service | Repeated failed RegisterHotKey (e.g. a conflicting app holds the combo) | accept | Registration is attempted at most once per startup and once per Settings-Save — there is no retry loop. MOD_NOREPEAT prevents a held key from generating an autorepeat storm. Failure is traced + toasted, never looped. |
| T-09-04 | Tampering | Garbage HotkeyModifiers/HotkeyKey hand-edited into settings.json | mitigate | TryRegisterConfiguredHotkey treats a null/incomplete pair as "nothing to register" and any RegisterHotKey rejection as a clean false (surfaced, not crashed); casts are of already-typed int? values, no parsing. |
| T-09-05 | Elevation of Privilege | RegisterHotKey requiring or granting elevated rights | accept | RegisterHotKey/UnregisterHotKey are non-elevated user32 calls on the app's own window; the app deliberately stays asInvoker (no manifest change in this plan), so no privilege boundary is crossed. |
| T-09-SC | Tampering | Package installs | accept | Zero new dependencies — hand-rolled user32 P/Invoke per CLAUDE.md, no NuGet/npm/pip/cargo install. Package-legitimacy gate not applicable. |

No HIGH-severity threat applies: no network surface, no untrusted remote input, no privilege change, and the one local-spoofing vector is bounded by the existing reentrancy guard and is not security-sensitive for a single-user rig utility.
</threat_model>
