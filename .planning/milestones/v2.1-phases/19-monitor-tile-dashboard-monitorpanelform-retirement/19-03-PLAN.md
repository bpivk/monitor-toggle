<objective>
Make the tiles live: port `MonitorPanelForm`'s mutation path (lease → confirmation gate → stale-path re-validation → `IMonitorController` call → refresh) and its Identify handler into `MainForm`, filling the two stubs Plan 02 left behind.

Purpose: this is the phase's highest-regression-risk work. Every behaviour here is already rig-verified inside the retiring panel; the job is to move it without "simplifying" any of it, and to fix the one thing that genuinely must change — Identify's numbering source, which used `DataGridView` rows that no longer exist.
Output: modified `src/RigToggle.App/MainForm.cs`. `MonitorPanelForm` still exists and is still reachable from the tray, so the two implementations can be compared before Plan 04 deletes the old one.
</objective>

<hard_constraints>
Load-bearing rules. Violating any one fails the phase even if tiles appear to work.

1. NEVER write a zero-survivors / "at least one monitor must stay active" pre-check anywhere in `MainForm`. The DISPLAY-12 guard lives solely inside `WindowsMonitorController.DeactivateMonitors`, is topology-aware (recomputes survivors from live CCD state at mutation time, unlike a UI-cached `IsActive` snapshot that can be stale by click time), and having exactly one implementation IS the requirement. Surface the adapter's `InvalidOperationException.Message` verbatim; never reword it per call site.
2. NEVER route a tile action through `ToggleService`, `ToggleOrchestrator.ToggleToRigMode`, or `ToggleOrchestrator.ToggleToNormalMode`. Those are three-step sequences that would switch audio, launch or minimize the companion app, and persist a `ToggleMode` the user never asked for. The only permitted orchestrator call from a tile action is `BeginExclusiveMonitorAccess()`.
3. NEVER write `AppSettings.MonitorsToDisable`, `MonitorsToEnable`, `NormalMonitorsToDisable`, `NormalMonitorsToEnable`, or `IModeStore` from a tile action. Tile actions are ad-hoc and session-local. The ONE permitted settings write in this plan is `SkipMonitorConfirmation = true` from the confirm dialog's "don't ask again" checkbox.
4. NEVER "unify" the tile action's explicit lease with `BtnToggle_Click`'s reliance on `ToggleOrchestrator`'s internal `_busy` guard, now that both live in the same class. They are not redundant: the lease exists to block a concurrent `WM_HOTKEY`-triggered toggle from starting WHILE `MonitorConfirmDialog.ShowDialog()`'s nested message loop is pumping messages, which has nothing to do with which class hosts the code (19-RESEARCH.md Pitfall 3). Leave `BtnToggle_Click` completely untouched.
5. Identify must number overlays from the SAME canonical `_lastKnownMonitors` list, in the same order, that Plan 02's `RefreshMonitorTiles()` used to number the tiles — and must increment the counter even for skipped monitors, so overlay number N always corresponds to tile number N (19-RESEARCH.md Pitfall 6). This is a deliberate behaviour change from the retired panel, whose `BtnIdentify_Click` did NOT increment on skip; note it in a comment.
6. NEVER use `System.Windows.Forms.Screen.*`. GDI `Screen.DeviceName` and CCD `DevicePath` are disjoint identity spaces with no built-in mapping; overlays are positioned exclusively from `CaptureState()` snapshots (17-RESEARCH.md Pitfall 2).
7. Do NOT delete `MonitorPanelForm`, `trayMonitorsMenuItem`, `TrayMonitorsMenuItem_Click`, `OpenMonitorPanel()`, or the panel factory in this plan. Plan 04 does that.
</hard_constraints>
