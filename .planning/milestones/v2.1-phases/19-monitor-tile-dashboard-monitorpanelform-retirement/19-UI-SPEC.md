# Phase 19 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a native Windows Forms (.NET 10, `net10.0-windows`) desktop application, not a web app. The shadcn/component-registry model from this template is not applicable — see Design System and Registry Safety sections below for the WinForms-equivalent contract. This document follows the same platform-adapted shape established by `12-UI-SPEC.md`/`13-UI-SPEC.md`/`17-UI-SPEC.md`.
>
> **Phase framing:** MainForm's `btnMonitors` button and `trayMonitorsMenuItem` are **deleted** this phase (TILE-07), not restyled — their capability is absorbed into a new `MonitorTile` control row inline on `MainForm`. `MonitorPanelForm` is deleted last, after the tile row is proven. This phase repositions the existing plain-`Button` Rig/Normal toggle (MAIN-01) but does **not** restyle it — the custom track+thumb switch redesign is Phase 20's scope (THEME-08), explicitly out of scope here. Accent-color *live reading* (THEME-07) and manual theme override (THEME-09) are also out of scope — this phase uses this codebase's existing **static** accent literal (`#005A9E` dark / `SystemColors.Highlight` light), the same one `ThemeApplier`/`13-UI-SPEC.md`/`17-UI-SPEC.md` already established, not a new live-reading mechanism.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn/npm component registries do not apply to a native WinForms desktop project |
| Preset | not applicable |
| Component library | raw `System.Windows.Forms` controls (`Form`, `Panel`/`FlowLayoutPanel`, `Button`, `Label`) plus one **new** owner-drawn `MonitorTile : UserControl` (`Controls/MonitorTile.cs`) — the first custom-drawn control in this codebase's `RigToggle.App` project, following the exact GDI+ idioms already proven in `MonitorPanelForm.CreateStatusDot` and `RigToggle.IconGen/IconGeometry.cs` |
| Icon library | none — all icon geometry procedurally drawn via `System.Drawing`/`GraphicsPath` (ported subset of `IconGeometry.BuildMonitorPath`, per D-01/Pitfall 7 — `RigToggle.IconGen` itself stays dev-time-only and unreferenced) |
| Font | Segoe UI, 9pt system default — inherited via `Form.Font`/`AutoScaleDimensions = (7F, 15F)`, matching every existing form in this codebase. This phase introduces no new font size or weight (see Typography below) |

**Visual anchor:** The tile row is MainForm's primary visual focal point — largest surface area, first in reading/tab order (D-09), and the only element carrying the accent-color fill (Color, below). The Identify button, toggle, and Settings gear are progressively de-emphasized below it, both in position and in visual weight.

## Spacing Scale

Declared values (must be multiples of 4), applied to `MainForm`'s new tile-dashboard layout:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon top-padding inside a tile; gap between a tile's icon and its number label |
| sm | 8px | Gap between the Identify button and the Rig/Normal toggle (pixel-matches the existing `btnToggle`→`btnSettings` 8px gap this codebase already established) |
| md | 16px | `MainForm`'s outer margin on all four edges (unchanged from the current 16px convention); gap between the tile strip and the Identify button |
| lg | 24px | Gap between the Rig/Normal toggle and the de-emphasized Settings gear button (MAIN-02's "no longer competing" spacing cue — deliberately more breathing room than the sm/md gaps above it) |
| xl | 32px | Reserved; not used by this phase's compact dashboard |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions: **12px** tile-to-tile gap inside the tile strip (a multiple of 4, but not one of the named tokens above — kept as its own explicit value rather than forced onto `sm`(8)/`md`(16) since neither reads right between fixed-size 72px tiles; see Tile Geometry Contract). This mirrors this codebase's existing convention (`17-UI-SPEC.md`'s own "reused/adjacent-to-existing-control positions keep pixel parity" exception) of naming a deliberate one-off rather than silently drifting off the 4px grid.

## Typography

This codebase has a single, deliberate typography discipline carried forward from `13-UI-SPEC.md`/`17-UI-SPEC.md`: **one system font, one size, one weight, everywhere** — differentiation is achieved via layout position, icon shape/color, and grouping, never via font size or boldness. Verified: zero `Bold`/`FontStyle` usage anywhere in `RigToggle.App` today. This phase introduces **zero** new typography — the tile's number label uses the exact same 9pt Regular as every other control, and the primary-monitor badge (D-03) is a pure shape (no glyph/text — see Color/Tile Geometry Contract) specifically to avoid needing a second, illegibly-small font size inside a 14px badge.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 9pt (Segoe UI, system default) | Regular (400) | native control auto-height (n/a) |
| Label | 9pt (Segoe UI, system default) | Regular (400) | native control auto-height (n/a) — this includes each tile's number label |
| Heading | 9pt (Segoe UI, system default) | Regular (400) | native control auto-height (n/a) — no distinct heading style exists in this codebase; do not introduce one |
| Display | not applicable this phase | — | — | the 120pt Bold Display role from `17-UI-SPEC.md` belongs to `MonitorIdentifyOverlay`, which is reused unchanged (Owner retargeted only) — this phase does not modify its typography |

## Color

This app themes via `Application.SetColorMode` plus the existing `ThemeApplier`/`WindowsThemeProvider` explicit-override pattern. Every new control this phase adds (`MonitorTile`, the Identify button, the new gear-icon Settings button) must be run through `ThemeApplier` (or a new sibling helper following the identical `try { } catch { /* cosmetic-only */ }` shape) and wired into **both** `MainForm.OnThemeChanged` and `MainForm.InitializeTrayState()` — see Pitfall 1 / Component Behavior Contract below. No new colors are invented; every literal below is reused verbatim from `ThemeApplier`/`13-UI-SPEC.md`/`17-UI-SPEC.md`.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Light: `SystemColors.Control`/`Window` (~#F0F0F0); Dark: `#202020` (`Color.FromArgb(32,32,32)`) | `MainForm` background / window chrome (unchanged) |
| Secondary (30%) | Light: `SystemColors.Control`; Dark: `#2D2D30` (`Color.FromArgb(45,45,48)`) | Button backgrounds (`ThemeApplier.ThemeButton`'s existing values, reused for the Identify and Settings-gear buttons); a tile's hover-state background tint only (rest-state tile background is transparent/matches the form) |
| Accent (10%) | Light: `SystemColors.Highlight`; Dark: `#005A9E` (`Color.FromArgb(0,90,158)`) | Reserved **only** for: (1) a tile's ON-state monitor-icon fill (D-02's "solid-filled in an active color"), and (2) the 2px keyboard-focus ring drawn around the currently focused tile. No other element in this phase uses the accent color — not the Identify button, not the Settings gear, not the toggle button (Phase 20's scope), not the primary badge. |
| Destructive | not applicable this phase | Disabling a monitor via a tile is a reversible, guarded action (TILE-03's confirmation gate + DISPLAY-12's zero-survivors guard already cover the risk) — consistent with this codebase's existing convention of never using red/destructive styling for monitor-disable, carried forward unchanged from `17-UI-SPEC.md` |

Additional small-area semantic colors (icon glyphs only, each covering well under 5% of any surface — not part of the 60/30/10 chrome split, do not treat as "accent"):

| Role | Value | Usage |
|------|-------|-------|
| OFF-state tile outline | Light: `SystemColors.GrayText`; Dark: `#A0A0A0` (`Color.FromArgb(160,160,160)`, reused verbatim from `ThemeApplier.ApplyHotkeyIdleUnconfigured`'s existing dark literal) | The hollow/outline-only monitor icon on a tile whose monitor is currently OS-disabled (D-02's OFF state — outline, no fill) |
| Primary-monitor badge | `#F5A623` (`Color.FromArgb(245,166,35)`) — single literal, theme-independent (same "deliberate isolated exception to the chrome palette" treatment `17-UI-SPEC.md` already applied to the Identify overlay's black/white) | D-03's small corner marker on the primary monitor's tile only. Deliberately distinct from both the green/red status-dot precedent (avoids confusion with on/off semantics) and the accent blue (avoids diluting the accent-reserved list above) |

Accent reserved for: **ON-state tile icon fill, and the tile keyboard-focus ring. Nothing else.** Do not use the accent blue for the Identify button, the Settings gear icon, tile hover backgrounds, or the primary badge — those follow `ThemeApplier.ThemeButton`'s existing gray-scale palette or the dedicated badge color above.

## Tile & Layout Geometry Contract

Supplements the Spacing Scale above with the exact starting values for this phase's one genuinely new visual element (`MonitorTile`). These are **prescriptive starting values** (informed by `19-RESEARCH.md`'s Assumption A2), not pixel-perfect final numbers — confirm proportions on the rig at 2 monitors (the user's actual setup) and adjust only the constants below, never the underlying fraction-based `OnPaint` approach (Pitfall 5: derive all tile-interior geometry from `ClientSize`, never hardcode pixel literals inside `MonitorTile.OnPaint` itself — these constants size the *tile*, not raw pixels inside its paint routine).

| Property | Value | Notes |
|----------|-------|-------|
| Tile size | 72px × 88px, fixed | D-07 — tiles never shrink regardless of monitor count |
| Tile gap | 12px | Horizontal and vertical gap between adjacent tiles in the `FlowLayoutPanel` |
| Tiles per row before wrap | 4 | D-05's "~4-5 tiles" cap. Enforced by `LayoutDashboard()` setting `tileStrip.Size` explicitly (`MaxTilesPerRow = 4`), not by `MaximumSize` — `WrapContents = true` then wraps within that computed width. Strip width at 4 tiles is `(72 + 2*6) * 4 = 336px`, i.e. the 324px tile+gap span plus the 6px outer margins on each edge. |
| Tile order | Ascending by the one canonical, `DevicePath`-sorted `GetAllMonitors()` order, established once per refresh and reused identically by tile numbering AND the ported Identify handler (D-08, Pitfall 6 / `19-RESEARCH.md` Open Question 1's recommendation) | Never re-sort independently in two places — one shared ordered list, two consumers |
| Icon area within tile | 48px × 48px, top-aligned, horizontally centered, 4px top padding | Reuses the ported `BuildMonitorPath` screen/neck/base silhouette (D-01), stroke-then-fill per Pattern 3 |
| Number label within tile | Below the icon, 4px gap, horizontally centered, 9pt Segoe UI Regular | The monitor's number in the canonical order above, e.g. `1`, `2`, `3` |
| Primary badge | 14px-diameter filled 5-point star, centered at the icon area's top-right corner (straddling the icon's outer boundary, half in/half out) | D-03 — shape-only marker (no glyph/text), deliberately distinct from the ON/OFF outline+fill signal so the two never visually collide |
| Focus ring | 2px accent-colored rounded rectangle (4px corner radius), drawn flush inside the tile's outer bounds when `Focused` | Pitfall 4 — a custom `UserControl` gets no free focus-visual; must be drawn explicitly |
| Tile hover background | Secondary (30%) color tint on `MouseEnter`, cleared on `MouseLeave` | Optional polish signaling clickability to mouse users; must not be the sole affordance (keyboard users rely on the focus ring, not hover) |
| Content-width floor | 288px | Matches this codebase's existing `btnToggle`/`btnSettings` width — at 1-3 tiles (fits under 288px), the tile strip is horizontally centered within this floor rather than the window shrinking narrower than the existing button width |
| Content-width ceiling before wrap | 324px of tiles+gaps (4 tiles), 336px as the measured strip width including its 6px outer margins | Beyond 4 tiles, additional tiles wrap to row 2+ instead of widening further (D-05). `LayoutDashboard()` derives this as `perRow * (TileWidthPx + 2 * TileMarginPx)`, all `Scaled()`. |
| Window auto-size | **Manual, not `Form.AutoSize`.** `MainForm.AutoSize` stays `false` (default) and `tileStrip.AutoSize = false`; `LayoutDashboard()` computes every position and the final `ClientSize` arithmetically from tile count, via a font-derived `Scaled()` helper (divisor `15f` = the form's own `AutoScaleDimensions.Height`). It runs on every population and hotplug, so the window still resizes instantly (no animation) on every tile-row content change, including the first `Show()` after a `--tray` hidden start (D-04/D-06). | Deliberate deviation from `AutoSize = true`: `19-RESEARCH.md` Open Question 2 (RESOLVED) flags that no form in this codebase has ever used `AutoSize`, and its layout-pass timing is unproven on the `--tray` hidden-start path where `InitializeTrayState()` — not `OnLoad`/`OnShown` — does the population work. Arithmetic layout depends on no WinForms layout pass having run, removing that risk. `FixedDialog` blocks user resize only, not programmatic resize. Correct first-`Show()` sizing under `--tray` is still verified as a rig checkpoint (`19-05-PLAN.md`). Do not "simplify" this back to `AutoSize = true`. |

## Component Behavior Contract

Beyond copy/color/spacing, these interaction details are load-bearing for the executor and are derived directly from `19-CONTEXT.md`'s locked decisions and `19-RESEARCH.md`'s patterns/pitfalls — included here so the plan doesn't have to re-derive them:

- **`MonitorTile : UserControl`**: dumb/presentational only — never calls `IMonitorController` directly (Pattern 1); exposes `SetState(MonitorInfo monitor, int displayNumber)` and a single `event EventHandler? ActionRequested` fired on click AND on `Space`/`Return` while focused (`ProcessCmdKey` override, Pitfall 4). `TabStop = true`; tab order follows the canonical `DevicePath`-sorted order (D-08/Pitfall 6), same order as the number labels and Identify.
- **Mutation orchestration**: `MainForm` remains the sole caller of `IMonitorController.ActivateMonitors`/`DeactivateMonitors`, and the sole caller of `ToggleOrchestrator.BeginExclusiveMonitorAccess()` for tile-originated actions. The lease-then-`using` + confirm-dialog + post-dialog re-validation structure is ported from `MonitorPanelForm.DisableMonitor` **verbatim, with zero simplification** (Pitfall 3) — this is not redundant with `BtnToggle_Click`'s reliance on `ToggleOrchestrator`'s internal `_busy` guard; both must coexist unchanged.
- **Confirmation gate (TILE-03)**: shown only when a tile disables a monitor AND `!AppSettings.SkipMonitorConfirmation`. Enabling a monitor via a tile is never gated, matching the retired panel's behavior exactly.
- **Safety guard (DISPLAY-12)**: no new pre-check is written in `MonitorTile` or in `MainForm`'s tile-click handler — the zero-survivors guard lives solely in `WindowsMonitorController.DeactivateMonitors`, unchanged.
- **Live refresh (TILE-06)**: `MainForm` subscribes to `Microsoft.Win32.SystemEvents.DisplaySettingsChanged` once, in its constructor, and **never unsubscribes** until process exit (Pitfall 2) — do not copy `MonitorPanelForm`'s subscribe/unsubscribe-on-`FormClosed` pattern, `MainForm`'s lifecycle is app-lifetime, not closable-and-reopenable.
- **Identify (TILE-04)**: single shared button (D-11), ported from `MonitorPanelForm.BtnIdentify_Click` with `Owner` retargeted to `MainForm` and numbering re-sourced from the same canonical ordered list the tile strip uses (not `DataGridView` rows, which no longer exist) — see Tile & Layout Geometry Contract's "Tile order" row.
- **Theming pipeline (Pitfall 1)**: every new control (`MonitorTile` instances, the Identify button, the Settings gear button) must be added to **both** `MainForm.OnThemeChanged` and `MainForm.InitializeTrayState()` — a control themed in only one call site renders correctly at whichever theme Windows happened to be in at startup, then freezes in that mode while surrounding buttons keep flipping live. Verify by flipping Windows Light↔Dark live while the app is running, and by launching with `--tray` and checking the tiles are correctly themed on first `Show()`.
- **DPI (Pitfall 5)**: all `MonitorTile.OnPaint` geometry (icon, number label, badge, focus ring) must be derived from `ClientSize`/fractional coordinates, matching `IconGeometry.cs`'s existing idiom — never hardcoded pixel literals. Verify at 125%/150% Windows display scale as a rig-only checkpoint (cannot be verified in this build environment).
- **GDI handle discipline**: cache brushes/pens/paths as instance fields inside `MonitorTile`, allocated once per instance, not reallocated on every `OnPaint` call — same discipline `MonitorPanelForm._dotActive`/`_dotInactive` already established, now load-bearing for a long tray-resident session with a live-repainting control.
- **Deletion order (TILE-07)**: `MonitorPanelForm.cs`/`.Designer.cs`, `btnMonitors` (+ its Designer entry and `BtnMonitors_Click` handler), `trayMonitorsMenuItem` (+ its Designer entry and `TrayMonitorsMenuItem_Click` handler), and the `MonitorPanelForm` factory wiring in `Program.cs` are removed **after** the tile row is proven working end-to-end (build order per `19-RESEARCH.md`'s Summary) — not deleted first, not left half-wired.
