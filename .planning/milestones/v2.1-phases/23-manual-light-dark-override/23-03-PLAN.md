<known_residual_risk>
Read this before writing the rig checklist — check 12 exists specifically for it.

`Application.SetColorMode` is the only lever WinForms exposes for application-level dark mode (confirmed against the .NET 10 reference assembly: the API surface is `SetColorMode`, the read-only `ColorMode`/`IsDarkModeEnabled` properties, and the three-member `SystemColorMode` enum — nothing else). Microsoft's guidance is to call it before any window is created, and it is **not documented as re-theming an already-created control tree** when called again at runtime.

23-01 handles this correctly for two of the three forms: `SettingsForm` and `MonitorConfirmDialog` are constructed fresh on every open, so the color mode already in force at construction time governs their whole native control tree. `MainForm` is the app's single long-lived window, and every visible element on it other than the window background is explicitly themed by `ThemeApplier` (tiles, toggle switch, both buttons) or by an explicit `ForeColor` assignment (`lblNoMonitors`) — which is why 23-01 added `ThemeFormSurface` for that one background and nothing else.

The residual is therefore precisely bounded: **the `SettingsForm` you are standing in while you click a radio button.** Its buttons, combo boxes, grids and hotkey box will re-theme (they are `ThemeApplier`-managed), but its labels, checkboxes, radio buttons and panel backgrounds depend on a runtime `SetColorMode` call taking effect on already-created controls. If it does not, that dialog renders half-themed until it is closed and reopened.

Note what is *not* at risk even in that case: the override itself is never lost, MainForm is fully correct, and any window opened afterwards is fully correct — so Success Criteria 1 and 3 are unaffected and Criterion 2 fails only for the in-place repaint of one already-open dialog.

**Pre-authorised gap-closure direction if check 12 fails** (record it, do not implement it here): extend `ThemeApplier` with an explicit `ForeColor`/`BackColor` pass over `SettingsForm`'s own surface, driven from its existing `OnThemeChanged`, using the same literals the rest of the class already uses (`Color.FromArgb(32, 32, 32)` background, `Color.FromArgb(240, 240, 240)` foreground, `SystemColors.Control`/`SystemColors.ControlText` in light). `Control.ForeColor` and `Control.BackColor` are ambient in WinForms, so setting them on the form itself cascades to every child that has not overridden them — which is every label, checkbox and radio button in this form. That keeps the fix to one targeted helper rather than a recursive control-tree walk, which this codebase forbids (12-RESEARCH.md Pitfall 1/8).
</known_residual_risk>

  <what-built>
    Settings now has a Theme choice — three options reading "System (default)", "Light" and "Dark", sitting in the shared section at the bottom of the Settings window, below "Start with Windows". "System (default)" is selected until you choose otherwise, and it means exactly what the app has always done: follow whatever light/dark mode Windows itself is set to, live.

    Picking "Light" or "Dark" locks the app to that theme and repaints it right away — the main window, the Settings window you are standing in, and any confirmation dialog opened afterwards. This is deliberately the only field in Settings that takes effect before you click Save; every other field still waits for Save. Clicking "Discard Changes", pressing Esc, or closing Settings with the X puts the theme back to whatever was last saved. Only "Save Changes" makes the choice stick across restarts.

    Underneath, the three places in the code that each independently decided "is dark mode on right now" now all ask one shared resolver, and the application-level colour mode that Windows uses to paint plain controls is now derived from your locked choice instead of from the Windows setting. That second part is the fix for the specific failure this phase exists to prevent: with a lock set, flipping Windows' own theme should no longer drag the app along.

    Nothing about monitors, audio, the companion app, the hotkey, or the tray changed. No new setting other than the theme choice, no new dialog, no new wording anywhere else.

    One thing genuinely needs your eyes: check 12. Windows does not officially support changing an app's colour mode after its windows already exist, so the Settings window you are standing in when you click "Dark" may or may not fully repaint its plain controls (its checkbox and radio text, its background) in place. Everything else — the main window, and Settings the next time you open it — should be correct regardless. Check 12 is what settles it, and a FAIL there is a known, already-scoped follow-up, not a surprise.
