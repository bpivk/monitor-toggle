# Phase 23 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase is a Windows desktop utility (WinForms, C#/.NET 10) — there is no web stack,
no component registry, and no shadcn ecosystem to gate. The `<shadcn_gate>` in the
gsd-ui-researcher instructions is not applicable; `components.json` does not exist and
will not be created (confirmed: `ls src/RigToggle.App/*.csproj` shows
`Microsoft.NET.Sdk` + `UseWindowsForms=true`, no Node/React/Vite tooling anywhere in the
repo). All design-contract sections below are adapted to native WinForms idioms rather
than left blank, per the researcher's "be prescriptive, not exploratory" mandate.

## Typography

This codebase sets **no per-control `Font` overrides anywhere** in `SettingsForm` — every
label and checkbox inherits the single Form-level default (confirmed by grep: zero
`Font = new System.Drawing.Font(...)` assignments in `SettingsForm.Designer.cs`). This
phase's new controls follow that same convention exactly — one size, one weight,
project-wide:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (radio option text: "System (default)" / "Light" / "Dark") | 9pt (Segoe UI, inherited Form default) | Regular (400) | native — WinForms `RadioButton` default vertical metrics, not explicitly set (matches every existing `CheckBox`) |
| Label (new "Theme:" group caption) | 9pt (Segoe UI, inherited Form default) | Regular (400) | native — matches `lblHotkeyCaption`/`lblMonitorCaption` |
| Heading | n/a | n/a | Not applicable — `flpShared` is a deliberately flat, unlabeled stack with no sub-section headings (Phase 22 D-02: "one flat top-down stack, no sub-grouping"); this phase's small "Theme:" caption is a *field* label, same tier as "Hotkey:", not a section heading |
| Display | n/a | n/a | Not applicable to a Settings dialog |

Deviation from the generic 3-4-size/2-weight template baseline is intentional: this is a
native-control WinForms form, not a web page, and the project's own established
convention (confirmed across `SettingsForm.Designer.cs` in full) is exactly one inherited
size/weight throughout. Introducing a second size or a bold weight for this phase's radio
group would be the actual inconsistency.

## Color

WinForms native controls (`RadioButton`, `CheckBox`, `Label`) do **not** get explicit
`ThemeApplier` color overrides in this codebase — they are themed automatically by
`Application.SetColorMode(SystemColorMode.System)`, called once per `OnThemeChanged`/Load
(confirmed: `ThemeApplier.cs` has zero `ThemeCheckBox`/`ThemeRadioButton`/`ThemeLabel`
methods, and none of the 4 existing checkboxes in `flpShared` appear in `SettingsForm.cs`'s
`OnThemeChanged` re-theme list — only `Button`, `ComboBox`, `DataGridView`, and `TextBox`
need explicit overrides because those are the control types this codebase's own code
comments document as *not* reliably picking up native dark-mode coloring). **The new
`RadioButton`s and caption `Label` require zero new `ThemeApplier` code** — they inherit
correct light/dark coloring automatically, exactly like their sibling checkboxes.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Light: `SystemColors.Control` (native) / Dark: `Color.FromArgb(32,32,32)` (applied by `Application.SetColorMode(System)`, the same literal `ThemeApplier.ThemeMonitorTile`/`ThemeToggleSwitch` use for their own background) | Form/window background — the radio group's parent (`pnlThemeReserved` → `pnlSharedSection`) surface |
| Secondary (30%) | Same as Dominant — WinForms/THEME-05 convention distinguishes "card" (`pnlSharedSection`) from "page" via a 1px `BorderStyle.FixedSingle` border only, not a separate fill color (confirmed: `pnlSharedSection` sets no distinct `BackColor`) | `pnlSharedSection`'s flat-bordered card boundary around the whole shared section, including this phase's radio group |
| Accent (10%) | The OS's own native accent-tinted radio-fill dot inside whichever option is currently selected — rendered automatically by Windows' visual-styles engine under `Application.SetColorMode(System)`, **not** a manually-set `Color.FromArgb` literal | Reserved for: the selected `RadioButton`'s inner dot only. No other element in this phase uses accent color — unlike `ToggleSwitch`/`MonitorTile` (Phase 20/21), this phase does **not** wire `IThemeProvider.AccentColor` into any new control; THEME-09 is scoped to light/dark only (ARCHITECTURE.md confirms `OverridableThemeProvider` passes `AccentColor`/`AccentColorChanged` through unmodified) |
| Destructive | n/a | Not applicable — no destructive action exists in this phase's scope; switching the radio selection is a non-destructive, instantly reversible live preview (D-01/D-02) |

## Interaction Contract

Governs how the radio group behaves — locked by CONTEXT.md D-01/D-02/D-03/D-04, restated
here as the concrete visual/interaction contract the executor implements against:

1. **Immediate apply (D-01):** Clicking any of the 3 radio buttons repaints the running
   app's theme *immediately* — `MainForm`, `SettingsForm` itself, and `MonitorConfirmDialog`
   (if currently open) all re-theme before Save is clicked. This is the one field in
   `SettingsForm` that does not wait for Save — deliberate, not a bug to "fix" toward
   consistency with every other field.
2. **Discard reverts the preview (D-02):** Clicking "Discard Changes" after previewing an
   unsaved selection reverts the live theme back to whatever was last *persisted*
   (`AppSettings.ThemeOverride`), or to System/live-follow if nothing was ever saved. Only
   "Save Changes" persists the new selection.
3. **Close-without-save matches Discard (D-03):** Closing `SettingsForm` via the window's
   X button — which today already resolves to the same `CancelButton = btnDiscardChanges`
   path (`SettingsForm.Designer.cs`: "declarative Discard button — no extra FormClosing
   handler needed") — must revert the theme preview identically to explicit Discard. No new
   close-handling pattern is introduced; this phase rides the existing one.
4. **Zero-exception reach (D-04):** All three of the codebase's current independent
   `IsDark`/`IsDarkTheme` resolution points (`MainForm` line 199, `SettingsForm` line 210,
   `MonitorConfirmDialog` line 63) must visibly honor the override with **zero**
   live-Windows-flip leakage on any surface — this is a design requirement, not just an
   implementation detail: a user who locks Dark must see Dark everywhere, including a
   currently-open confirm dialog, even if Windows itself flips to Light while the app is
   running.
5. **No new visual "dirty" indicator:** The radio group does not introduce a title-bar
   asterisk or other unsaved-changes marker beyond what already exists for other fields in
   this form (none exists today) — the live-preview *is* the feedback that a change was
   made; Save/Discard behave exactly as they do for every other field.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5). Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many /
> long-text). Empty-state and error-state COPY live in `## Copywriting Contract` above.

Element classified: `theme-override-radio-group` — "System/Light/Dark radio group filling
Phase 22's reserved `pnlThemeReserved` slot" — engine-detected kinds (compiled
`ui-consideration-probe.cjs`, re-run at Step 9.5 against the authoritative engine rather than
trusted from research-time authoring): **`form` + `static-content`** — the word "radio" trips
the `form` cue (shared with genuine data-entry radio/checkbox fields) and "labels" trips
`static-content`; both are surface-word matches, not a claim this is a submittable form.
Confirmed via propose-then-confirm: no additional kind (e.g. `interactive-control`) changes
which categories apply here, since `form ∪ static-content` is already the superset that would
result from also including `interactive-control` (loading/error/long-text are covered by all
three kinds' cue sets).

Applicable categories for `form ∪ static-content`: empty, loading, error, partial, overflow,
long-text (per the compiled taxonomy; populated/zero-one-many do not apply to either kind).

Applicable state considerations resolved: 4 covered (explicit), 0 backstop, 2 dismissed, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | theme-override-radio-group | ✅ covered | "No override set" is not an unhandled empty/blank state — it IS the documented default (D-07): the radio group always renders with one option pre-selected (System when `ThemeOverride` is `null`). There is no rendered state where all three radio buttons are unselected. |
| loading | theme-override-radio-group | ✅ covered | Population is a synchronous local read (`ISettingsStore.Load().ThemeOverride`) inside `SettingsForm_Load` — no network/async I/O exists on this path, so no loading state (spinner/skeleton) is ever needed or shown. |
| error | theme-override-radio-group | ✅ covered | A 3-option radio group cannot hold an invalid selection. | partial | theme-override-radio-group | ⛔ dismissed | WinForms `RadioButton`s in one container group are mutually exclusive — exactly one is always selected. There is no state where the group is "partially filled"; the category doesn't map onto a single-select radio group. |
| overflow | theme-override-radio-group | ⛔ dismissed | All 3 labels are short (≤15 chars), fixed, English-only literals locked by D-06/D-07 — never dynamic or user-supplied, so no container/text can ever overflow. Structurally the same guarantee as the long-text row below. |
| long-text | theme-override-radio-group | ✅ covered | All 3 labels ("System (default)", "Light", "Dark") are fixed, short, English-only literal strings locked by D-06/D-07 — never dynamic, never user-supplied, never subject to truncation/wrap handling. |
