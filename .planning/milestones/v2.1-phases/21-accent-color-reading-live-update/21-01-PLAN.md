<objective>
Turn `IThemeProvider` into a source of the user's real, live Windows accent color, and make `WindowsThemeProvider` the one component that reads it and announces changes.

Purpose: Every accent-tinted element in this app currently reads a hardcoded `Color.FromArgb(0, 90, 158)` / `SystemColors.Highlight` placeholder. THEME-07 requires the real thing. This plan builds only the producer side — the contract, the two OS reads, and the change notification — so that Plan 02's consumer swap is a pure repoint with no new logic in it.
Output: An extended `IThemeProvider`, a registry-primary/DWM-fallback accent read in `WindowsThemeProvider`, one new P/Invoke declaration, an extended test double, and one new contract test. Build green, 82 tests passing. No visible UI change yet — `MainForm` still uses its own placeholder until Plan 02.
</objective>

<hard_constraints>
1. **Do not add a second `SystemEvents.UserPreferenceChanged` subscription** (D-02, `research/ARCHITECTURE.md` Anti-Pattern 2). The whole solution must end this plan with exactly one `+=` and one `-=` for that event, both in `WindowsThemeProvider`. Do not create a new class that implements `IThemeProvider` or a separate accent provider.
2. **Do not add a public façade class** for `DwmGetColorizationColor` (no `DwmAccentColor.cs`). `DwmTitleBar.cs` exists only because a *different* assembly needs an `internal` member; `WindowsThemeProvider` lives in `RigToggle.Windows` alongside `NativeMethods` and calls it directly.
3. **Do not persist the accent color.** No `AppSettings` field, no `settings.json` key, no cached-across-runs value. It is read live, exactly like `CurrentTheme`.
4. **Do not change `CurrentTheme` / `ThemeChanged` / `ReadThemeFromRegistry` / `Dispose`.** The existing theme block inside `OnUserPreferenceChanged` must survive byte-for-byte; the accent block is appended as an independent second block, not merged into it and not gated behind its `changed` flag.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Windows registry (`HKCU\Software\Microsoft\Windows\DWM\AccentColor`) → app process | Untrusted-shaped input crosses here. The value is current-user-writable, so any process running as this user (including a misbehaving or malicious one) can set it to an arbitrary type, an absent value, or an arbitrary 32-bit number. |
| `dwmapi.dll` (native, out-of-process API surface) → app process | An `out` parameter marshalled back from native code, plus an HRESULT that may be non-`S_OK`. The DLL itself is loaded by name, not by full path. |
| `SystemEvents.UserPreferenceChanged` callback thread → UI thread | The read/diff/raise runs on a thread this app does not own. An unhandled exception on that thread terminates the process; a raced write corrupts the last-known value. |
| App → `%APPDATA%\RigToggle\debug.log` | The resolved accent color is written to an opt-in local log file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-21-01 | Tampering | `ReadAccentColorFromRegistry` — malformed or hostile `AccentColor` value (wrong type, e.g. `REG_SZ`/`REG_QWORD`; absent value; absent key; arbitrary DWORD) | mitigate | Type-gate with `if (raw is not int i) return null;` before any arithmetic, `?.` on the key handle so an absent key yields null, whole body in `try`/`catch { return null; }`; a null result falls through to the DWM path, which itself falls back to `SystemColors.Highlight`.
