## Unregistered Flags

New attack surface identified during implementation with no mapping to any declared threat ID in the Phase 14 threat model. These are **WARNING**, not blockers — `block_on: high` in this run's config does not require stopping the phase for these, but they should be triaged and either mapped to a future threat entry or fixed.

| Flag | Category | Component | Finding | Source |
|------|----------|-----------|---------|--------|
| UF-14-01 | Elevation of Privilege | `.github/workflows/build.yml` | No explicit `permissions:` block. The job runs on `pull_request` (and `push`) and executes `dotnet restore`/`build`/`test`, which can run arbitrary MSBuild-target/NuGet-restore-time code from PR-controlled `.csproj`/`NuGet.config` content, under whatever the repo/org's default `GITHUB_TOKEN` scope happens to be. T-14-02's declared mitigation text is explicitly scoped to `release.yml` only ("release.yml token scope" per the Component column) — `build.yml`'s token scope was never covered by any threat entry. Already flagged independently by code review as WR-02. | Independent grep in this audit (`grep -n permissions .github/workflows/build.yml` → no match) + 14-REVIEW.md WR-02 |
| UF-14-02 | Tampering | `.github/workflows/release.yml` | No `dotnet build`/`dotnet test` step runs before `dotnet publish` + asset attach. A `v*` tag can be pushed against any commit — including one that was never pushed to `master`/never ran through `build.yml` — and `release.yml` will still publish and attach the resulting exe to a public GitHub Release with zero CI signal gating it. No threat in the Phase 14 register covers "release published from untested code" (T-14-01 covers publish-command/runner-OS drift only, not test-gating). Already flagged independently by code review as WR-04. | Independent read of `.github/workflows/release.yml` (no build/test step present) + 14-REVIEW.md WR-04 |

## Notes on Scope

- This audit verifies declared mitigations only; it does not perform a blind vulnerability scan. Both unregistered flags above were surfaced because the launching agent's `<additional_context>` and the prior code review (`14-REVIEW.md`) explicitly pointed at them for cross-checking against the threat register — not from independent scanning beyond the threat model's boundaries.
- WR-01 (README screenshot placeholders point at non-existent PNGs) and WR-03 (floating major-version action tags) from `14-REVIEW.md` were considered and are **not** logged as unregistered flags: WR-01 is a documentation-completeness defect, not a STRIDE-relevant security gap (broken image icons carry no exploit surface), and WR-03 matches T-14-SC's mitigation exactly as declared (major-version pinning was the stated bar, not SHA pinning), so it is not new/unmapped attack surface — it's a residual hardening opportunity against an already-closed threat, noted in T-14-SC's evidence above.
- No `## Threat Flags` section was present in any of the three Phase 14 SUMMARY.md files (14-01, 14-02, 14-03) — confirmed via direct grep. The two unregistered flags above were found independently in this audit, not sourced from executor self-reporting.
