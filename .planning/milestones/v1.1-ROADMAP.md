# Milestone v1.1: Automation & Multi-Monitor

**Status:** ✅ SHIPPED 2026-08-01
**Phases:** 6-9, 11 (Phase 10 scoped but not delivered — see Milestone Summary)
**Total Plans:** 21 (19 planned + 2 gap-closure quick tasks)

## Overview

Removed the remaining daily-use friction from v1.0: the app no longer requires opening the GUI to toggle (tray residency, global hotkey), and monitor control generalized from a single hardcoded primary monitor to arbitrary independently-configurable disable/enable sets for any multi-monitor rig. A shared reentrancy-safe orchestration helper now guards every trigger path (button, tray, hotkey) against corrupted state from concurrent toggles. A late-breaking user need (configurable tray close/minimize behavior) was folded in as Phase 11, ahead of the originally-scoped Phase 10 (CLI trigger), which was ultimately dropped from this milestone's delivered scope.

## Phase Details

### Phase 6: Multi-Monitor Data Model & Controller Generalization

**Goal**: Users can configure independent sets of monitors to disable and enable when entering rig mode (not limited to one monitor each), and a user upgrading from v1.0 keeps their existing single-monitor configuration working automatically.
**Depends on**: Phase 5 (v1.0)
**Requirements**: DISPLAY-04, DISPLAY-05, DISPLAY-06, DISPLAY-07, DISPLAY-08
**Success Criteria** (what must be TRUE):
  1. User can select multiple monitors to disable when entering rig mode, not limited to one (DISPLAY-04)
  2. User can select multiple monitors to enable when entering rig mode, e.g. a rig monitor normally kept OS-disabled to save power (DISPLAY-05)
  3. Settings refuses to save a configuration that would disable every monitor, with a clear explanation (DISPLAY-06)
  4. The pre-disable confirmation modal names every monitor being disabled and every monitor being enabled, not just one (DISPLAY-07)
  5. A user upgrading from a genuine v1.0-era settings.json sees their previously-configured single monitor already selected as the disable-set on first launch, with no re-configuration required (DISPLAY-08)

### Phase 7: Shared Toggle-Orchestration Helper Extraction

**Goal**: Every toggle trigger (button, tray menu, hotkey, CLI) runs through one shared, reentrancy-safe pipeline, so a toggle already in progress can never be corrupted by a second concurrent request.
**Depends on**: Phase 6
**Requirements**: CORE-06
**Success Criteria** (what must be TRUE):
  1. If a toggle is triggered while another toggle is already in progress, the app safely rejects the second request rather than risking corrupted state (CORE-06)
  2. Rapidly double-clicking (or otherwise double-firing) the toggle trigger results in exactly one toggle executing, never two overlapping ones (CORE-06)
  3. The existing GUI toggle button's behavior (confirmation dialog, per-step outcome report) is unchanged after the refactor (CORE-06)
**Plans**: 1 plan (wave: 1)
- [x] 07-01-PLAN.md — ToggleOrchestrator (Interlocked non-blocking busy-guard) + ToggleInProgressException + deterministic reentrancy tests, then MainForm/Program.cs routed through the orchestrator (CORE-06)

**Notes:** Reentrancy guard is a non-blocking busy-flag (`Interlocked.CompareExchange`), one shared flag guarding both directions, rejecting the second request immediately (not a queue) — resolved during discussion (D-01/D-02). `ToggleService.cs` confirmed byte-unchanged; 35/35 tests pass including 4 deterministic reentrancy tests.

## Milestone Summary

**Scope Change:** Phase 10 (CLI Trigger + Single-Instance IPC — TRIG-02, TRIG-03) was part of the original v1.1 roadmap (Phases 6-10) but was never planned or executed. Phase 11 (configurable tray close/minimize behavior) surfaced as a genuine user need during Phase 9's rig checkpoint and was prioritized ahead of it. At milestone close, TRIG-02/TRIG-03 were reviewed and dropped to v2 rather than completed — Phase 8/9's tray and hotkey triggers already cover the daily-use case this milestone set out to solve, and a CLI/IPC trigger is now considered a nice-to-have rather than a gap in the core value.

**Key Decisions:**
- Reentrancy guard: non-blocking `Interlocked.CompareExchange` busy-flag on a new `ToggleOrchestrator` wrapper, not logic inside `ToggleService` itself — keeps `ToggleService` a pure, unit-tested step sequencer (Phase 7)
- Multi-monitor sets keyed by stable `DevicePath`, not index/position — avoids repeating a v1.0 fragility (Phase 6)
- `--tray` hidden-startup uses `Application.Run(new ApplicationContext())` with no `MainForm` reference, not `ApplicationContext(mainForm)` — the only pattern that actually suppresses `Show()` on this runtime (Phase 8)
- Autostart via plain `HKCU\...\Run` registry key, not Task Scheduler — matches the app's existing non-elevated execution model
- Toast notifications via `NotifyIcon.ShowBalloonTip`, not packaged-app toast APIs — avoids AUMID/shortcut-registration traps for unpackaged self-contained exes
- Tray icon existence derived as `CloseMinimizesToTray || MinimizeToTray` rather than a single combined flag — lets close-to-tray and minimize-to-tray be configured independently (Phase 11)

**Issues Resolved:**
- `GetAllMonitors()` duplicate-row/dual-primary bug (rig-discovered during Phase 6 checkpoint, fixed as quick task 260728-qj1)
- `Restore()` Source-ID staleness bug for enable-set monitors (Phase 6 gap-closure round 2)
- Settings-migration guard re-corrupting a deliberately-emptied disable set (Phase 6 code review CR-01)
- Non-exception-safe companion-app minimize step that could strand the UI in "Mode: Rig" (Phase 6 code review CR-02)
- `--tray` hidden-start mechanism not actually suppressing the window (Phase 8 rig checkpoint)
- Autostart save-failure recovery path itself throwing unhandled (Phase 8 code review CR-01)
- Hotkey owner-window-destroyed timing bug and Escape-closes-Settings-during-capture bug (Phase 9 rig checkpoint)
- Critical lockout bug: disabling both tray preferences while the window was hidden could leave the app with no reachable UI surface at all (Phase 11 code review, two fix commits, re-verified on rig at milestone close)

**Issues Deferred:**
- CLI trigger + single-instance IPC (TRIG-02, TRIG-03 / Phase 10) — dropped to v2, see Scope Change above
- Toggle history/log (LOG-01) — deferred again, still lower priority

**Technical Debt Incurred:**
- None newly introduced this milestone beyond the pre-existing `.lnk`-launch-target process-name-matching limitation carried over from v1.0 (unchanged, still documented in STATE.md Known Limitations)
