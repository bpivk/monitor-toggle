<objective>
Build the deliberate, explicitly-named startup-gate bypass that Phase 26's update-apply relaunch will reuse: a `--apply-update` flag parsed by `RigToggle.Core`, checked as the very first branch in `Main()`, transferring control to a placeholder relaunch-helper entry point that returns before the single-instance guard is ever touched.

Phase 25 does not implement update-apply logic. It builds and proves the bypass mechanism, so Phase 26 inherits a working, tested gate instead of inventing one under pressure while also debugging a self-replace.

**Decision coverage:**
- **D-03 (rated one-way):** the bypass is a dedicated CLI flag, not a generic guard-disable switch, and it is checked as the very first branch in `Main()` — before the guard is touched, before settings/mode-store bootstrap, before any Form is constructed. Task 1's blocking decision checkpoint exists specifically because this is one-way: Phase 26 (UPDATE-07) binds directly to this flag name and parse contract, so renaming it after Phase 26 ships means touching both phases' code.
- **D-04 (rated one-way):** the flag is the real, final `--apply-update`, parsed by a new `StartupArgs.TryGetApplyUpdateArgs(args)` helper in the same file and shape as the existing `ShouldStartHidden`. Phase 25 ships it with a placeholder body that proves control transferred and the guard/tray/hotkey path was skipped; Phase 26 replaces the body only.
- **Claude's Discretion — how "proves control transferred" is observed:** resolved to a distinct process exit code published through `Environment.ExitCode`, with the constant declared in `RigToggle.Core` so an automated test can assert on it. No marker file, no log line, no temp directory — a marker file would introduce exactly the filesystem side effect that makes the idempotency and concurrency guarantees above unprovable, and would hand a same-user caller an arbitrary-write primitive for nothing.

Purpose: UPDATE-07 — the update-apply relaunch always succeeds despite the single-instance guard being active.
Output: one modified Core helper with tests, one new placeholder entry point, one new branch at the top of `Main()`.
</objective>

  <context>
    D-04 already locks the flag **name** (`--apply-update`) and the **helper name** (`StartupArgs.TryGetApplyUpdateArgs`). That constant is reversible — Phase 26 replaces the body and may retire it — and needs no gate.
  </context>

  <options>
    <option id="option-a">
      <name>Opaque trailing payload (recommended)</name>
      <pros>Signature is `TryGetApplyUpdateArgs(string[]? args, out string[] payload)`; `payload` is every token after the first case-insensitive `--apply-update` occurrence, in order, unvalidated and uninterpreted. Smallest possible one-way surface: the only thing Phase 26 inherits is the token and the rule "everything after it is yours." Phase 26 defines and can freely evolve the positional meaning without ever touching Phase 25's parser or this plan's tests. Matches D-04's `Try*` shape ("detect the flag AND extract the trailing args") literally. Keeps Phase 25 from inventing Phase 26's schema, which would be unplanned scope and would need re-litigating in Phase 26 anyway.</pros>
      <cons>The payload is untyped at the boundary, so Phase 26 does its own positional parsing and its own validation. Phase 25's tests can only prove tokens are extracted in order, not that any particular token is meaningful.</cons>
    </option>
    <option id="option-b">
      <name>Fixed positional arity parsed into a typed record now</name>
      <pros>Phase 26 inherits a validated, typed request object rather than a string array; malformed command lines are rejected in Core, where they are unit-testable, instead of in App. Arguably the more finished-looking contract.</pros>
      <cons>Phase 25 would be committing to Phase 26's argument schema before Phase 26's apply mechanism has been designed or rig-verified — the research sketch for that mechanism is explicitly flagged MEDIUM confidence and not yet verified on real hardware. Getting the arity wrong here is a one-way mistake that has to be unwound across two phases, which is the exact risk this gate exists to avoid. Also imports Phase 26 scope into Phase 25.</cons>
    </option>
    <option id="option-c">
      <name>Flag-only predicate, no payload at all</name>
      <pros>Simplest possible parser, an exact structural twin of `ShouldStartHidden`, trivially testable.</pros>
      <cons>Contradicts D-04, which specifies `--apply-update <args>` and a `Try*`-shaped helper precisely because it must extract trailing args.     </option>
  </options>
