<objective>
Prove the entire auto-update architecture end-to-end on one thin path: a version-stamped
build queries GitHub's latest release, detects a newer version, shows a themed confirm
dialog, downloads the asset, self-replaces at its original path, and relaunches on the new
version.

Purpose: this is the phase's tracer. Every later plan (checksum integrity, never-stranded
recovery, skip-this-version, formatted release notes, manual check) expands outward from
this proven slice. Getting the self-replace-and-relaunch mechanism wrong is the one failure
that cannot be patched later without restructuring — so it is proved first, on the
executor's best early-context tokens, before any expansion lands on top of it.

Output: the version-stamping infrastructure (UPDATE-01), the Core check/compare/decide
layer, the Windows download+spawn adapter, the real `UpdateApplyEntryPoint` body replacing
Phase 25's placeholder, the themed `UpdatePromptDialog`, the `Program.cs`/`MainForm` wiring,
and automated unit coverage of the pure logic.

**(d) `GitHubReleaseFeed` (Core).** This is the app's first-ever `HttpClient` usage — there
is no in-repo analog, so carry an unusually thorough class doc comment citing

`https://api.github.com/repos/{owner}/{repository}/releases/latest`. Set a static
`User-Agent` product header (`RigToggle` plus the running version) — GitHub returns 403
without one. Deserialize with `System.Text.Json` into small private DTO types mapping only

server-side, so no client-side filtering is needed.

**(e) `UpdateVersionComparer` (Core).** Pure static class, no I/O, never throws — the
`ToggleResultFormatter.TruncateForBalloon` discipline. Expose
`public static bool TryParseTag(string? tag, out int major, out int minor)` and
`public static bool IsNewer(Version? runningVersion, string? tagName)`. `TryParseTag`
strips an optional leading `v`/`V`, splits on `.`, and requires the first two segments to
parse as non-negative `int` via `int.TryParse` with `CultureInfo.InvariantCulture`;
additional segments are ignored, fewer than two segments is a parse failure. `IsNewer`
compares `major` first, then `minor`, using ONLY those two components from both sides —
never `Version.CompareTo`, because `new Version("2.2")` yields `Build`/`Revision` of `-1`
while a stamped assembly yields `0`, which makes an equal-version comparison read as
"older" (ARCHITECTURE.md Anti-Pattern 4). Put that rationale in the doc comment, and cite
PITFALLS Pitfall 3 for why the comparison is numeric rather than lexical.

`void ApplyAndRelaunch(string stagedExePath, bool wasStartedHidden)`. Both are documented

`(IReleaseFeed releaseFeed, IUpdateApplier updateApplier, Version runningVersion)` with
`ArgumentNullException` guards, mirroring `ToggleOrchestrator`'s constructor shape. Expose
`public async Task<UpdateCheckOutcome> CheckOnLaunchAsync(Func<ReleaseInfo, bool> confirm,

fetch/compare segment so any exception yields `NotAvailable` — an automatic check must never

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network → app | The GitHub Releases API response and the downloaded exe bytes cross into the process from an untrusted network. |
| app → OS filesystem | The helper process renames and replaces the live application binary at a path the HKCU Run key already points at. |
| local process → helper CLI | The `--apply-update` payload appears verbatim in the process command line, readable and forgeable by any process on the machine. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-01 | Tampering | `GitHubReleaseFeed` asset-URL selection | high | mitigate | Reject any asset URL whose scheme is not `https` or whose host is not `github.com` / `api.github.com` / `objects.githubusercontent.com`; return `null` rather than download from an unexpected host. Never construct an `http://` request URI. |
| T-26-02 | Tampering | downloaded exe bytes (integrity) | high | mitigate | Deferred by design to plan 26-02, which adds SHA256 verification against the published `.sha256` before the swap (D-10/D-11). Until then the trust model is HTTPS plus GitHub hosting integrity — recorded here so the gap is explicit, not accidental. |
| T-26-03 | Spoofing | the freshly-downloaded exe is unsigned (no Authenticode) | medium | accept | No code-signing certificate exists and none is budgeted for a personal single-user tool (PITFALLS Pitfall 6, CLAUDE.md). Accepted, documented limitation. Plain `HttpClient` is chosen deliberately because it does not stamp Mark-of-the-Web, so the unattended relaunch is not gated behind a SmartScreen interstitial. |
| T-26-04 | Elevation of Privilege | `--apply-update` payload supplied by any local process | medium | mitigate | The payload carries only file paths and a process id, never a secret (already a contract in `StartupArgs`' doc comment). The helper refuses to act unless the staged file exists and resolves into the same directory as the target path, and a malformed payload is a total no-op returning the unchanged bypass exit code. |
| T-26-05 | Denial of Service | a failed swap leaves no launchable exe, breaking autostart | high | mitigate | Rename-not-overwrite ordering, plus an immediate rollback that moves `.bak` back if the staged move throws. Full retained-backup lifecycle lands in plan 26-03 (UPDATE-05). |
| T-26-06 | Information Disclosure | the launch-time check reveals app usage to GitHub | low | accept | The request carries only a static product `User-Agent` and no query parameters, machine identifiers, or telemetry. A single unauthenticated GET to a public repo is the minimum possible disclosure for this feature to exist at all. |
| T-26-SC | Tampering | supply chain | high | mitigate | This phase adds ZERO package-manager dependencies — no npm/pip/cargo installs and no new NuGet package (BCL `HttpClient`, `System.Text.Json`, `System.Security.Cryptography` only), so no package-legitimacy checkpoint applies. The downloaded release asset is this phase's entire supply-chain surface and is covered by T-26-01 and T-26-02. |
</threat_model>
