<objective>
Make a failed update unable to strand the app. The helper retains the previous exe as a
backup and records an applied-but-unconfirmed marker; the new exe only earns the right to
delete that backup by actually pumping its message loop; and a launch that finds an
unconsumed marker restores the backup, tells the user why, and relaunches on the version
that worked.

Purpose: UPDATE-05 and D-09. PITFALLS Pitfall 5 and Pitfall 9 together describe the failure
this closes — an unattended update that half-completes leaves the HKCU Run key pointing at a
file that no longer exists, and nobody is watching at the moment it happens. This plan also
lands the first real automated proof of the swap mechanism itself, as a child-process test in
the established Phase 25 style.

Output: the marker model/store, the above-the-guard `UpdateRollbackChecker` state machine,
the helper's marker write and backup retention, the confirmed-healthy watch in `MainForm`,
and both cross-platform and Windows child-process test coverage.
</objective>

  <decision>What on-disk format records "an update was applied but has not yet proven healthy", and what filename holds the retained previous exe?</decision>
  <context>
This is the one genuinely one-way door in this phase. Every other on-disk artifact here is
written and read by the same binary. This one is not: the marker is written by version N's
helper process and read by version N+1's startup code, and the retained backup is created by
version N and deleted by version N+1. Once v2.2 ships and starts writing these files, v2.3
must still be able to read them or auto-rollback silently stops working — and it stops
working precisely in the situation nobody is watching, which is the entire failure mode
UPDATE-05 exists to prevent. There is no migration path: a v2.3 that changed the shape would
simply not recognise a v2.2-written marker and would leave the user on a broken build.

CONTEXT.md leaves the exact shape to planning time (Claude's Discretion), so this is a live
decision, not a re-ask of something already settled. `.planning/phases/26-auto-update/26-PATTERNS.md`
recommends option A on the strength of the existing `ToggleInProgressMarker` /
`JsonToggleInProgressStore` precedent and the codebase's established split between long-lived
config (`AppSettings`) and short-lived crash-detection markers.

Undo cost if wrong: a v2.3 release must ship code that can read BOTH shapes forever, or every
user mid-update at the v2.2→v2.3 boundary loses their rollback safety net.
  </context>
  <options>
    <option id="option-a">
      <name>Dedicated JSON marker file plus a `.bak` sibling of the exe (recommended)</name>
      <pros>Directly mirrors `ToggleInProgressMarker` + `JsonToggleInProgressStore`, which this codebase already trusts for exactly this "risky operation interrupted" shape. Marker lives at `%LocalAppData%\RigToggle\update-applied.json`, well away from `settings.json`, so a corrupt marker can never take user configuration down with it. The backup is `<exe path>.bak` — same directory, same volume, so restoring it is a rename, not a copy. A three-stage field (`Applied` / `FirstLaunchAttempted` / `Reverted`) makes the state machine explicit and loop-free.</pros>
      <cons>One more file and one more store class. The stage enum's member names become part of the persisted format, so renaming a member later is itself a breaking change.</cons>
    </option>
    <option id="option-b">
      <name>Fields on the existing `AppSettings` / `settings.json`</name>
      <pros>No new store class, no new file, and the developer can hand-edit the state in a file they already know about.</pros>
      <cons>Mixes short-lived crash-detection state into long-lived user configuration — the exact separation this codebase deliberately maintains. A settings write during the fragile post-swap window risks corrupting monitor/audio/hotkey configuration. `JsonSettingsStore.Load` degrades to a fresh `AppSettings` on any read failure, which would silently erase an in-flight rollback state rather than surfacing it.</cons>
    </option>
    <option id="option-c">
      <name>Encode the state in filenames only (presence of `.bak` / `.pending` sentinels, no JSON)</name>
      <pros>Zero serialization surface; nothing to version. Trivially inspectable in Explorer.</pros>
      <cons>Cannot carry the two version strings the D-09 revert toast must name ("Update to vX failed to start — reverted to vY"), so the user gets a revert with no explanation. Distinguishing "first attempt" from "second attempt" needs a second sentinel file, which is a worse state machine than one JSON field.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c (option-a is the planner's recommendation and matches 26-PATTERNS.md)</resume-signal>

**(a) `UpdateAppliedMarker` (Core/Models).** `public sealed record UpdateAppliedMarker(string
NewVersion, string PreviousVersion, DateTimeOffset AppliedAtUtc, UpdateMarkerStage Stage)`
plus `public enum UpdateMarkerStage { Applied, FirstLaunchAttempted, Reverted }` in the same
file. Doc-comment it as disk-persisted cross-version state: written by the outgoing version's
helper process and read by the incoming version's startup code, which is why the member names
are part of the format and may not be renamed casually. Follow
`ToggleInProgressMarker.cs`'s file shape — one record, no behaviour.

**(b) `IUpdateAppliedMarkerStore` + `JsonUpdateAppliedMarkerStore`.** Mirror
`IToggleInProgressStore` / `JsonToggleInProgressStore` member-for-member: `Save`, `TryLoad`,
`Clear`, plus the private `Exists`. Copy the temp-file-then-`File.Move(overwrite: true)`
atomic write, the `TryLoad` that catches `JsonException`, `IOException`, and
`UnauthorizedAccessException` and returns null rather than throwing, and the `Clear` that
swallows `IOException` and `UnauthorizedAccessException`. Serialize the enum as a string so
the on-disk value is self-describing rather than a bare ordinal that a future member reorder
would silently reinterpret — configure a `JsonStringEnumConverter` in the serializer options
and say why in a comment. Deliberately do NOT reuse or extend the existing toggle-in-progress
marker or its store: these are two distinct crash-detection concerns and this codebase keeps
such concerns in separate types (the same instinct PITFALLS Pitfall 7 documents for the
reentrancy guard).

**(c) `UpdateApplyEntryPoint` — retain the backup and record the marker.** In the successful
swap branch added by plan 26-01, after `File.Move(stagedPath, targetPath)` succeeds and
before the relaunch, construct a `JsonUpdateAppliedMarkerStore` over
`Path.Combine(Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
"RigToggle", "update-applied.json")` and `Save` a marker with `Stage = Applied`. Derive
`NewVersion` from the staged file via `FileVersionInfo.GetVersionInfo(...)` before the move
(read it while the path is still valid) and `PreviousVersion` the same way from the target
path before the rename; fall back to the string `unknown` if either read throws. Note in a
comment that this helper computes the base path itself because it runs above every
`Program.cs` bootstrap step by contract and cannot borrow that file's `basePath` local. Leave
the `.bak` file in place — do not delete it here and do not delete it in any code path this
helper owns. Wrap the marker write in a try/catch that logs and continues: a marker-write
failure must not abort a swap that already succeeded on disk.

**(d) `UpdateRollbackChecker` (App).** New `internal static class`, a sibling of
`StartupRecoveryChecker`. Expose
`internal static bool Run(IUpdateAppliedMarkerStore markerStore, string runningExePath, out
string? revertNotice)` returning true when the caller must return from `Main` immediately,
and `internal static void ConfirmHealthy(IUpdateAppliedMarkerStore markerStore, string
runningExePath)`. Add the file-local best-effort `Log` helper in this codebase's usual shape.
`Run`'s state machine, with `revertNotice` defaulting to null:
  - Marker is null: best-effort delete an orphaned `<runningExePath>.bak` and
    `<runningExePath>.failed` if either exists (ARCHITECTURE.md's Robustness table calls for
    exactly this next-launch cleanup), return false.
  - `Stage == Applied`: this is the new version's very first launch. Re-save the same marker
    with `Stage = FirstLaunchAttempted` — consuming the attempt so a crash later in this same
    boot cannot be mistaken for a fresh first attempt — and return false so startup continues.
  - `Stage == FirstLaunchAttempted`: the previous boot of this version never reached
    confirmed-healthy. If `<runningExePath>.bak` does not exist, clear the marker, log, and
    return false (nothing to restore; never loop). Otherwise rename `runningExePath` to
    `<runningExePath>.failed` (renaming a running exe is permitted; deleting it is not), move
    the `.bak` back onto `runningExePath` so the restored binary lands at the identical path
    the HKCU Run value already names (Pitfall 9), re-save the marker with `Stage = Reverted`,
    relaunch `runningExePath` with the `ProcessStartInfo { UseShellExecute = true }` shape —
    forwarding `--tray` when `StartupArgs.ShouldStartHidden(Environment.GetCommandLineArgs())`
    is true — and return true. If any step throws, undo what has been done so far as far as
    possible, clear the marker so the next launch cannot loop, log, and return false.
  - `Stage == Reverted`: this process IS the restored previous version. Clear the marker, set
    `revertNotice` to `Update to v{NewVersion} failed to start — reverted to
    v{PreviousVersion}.`, and return false.
`ConfirmHealthy` clears the marker and then best-effort deletes `<runningExePath>.bak` and
`<runningExePath>.failed`, each in its own try/catch. Document that this is the commit point
PITFALLS Pitfall 5 requires: the backup is removed only once the new exe has demonstrably
run, never merely because a file move completed.

**(e) `Program.cs` wiring.** Construct
`var updateMarkerStore = new JsonUpdateAppliedMarkerStore(Path.Combine(basePath,
"update-applied.json"));` immediately after `settingsStore`, and insert
`if (UpdateRollbackChecker.Run(updateMarkerStore, Environment.ProcessPath ?? string.Empty,

placement is load-bearing for the same reason the `--apply-update` branch is: the rollback
path spawns a replacement process, and doing that while holding the mutex is exactly the race
PITFALLS Pitfall 4 describes. Do not move the existing settings-load, `DebugLog`, guard,

`mainForm.InitializeTrayState()` and before `guard.MarkReady()`, call
`mainForm.BeginUpdateHealthWatch(() => UpdateRollbackChecker.ConfirmHealthy(updateMarkerStore,
Environment.ProcessPath ?? string.Empty));` and, when `revertNotice` is not null,
`mainForm.ShowUpdateRevertNotice(revertNotice);`.

**(f) `MainForm` health watch and revert notice.** Add
`public void BeginUpdateHealthWatch(Action onConfirmedHealthy)`: create a
`System.Windows.Forms.Timer` with `Interval` of 10000, wire a `Tick` handler that stops and
disposes the timer then invokes the callback inside a try/catch, and start it. Doc-comment
that reaching a timer tick is the deliberate confirmed-healthy signal CONTEXT.md's Claude's
Discretion note asks for — a tick can only fire once the message pump is actually running, so

native chrome, and never the `Error` icon.
