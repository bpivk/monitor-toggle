<objective>
Close the corrupted/truncated-download gap: publish a SHA256 checksum alongside every
release asset, and make the updater verify the downloaded exe against it before anything on
disk is touched.

Purpose: D-10/D-11 are a deliberate hardening step the developer chose to include even
though UPDATE-01..06 do not mandate it — they directly close the gap PITFALLS Pitfall 5 and
the Security Mistakes table both flag. Verifying in the downloader (while the app is still
running with a working UI) rather than in the helper process means a mismatch surfaces as an
ordinary toast on the still-alive old version, not as a half-swapped installation.

Output: a new `release.yml` checksum step, `ReleaseInfo.ChecksumDownloadUrl`, a Core
`UpdateChecksum` utility, verify-before-spawn in `WindowsUpdateApplier`, and automated
coverage of both the checksum utility and the feed's asset resolution.
</objective>

**(a) `release.yml` (D-10).** Add a step named `Compute SHA256 checksum` between the publish
step and the existing `Attach exe to GitHub Release` step. It runs on `windows-latest`, so
use PowerShell: compute the hash of
`src/RigToggle.App/bin/publish/win-x64/RigToggle.App.exe` with `Get-FileHash -Algorithm
SHA256` and write a single `sha256sum`-style line — the lowercase hex digest, two spaces,
then the bare filename `RigToggle.App.exe` — to
`src/RigToggle.App/bin/publish/win-x64/RigToggle.App.exe.sha256`. Then extend the existing
`softprops/action-gh-release@v3` step's `files:` value from a single scalar path to a
multi-line list containing both the exe and the new `.sha256` file. Do not change the raw-exe
attachment path, the action version, the trigger, or `permissions:` — D-10 is explicit that
what is already attached does not change, only that a second file joins it.

**(b) `ReleaseInfo` (Core/Models).** Append a positional member
`string? ChecksumDownloadUrl` to the record. Nullable because a release published before this
phase (every tag through v2.1) has no checksum asset; document that on the member, along with
the fail-closed consequence: an update offered from a pre-checksum release cannot be verified
and therefore cannot be applied.

**(c) `GitHubReleaseFeed` (Core).** In the asset-selection block, resolve a second asset
whose `name` equals `RigToggle.App.exe.sha256` and run its `browser_download_url` through the
SAME scheme/host allow-list already applied to the exe asset (`https` only; host in
`github.com`, `api.github.com`, `objects.githubusercontent.com`). Pass it through as
`ChecksumDownloadUrl`, or `null` when the asset is absent or fails the allow-list. Absence of
the checksum asset must NOT cause the whole release to be discarded — return the
`ReleaseInfo` with a null `ChecksumDownloadUrl` and let the applier decide, so the "no
checksum published" case is visible and reportable rather than silently indistinguishable
from "no release found".

**(d) `WindowsUpdateApplier.DownloadAndStageAsync` (Windows).** After the exe stream has been
written to the staged path and before returning, verify integrity: if
`release.ChecksumDownloadUrl` is null, delete the staged file and throw an
`InvalidOperationException` whose message states that the release published no checksum and
the update cannot be verified. Otherwise fetch the checksum text with
`HttpClient.GetStringAsync`, compute `UpdateChecksum.ComputeSha256(stagedPath)`, and compare
with `UpdateChecksum.Matches`. On mismatch, delete the staged file and throw an
`InvalidOperationException` naming the expected and actual digests (truncated to their first
16 characters so the message stays inside the balloon's 250-character budget). Both throws
propagate to `MainForm`'s existing post-confirm catch, which already renders the D-08 Warning
toast — that is deliberate and is exactly what D-11 asks for ("a mismatch is treated as an
apply failure, same toast-and-rollback behavior as D-08, not a separate failure mode"); say so
in a comment so a future editor does not "improve" it into its own bespoke failure path.
Place this verification so that no code path can reach `ApplyAndRelaunch` with an unverified
staged file, and record in the method's doc comment that verification lives here — in the
still-running old process with a working tray icon — rather than in the helper process, so a
mismatch never produces a half-swapped installation.

**(e) `UpdateChecksum` (Core).** New pure static class, no I/O beyond reading the file it is
handed, in the `ToggleResultFormatter` discipline (defensive, never throws on degenerate
input). `public static string ComputeSha256(string filePath)` opens a `FileStream` and uses
`System.Security.Cryptography.SHA256.HashData(stream)`, returning
`Convert.ToHexString(hash).ToLowerInvariant()`.
`public static bool Matches(string? computedHex, string? publishedText)` returns false for
any null/whitespace input, extracts the first whitespace-delimited token from
`publishedText` (so a full `sha256sum`-style line works as-is), requires that token to be
exactly 64 characters of `[0-9a-fA-F]`, and compares case-insensitively with
`StringComparer.OrdinalIgnoreCase`. Document that "cannot establish the checksum" always
resolves to `false`, never to `true` — fail closed. Note in the class doc comment that
`System.Security.Cryptography` is BCL and adds no package dependency, and that no prior
hash-comparison code exists anywhere in this repository to pattern-match against.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network → app | The GitHub Releases API response, the downloaded exe bytes, and the downloaded checksum text all cross into the process from an untrusted network. |
| CI → release artifact | `release.yml` produces both the exe and the digest that vouches for it, so the digest is only as trustworthy as the workflow run and GitHub's asset hosting. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-02 | Tampering | downloaded exe bytes (integrity) | high | mitigate | SHA256 computed over the staged file and compared against the published `.sha256` before `ApplyAndRelaunch` is reachable; mismatch deletes the staged file and throws, surfacing as the D-08 Warning toast. |
| T-26-07 | Tampering | the checksum file itself is fetched over the same channel as the exe | medium | accept | A MITM able to rewrite the exe can rewrite the sidecar digest too — the digest defends against corruption and truncation, not against a compromised transport. Accepted: the transport defence is HTTPS plus GitHub's own hosting integrity (threat T-26-01's host allow-list), and code signing, which would close this properly, is out of budget for a personal single-user tool (PITFALLS Pitfall 6). |
| T-26-08 | Spoofing | a release published before this phase has no `.sha256` asset | medium | mitigate | Fail closed — a null `ChecksumDownloadUrl` throws before staging completes rather than silently skipping verification. Verified by the "missing checksum" test case. |
| T-26-01 | Tampering | asset-URL host for BOTH the exe and the checksum | high | mitigate | The same scheme/host allow-list is applied to the checksum asset URL as to the exe asset URL; a downgraded or off-host URL yields `null` rather than a fetch. |
| T-26-SC | Tampering | supply chain | high | mitigate | Zero package-manager installs in this plan — `System.Security.Cryptography` is BCL. No package-legitimacy checkpoint applies. The release asset remains the only supply-chain surface, now covered by T-26-01 and T-26-02. |
</threat_model>
